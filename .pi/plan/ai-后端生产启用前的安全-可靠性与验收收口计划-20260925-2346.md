# AI 后端生产启用前的安全、可靠性与验收收口计划

## 目标与边界

目标是把现有 AI 后端从“源码设计较完整、真实环境证据不足”推进到“可在隔离环境验收、可灰度启用、可随时关闭和追溯”。

只覆盖以下 AI 直接相关范围：

- AI Profile、AI Search、AI Compatibility、AI Recommend、AI Advisor/Avatar、Moxiang Journey；
- AI 任务队列、Worker、租约、重试、派生数据和删除传播；
- AI Provider、审计、日志脱敏、retention；
- AI 半双工/全双工实时语音及其临时音频；
- AI API 契约、AI 专项测试、发布证据和灰度闸门。

不在本计划内：普通支付、红娘后台整体数据范围、非 AI 的普通媒体业务、腾讯直播业务本身，以及无关的全仓架构重构。保持现有工作区修改，不覆盖、不清理、不回滚用户变更。

## 当前基线

- AI 功能开关默认关闭，生产启用已有三项审批门禁：`ai_policy_approved`、`ai_provider_approved`、`ai_retention_policy_version`。
- `app/services/ai/tasks.py` 已有幂等、租约、并发冲突重读、版本/同意复查等较成熟机制。
- `app/workers/ai_worker.py` 已有任务异常隔离、语音音频清理、Memory State TTL 清理和 retention 调度。
- 已有 AI 审计脱敏、指标和运维手册。
- 当前主要阻断项：实时语音使用长期 JWT query token；WebSocket 不复查 session 撤销状态；Provider 日志记录内容前 40 字；AI 真实 MySQL/Redis/Provider 环境尚未验收；AI API 文档和 200/202 契约存在漂移。

## 阶段 2：实时 AI WebSocket 鉴权改造

### 2.1 增加一次性 AI WebSocket ticket

参考 `live_ws.py` 的既有模式，在 `app/core/security.py` 增加：

- `create_ai_ws_ticket(user_id, session_id, ticket_id, expires_seconds)`；
- `decode_ai_ws_ticket(token)`；
- 独立 token type，例如 `ai_ws_ticket`；
- 必须包含 `sub`、`sid`、`jti`、`iat`、`exp`。

在现有语音 HTTP 路由中增加受保护的 ticket 签发入口，使用 `get_current_user`，并通过 Redis `consume_once` 限制单次使用。长生命周期 access JWT 不再直接进入 WebSocket URL。

涉及文件：

- `app/core/security.py`
- `app/api/routes/voice.py`
- `app/core/redis.py`（仅复用现有一次性消费能力）
- `app/schemas/voice.py` 或现有语音 schema 文件

### 2.2 抽取可复用 session/账号状态校验

将 `app/api/dependencies.py:get_current_user` 中的以下校验抽成可被 HTTP 和 WebSocket 复用的服务函数：

- token 中的 `user_id/session_id` 与数据库记录匹配；
- `user_session.status=1`；
- `revoked_at IS NULL`；
- `access_expire_at` 未过期；
- 用户账号状态正常。

HTTP 依赖保持现有行为；WebSocket 在 `accept()` 前执行同样校验。

建议落点：`app/services/auth.py` 或独立的 `app/services/voice/auth.py`，避免 service 层导入路由层。

### 2.3 改造两个语音 WebSocket

修改：

- `app/api/routes/voice_ws.py`
- `app/api/routes/voice_moxiang.py`

行为要求：

- 接收短期 `ticket`，不再接收长期 access JWT；
- 校验 ticket 类型、过期时间、jti 单次消费；
- 校验 session 和账号状态；
- 失败在 `accept()` 前关闭，使用稳定 close code；
- 日志只记录 `user_id/request_id/ticket_id hash`，不记录原 ticket。

测试：

- `tests/test_voice_ws.py`
- `tests/test_voice_conversation.py`
- `tests/test_voice_moxiang_master.py`
- `tests/test_realtime_voice_gate.py`

至少覆盖：缺 ticket、伪造 ticket、过期 ticket、重复 ticket、session 撤销、账号封禁、正常连接、断线和 Redis 不可用。

## 阶段 6：灰度启用和回滚

### 灰度顺序

1. 生产保持 `AI_MASTER_ENABLED=false` 完成部署验证；
2. 开启 Profile/Search/Recommend 的内部或影子模式，不向用户外显；
3. 开启 Compatibility shadow，验证结果质量、延迟、Provider 失败率；
4. 小比例开启 Compatibility 外显；
5. 再评估 Advisor/Avatar；
6. 半双工语音单独灰度；
7. 最后才评估 Moxiang Journey 和全双工实时语音。

### 回滚方式

- 第一优先级：关闭具体 feature switch；
- 第二优先级：关闭 `AI_MASTER_ENABLED`；
- 保留任务和审计数据，禁止直接删除状态以“伪造恢复”；
- Worker 出现积压时暂停新任务入口，保留 cleanup/retention；
- Provider 故障时切换到关闭或明确的安全 fallback，不自动切换到未审批 Provider；
- 回滚后核对是否有未完成 cleanup、死信、audit_lost 和隐私残留。

## 最终验收标准

### 必须全部满足

- 生产缺少审批或凭据时 AI 无法启动；
- 长期 access JWT 不出现在 AI WebSocket URL 或日志中；
- 被撤销 session/封禁账号无法建立 AI WebSocket；
- AI 日志、审计表和 evidence 不含原始 prompt、回答、音频内容或敏感字段；
- AI 任务幂等、租约、重试、版本围栏、授权撤回在真实 MySQL/Redis 中通过；
- 派生数据删除和 retention 有真实执行证据；
- Provider 失败、限流和非法输出有稳定错误码、重试和告警；
- AI 路由、状态码、OpenAPI、文档和前端轮询契约一致；
- AI 单元测试、AI 集成测试、相关 Ruff 检查全部通过；
- 完成至少一次 Worker 重启、Provider 故障、Redis 故障、删除传播和 AI 总闸回滚演练。

### 明确禁止

- 未完成真实依赖验收前打开生产 AI；
- 用 Mock Provider 的结果代替真实 Provider 验收；
- 用静默 skip、源码字符串断言或伪造 evidence 代替行为验证；
- 为了通过门禁删除隐私、删除传播或失败恢复测试；
- 在日志、测试输出或文档中写入任何真实密钥或用户原文。

## 实施顺序与交付物

建议按 3 个迭代周期执行：

- **迭代 1（安全止血，2～3 个工作日）**：日志脱敏、AI 音频访问、WS ticket、session 校验、回归测试；
- **迭代 2（可靠性闭环，4～6 个工作日）**：真实 MySQL/Redis、任务/Worker、consent、删除传播、retention、Provider 故障测试；
- **迭代 3（契约与发布，3～5 个工作日）**：OpenAPI/文档对齐、service 解耦、AI CI、Provider 沙箱、release evidence 和灰度/回滚演练。

最终交付：

1. AI 安全和隐私修复；
2. AI 专项回归与集成测试；
3. AI API/任务/Provider 契约文档；
4. AI CI job 和可复现集成环境说明；
5. AI release evidence、灰度清单、监控阈值和回滚记录。
