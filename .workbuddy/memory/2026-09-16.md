## 修复生产 500：`1054 Unknown column 'audit_status'`

**现象**：生产 `/admin/customer-leads` 列表 500，报 `Unknown column 'audit_status' in 'field list'`。

**根因（链路完整还原）**：
- 提交 `8ec8ff1` 新增 `_ensure_m4_columns` / `_ensure_m5_columns` / `_ensure_m6_columns` / `_ensure_m7_columns`，传给 `_ensure_table_columns` 的列定义**缺 `字段名` 前缀**。
- `_ensure_table_columns` 模板是 `ALTER TABLE {表} ADD COLUMN {列定义}` → 生成非法 SQL（MySQL 1064），异常被 `except` 降级成一条 WARNING，**静默吞掉**。
- 结果 M4/M5/M6/M7 这批列在**所有已存在的库**上都没建上。
- 提交 `588029e` 新增 `_named_columns` 修好了清单，但生产 `AUTO_INIT_DB=false`，修复后的初始化脚本从未在线上执行 → 生产持续 500。
- 本地库核对：列全在（本地跑过修复后的初始化），所以只有生产炸。

**改动**：
1. `database_setup_marriage.py`：新增 `_assert_column_definition()`，在 `_ensure_table_columns` 里对缺前缀的列定义**快速失败抛 ValueError**（堵住静默吞异常这个根因）。+17 行。
2. `migrations/m4_m7/20260916_01_m4_m7_backoffice_columns_up.sql` + `_down.sql`：生产定向补列迁移，幂等（`information_schema` 守卫 + `group_concat_max_len` 放开到 1MB，因为 `offline_activity` 27 列拼出的 ALTER 超默认 1024 上限）。已演练 补列 → 重复执行幂等 → down 生效。
3. `scripts/report_db_drift.py`：**只读**结构缺口体检。包装 cursor，读语句真跑、写语句只记录不执行，于是"被记录的语句"就是需要在目标库补的 DDL。可随时对生产跑。
4. `tests/test_m4_m7_column_migration.py`：锁住三件事——缺前缀快速失败、四个 helper 生成的 ALTER 列名合法、服务层 SELECT 的列必须存在于建表定义。
5. `.gitignore`：`migrations/` 整体被忽略，只放行了 `live/*.sql`，新目录进不了库 → 补 `!migrations/m4_m7/` + `!migrations/m4_m7/*.sql`。

**验证**：`114 passed`（新测试 + 5 个受影响模块回归）。新增文件 ruff 全过；`database_setup_marriage.py` 的 3 条 ruff 报错为**改动前既有**（F601 重复 key `user_report`、2× F541 多余 f 前缀）。

## 后台账号注销申请（M10 延伸）2026-09-16 下午

**需求**：截图里「删除账号」弹窗调 `DELETE /admin/matchmaker/accounts/{id}` 返回 405；用户要求该接口改为提交注销申请，并补列表查询与审核页。

**设计决策**：注销申请的对象是**后台账号**（matchmaker_admin_account），不是会员——reg-user-all 页列表/弹窗展示的都是 admin 账号字段；会员侧的 `/admin/user-cancellations`（user_cancellation 表）已存在且语义不同。新表 `admin_account_cancellation`，唯一键 `(account_id, status)` 防重复 pending（与 user_cancellation 同款技巧）。

**业务流**（按 UI 文案实现）：
1. DELETE 提交申请 → 快照 username/display_name/linked_user_id/previous_status + 四个关联项（会员资料=linked user 存在、推广/服务红娘=user_matchmaker_apply status IN(1,2)、合伙=partner_team owner status=1），账号置 status=2 暂停登录 + 吊销会话；自己注销自己 → 403。
2. 审核取消（approve=false）→ 按 previous_status 快照恢复账号状态。
3. 确定注销（approve=true）→ status=2 + `matchmaker_user_id=NULL`（解绑）+ 清空 matchmaker_admin_permission + 吊销会话。
4. 审计 `account_cancellation.submit/approve/reject`，resource_type `admin_account_cancellation`。

**端点**（挂在 matchmaker_admin_account 路由，权限均 `matchmaker.account.manage`）：
- `DELETE /admin/matchmaker/accounts/{id}` 提交申请（返回申请项）
- `GET /admin/matchmaker/account-cancellations?page&page_size&status(all|pending|approved|cancelled)&keyword`
- `POST /admin/matchmaker/account-cancellations/{id}/review` `{approve, note}`

**前端**（独立仓库，未提交）：`admin-endpoints.ts` 加 `accountCancellations` / `reviewAccountCancellation` + `AccountCancellationItem/Page` 类型；`reg-user-cancel/page.tsx` 从静态 mockup 接真实列表+状态筛选+关键字搜索+AdminPagination，取消注销/确定注销带 window.confirm；顺手修了 4 个页面 8 个 UserCandidatePicker 相关的**预存在** tsc 报错（三个 UserCandidate 接口字段改可选并对齐 UserCandidate）。

**验证**：`tsc --noEmit` 全绿；后端新测试 7 项 + 账号域回归 43 passed；直连本地库全链路冒烟（提交/暂停登录/重复 409/列表/取消恢复/确定注销清权限/重复审核 409/审计两条）通过且无残留；`database_setup_marriage.py` 幂等建表后 drift 体检归零。
