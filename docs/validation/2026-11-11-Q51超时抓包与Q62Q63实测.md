## 1. Q51：怎么把「客户端感知」和「后端日志」对上

客户端的 `request:fail timeout` 在后端可能留下记录、也可能一个字都没有。同一个症状背后
是三种互斥故障，所以先要一次**能互相指认的快照**。

对账的做法是**客户端自己给这次请求编号**：后端 `app/main.py` 的日志中间件接受调用方传入的
`X-Request-ID`（匹配 `REQUEST_ID_PATTERN` 才采纳），并把它回写到响应头；
`app/core/logging.py` 的 formatter 每条日志都带 `request_id=%(request_id)s`。
于是同一个 id 既能查到客户端耗时，也能 grep 到后端那一行 `request_completed ... duration_ms=`。

### 1.1 实测数据

| 请求 | 状态 | 耗时(ms) | 回显 `X-Request-ID` | 判定 |
| --- | --- | --- | --- | --- |
| `GET /health` | 200 | 130 | 是 | ok |
| `GET /ai/capabilities`（无 token） | 401 | 18 | 是 | auth（路由可达） |
| `GET /ai/capabilities`（带 token） | 200 | 19 | 是 | ok |
| `GET /support/help-docs` | 200 | 12 | 是 | ok |
| `GET /support/feedback/mine` | 200 | 23 | 是 | ok |
| `GET /ai/profile/thoughtfulness`（读缓存） | 200 | 17 / 15 | 是 | ok |
| **`POST /ai/profile/thoughtfulness`（同步等模型）** | **200** | **10867 / 11491** | **是** | ok |

### 1.2 判定

- **不是「未部署」**：没有 404/405，所有路由都命中了。
- **不是「反代超时」**：反代先掐的话客户端拿到的是 502/504、且**响应里不会有后端回写的
  `X-Request-ID`**。本次 11 条请求全部回显了 id，说明响应确实穿透了网关。
- **是「客户端先放弃」**：模型侧稳定在 **10.9~11.5 秒**，端侧默认超时 **15 秒**，只剩 3.5 秒余量。
  内容稍长、模型稍慢、网络首包抖一下，就先撞 15 秒 —— 用户看到 `request:fail timeout`，
  而后端这时还在跑、结果白生成、额度已扣。

### 1.3 当前代码状态

同步等模型的调用已全部显式抬到 `AI_LLM_TIMEOUT`（45s，`api/config.uts`）：

| 接口 | 前端超时 |
| --- | --- |
| `POST /ai/profile/thoughtfulness` | `AI_LLM_TIMEOUT` |
| `POST /ai/profile/polish` | `AI_LLM_TIMEOUT` |
| `POST /ai/advisor/sessions/{id}/advice` | `AI_LLM_TIMEOUT` |
| `POST /ai/roleplay/submit` | `AI_LLM_TIMEOUT` |
| `/ai/avatar/*` | 60000 |
| `GET /ai/profiles/{subject}/narrative` | 8000（只读 worker 产物，实测 32~51ms，故意压短） |

**未使用 `AI_LLM_TIMEOUT` 的 AI 端点都是「入队 + 立刻返回」的异步任务**（`/ai/search-drafts`、
`/ai/compatibility/*`、`/ai/profile-card/*`、`/ai/search-suggestions/generate`），不阻塞等模型，
保持默认 15 秒是对的 —— 给它们也套 45 秒只会让真挂了的请求多卡 30 秒。

### 1.4 复现命令

```bash
# 公开端点
python scripts/probe_request_trace.py

# 打真 AI 端点（会真的产生模型调用）
python scripts/probe_request_trace.py \
    --login-phone 13100000000 --login-password password123 \
    --probe "POST /ai/profile/thoughtfulness {}" \
    --probe "GET /ai/profile/thoughtfulness" \
    --repeat 2 --timeout 90
```

拿到输出里的 `probe-xxxxxx-NN`，去后端日志 grep：

```bash
grep 'request_id=probe-xxxxxx-00' api.log
# 期望一行：request_completed method=POST path=/api/v1/ai/profile/thoughtfulness
#          status=200 duration_ms=10867.2 ... request_id=probe-xxxxxx-00
```

**如果 grep 不到这一行**，才说明后端根本没收到（部署/反代问题）；grep 得到且 status=200，
就是客户端先放弃，按 §1.3 对照表处理。

## 2. Q62：AI 军师到底能不能测

以前判断"没有接口测不了"，实测下来是两件事叠在一起：能力位开关 + 门禁位置。

### 2.1 测试服实测（端到端跑通）

| 步骤 | 结果 |
| --- | --- |
| `GET /ai/capabilities` | 200 `{"master": true, "profile": true, "search": true, "compatibility": true, "voice": false, "advisor": true, "avatar": true}` |
| `POST /ai/advisor/sessions` | 201，会话 id=4 |
| `POST /ai/advisor/sessions/4/advice` | **201，5273ms**，返回 `analysis` + 2 条 `suggestions` + `risk_level` + `next_step` + `disclaimer` |
| `DELETE /ai/advisor/sessions/4` | 204（探针数据已清理） |

**所以「没有接口」不成立**：测试服 `advisor=true`，建议生成 5.3 秒出结果，模型确实在跑。

### 2.2 本机为什么一直「暂未开放」

- `capabilities.advisor` = `_usable(AiFeature.ADVISOR)` → `is_ai_feature_enabled` →
  `ai_master_enabled and ai_enabled`。本机 `.env` 里**一条 `AI_*` 都没有**，两个都吃默认 False。
- 非 production 免审批（`_production_approvals_ok` 直接 True），所以卡点不是审批。
- 另外 `app/api/routes/ai_advisor.py` 的五个路由**都没有 `require_ai_feature`**，
  门禁只在 `ai_provider.complete()` 内部。所以即使 capability 报 true，
  `ai_provider == "mock"` 或 `ai_api_key` 为空时仍会 503 `AI_TEMPORARILY_UNAVAILABLE`
  —— 这是「能进页面但一生成就失败」的来源。

### 2.3 本轮修复的落点

`pagesSub/chat/detail.uvue` 的 `openAiAdvisor` 不再把三种情况抹成一句「暂未开放」：
网络异常 / 5xx / 透传后端 message / 取不到状态 四分法，并按 `master` 区分
「AI 功能总开关未开启」与「AI 军师暂未对你开放」。

## 3. Q63：撤回不外露，服务端实测

### 3.1 端到端（测试服真实读写）

| 步骤 | 结果 |
| --- | --- |
| 发一条消息（`POST /chat/sessions/3/messages`） | 201，`message_id=15` |
| 发完看会话列表 `last_message` | 等于这条消息原文（符合预期） |
| 撤回（`POST /chat/messages/15/recall`） | 200，`content="消息已撤回"`，`revoked=true` |
| 撤回后看会话列表 `last_message` | **回到上一条未撤回消息**，不含被撤回的原文 ✅ |
| 撤回后看消息体 | `{"content": "消息已撤回", "revoked": true}` ✅ |
| `message_recalled` 通知 | 本人 0 条 —— 通知只发给**对方**（actor 是撤回者），符合设计 |

### 3.2 代码层面的三条保证

- `list_chat_sessions` 的三个 `last_visible_type/content/time` 子查询都带 `revoked_at IS NULL`；
- `recall_message` 撤回后按会话内最新一条未撤回消息**重算** `chat_session.last_message`；
- `emit_notification(event_type="message_recalled")` 的 content 固定是「对方撤回了一条消息」，
  `payload` 只有 `message_id`，不带原文。

### 3.3 前端配套（本轮）

- 撤回后清掉输入框里的引用草稿（引用预览会露原文）；
- 已撤回消息保留「仅自己删除」（旧实现整条 return，撤回消息永久占位删不掉）；
- 长按新增「多选」+ 批量「仅自己删除」，逐条走 `/chat/messages/{id}/for-me`，部分失败保留失败项；
  跨用户撤回仍单条走服务端召回口径，不批量化；
- 通知中心补 `chat_session` / `chat_session_request` 分支（撤回通知只带 `session_id`、
  不带对方 `userId`，以前点进去必然「该通知关联内容已不可查看」）。
