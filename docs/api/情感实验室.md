## `PUT /api/v1/emotion-lab/profile-source`

**基本信息**

- 用途：把情感实验室测出的 16 型结果（或用户手选结果）写入个人资料
- 完整 URL：`/api/v1/emotion-lab/profile-source`
- Method：`PUT`
- 是否需要登录：是（`Authorization: Bearer <access_token>`）
- 所需角色/权限：任意登录用户；无会员、实名、资料完整度要求
- Content-Type：`application/json`；响应 `application/json`
- 成功状态码：`200 OK`

**请求参数**

| 参数 | 位置 | 类型 | 必填 | 默认 | 校验 | 含义 |
|---|---|---|---|---|---|---|
| `mbtiType` | body | string | 是 | — | 16 型枚举，大小写敏感；也接受 `mbti_type` | MBTI 类型，如 `ENFP` |
| `source` | body | string | 否 | `self_reported` | `assessment` / `self_reported` | 结果来源：测评 / 手选 |
| `confirmed` | body | boolean | 是 | `false` | 必须为 `true` | 用户明确确认"同步到资料"；缺省或 `false` 一律拒绝 |
| `resultId` | body | string/null | 条件必填 | `null` | ≤64 字符 | `source=assessment` 时必填。E1.5 只透传、不校验其有效性（会话表在 E2 才有） |

请求体示例：

```http
PUT /api/v1/emotion-lab/profile-source
Authorization: Bearer <access_token>
Content-Type: application/json

{"mbtiType":"ENFP","source":"self_reported","confirmed":true}
```

测评结果同步示例：

```json
{"mbtiType":"INFP","source":"assessment","confirmed":true,"resultId":"res_20261029_ab12"}
```

非法示例（缺确认）：

```json
{"mbtiType":"ENFP","source":"self_reported","confirmed":false}
→ 422 {"detail":{"code":"PROFILE_SYNC_CONFIRMATION_REQUIRED","message":"同步资料前需要明确确认","retryable":false}}
```

**返回参数**

| 字段 | 类型 | 必返 | 空值含义 | 说明 |
|---|---|---|---|---|
| `mbtiType` | string | 是 | — | 已写入资料的类型（16 型枚举） |
| `source` | string | 是 | — | 回显请求来源 |
| `assessmentVersion` | string/null | 是 | E1.5 恒为 `null` | 服务端计分版本；E2 由 submit 返回 |
| `resultId` | string/null | 是 | 非测评来源时为 `null` | 回显请求的端侧结果 id |
| `confirmedAt` | string(datetime)/null | 是 | 资料无变更时间时补当前时间 | 本次确认时间；**资料未变化时返回上次变更时间**（幂等） |

返回示例：

```json
{
  "mbtiType": "ENFP",
  "source": "self_reported",
  "assessmentVersion": null,
  "resultId": null,
  "confirmedAt": "2026-10-29T07:12:31"
}
```

**使用方法与业务规则**

1. **前置条件**：已登录；`user_profile` 行已存在（注册即创建，缺失返回 404）。
2. **调用顺序**：端侧完成测评或手选 → 用户点"同步到资料" → 调本接口 → 再拉
   `GET /users/me/profile` 或 `GET /users/me/completion` 复核。E1.5 没有 `summary`，
   前端不要依赖它判断是否已同步。
3. **幂等**：同一 `mbtiType` 重复提交不写库、不产生修订记录，返回上次 `confirmedAt`。
   资料未变时不会改动 `user_profile.updated_at`。
4. **副作用**：走 `profile.update_profile`，因此会重算资料完整度（`mbti` 是 18 项之一，
   权重 2 分）并登记一次资料修订；与在资料编辑页改 MBTI 完全等价。
5. **不做什么**：不写 `user_mbti_result`（该表只在 legacy `database_setup_marriage.py` 定义，
   不在 `app/db/business_schema.py`，新环境不存在；E2 落库时再进 schema + 迁移）。
6. **边界**：`mbtiType` 非法 → pydantic 422（`detail` 为数组）；`source` 非枚举 → 422；
   `extra` 字段一律 422（`extra="forbid"`）。

**错误**

| HTTP | 响应 | 触发条件 | 前端处理 |
|---|---|---|---|
| 401 | 现有认证错误响应 | 未登录/token 失效 | 走登录引导 |
| 404 | `{"detail":"资料不存在，请先完成注册"}` | `user_profile` 无行 | 引导完成注册流程 |
| 422 | `{"detail":{"code":"PROFILE_SYNC_CONFIRMATION_REQUIRED",...}}` | `confirmed` 不为 `true` | 补一次确认弹窗后重试 |
| 422 | `{"detail":{"code":"ASSESSMENT_RESULT_REQUIRED",...}}` | `source=assessment` 且缺 `resultId` | 传端侧结果 id；手选场景改 `self_reported` |
| 422 | pydantic 校验数组 | `mbtiType` 非 16 型、`source` 非枚举、含未知字段、`resultId` 超长 | 修正请求体，不要重试同一份 |

**兼容性**：新增接口，无旧调用方。出入参同时接受 camelCase 与 snake_case
（`mbtiType`/`mbti_type`、`resultId`/`result_id`），响应按 camelCase 序列化，与前端
`api/emotionLab.uts` 现有类型定义一致。
