# 积分接口

积分摘要返回当前余额、累计获得和累计扣减；积分流水返回每笔变动后的余额及原因。申请、资料查看等免费或套餐额度使用记录写入 `user_quota_usage`，用于按用户、功能和日期审计次数。

`GET /api/v1/users/me/quotas` 返回申请、资料查看、爆灯和纸飞机的每日额度、已用次数、每日剩余次数、积分兑换剩余次数及总剩余次数。**四类额度的 `daily_limit` 现在全部与实际扣次同源**，统一由 `app/services/quotas.py` 的三个解析函数给出：

| 额度 | 上限解析函数 | 来源优先级（前者覆盖后者） |
| --- | --- | --- |
| `browse` | `resolve_browse_limit` | 平台权限快照 `free_browse_daily_limit`（普通）/ 套餐 `rights.browse_daily_limit`（VIP，缺键回退 20） |
| `apply` | `resolve_apply_limit` | 卡片4 统一值 `apply_daily>0` → 快照 `free_apply_daily_limit` → VIP 再叠加套餐 `rights.apply_bonus` |
| `superlike` | `resolve_superlike_limit` | 快照 `vip_superlike_daily_limit` / `free_superlike_daily_limit` → settings 默认 |
| `paper_plane` | `resolve_paper_plane_limit` | 快照 `paper_plane_daily_limit` → settings 默认 |

`browse` 的 `daily_used` 表示**当天已查看过的不同用户数**，不是请求次数。`GET /api/v1/community/quotas` 的数值也改为复用同一份 `quotas.summary` 结果（字段名不变），因此两个接口不会再出现"一个说 10、一个说 3"。

积分永久有效，不可提现、转账或由前端修改。所有列表稳定分页，返回 `items`、`page`、`page_size`、`total`、`has_more`。

| Method | URL | 说明 |
|---|---|---|
| GET | `/api/v1/users/me/points` | 返回 `balance`、`total_earned`、`total_spent` |
| GET | `/api/v1/users/me/points/ledger?page=1&page_size=20` | 查询积分流水 |
| POST | `/api/v1/users/me/checkin` | 每日签到 5 分，重复签到幂等 |
| GET | `/api/v1/users/me/tasks` | 查询资料完成、实名认证任务 |
| POST | `/api/v1/users/me/tasks/{task_code}/claim` | 领取已完成任务奖励 |
| GET | `/api/v1/users/me/invites?page=1&page_size=20` | 查询本人邀请记录 |
| GET | `/api/v1/points/products` | 查询可兑换商品和权益 |
| POST | `/api/v1/users/me/points/redeem` | 扣除积分并创建兑换订单 |
| GET | `/api/v1/points/recharge-packages` | 查询人民币充值商品（见下文充值小节） |
| POST | `/api/v1/points/recharge/orders` | 创建积分充值订单（微信支付） |
| GET | `/api/v1/points/recharge/orders/{order_no}` | 查询本人充值订单 |

当前任务奖励：资料完整度 100% 奖励 50 分，实名认证状态为 2 奖励 100 分。任务只能领取一次；余额与流水在同一事务中写入，当前实现只做收入类积分，积分兑换接口按设计预留到后续阶段。

签到和任务奖励可通过 `POINT_CHECKIN_REWARD`、`POINT_PROFILE_COMPLETE_REWARD`、`POINT_REALNAME_VERIFIED_REWARD` 配置。积分商品的每次消耗可通过对应的 `POINT_COST_<功能编码>` 配置，例如 `POINT_COST_EXTRA_APPLY`；配置值会覆盖 `config_point_product.points_cost`，商品的库存、上下架和权益内容仍以数据库为准。

兑换请求体为 `{"product_code":"extra_apply","count":1}`，必须带 `Idempotency-Key`（1~128 字符）。`count` 为可选整数，默认 `1`，范围 `1~10`；总价 = 商品单价 × `count`，权益数量、库存扣减和订单 `points_cost` 都按总量计算。商品由 `config_point_product` 配置，商品类型可为 `goods` 或 `right`；服务端校验库存和余额，在同一事务中扣除积分、写入兑换订单并减少库存。兑换订单初始状态为 0（待履约），实物发货或权益发放由后台履约流程处理；同一用户同一幂等键重复请求不会重复扣分，但**同键必须同 `product_code + count`**，不同载荷返回 `409`，不会静默按旧单返回。

请求示例：

```json
{"product_code":"extra_apply","count":3}
```

返回示例：

```json
{"order_no":"PT20261110120000ABCDE","product_code":"extra_apply","product_name":"额外申请次数","points_cost":60,"count":3,"status":1,"balance":940}
```

错误：`count` 为 0/11 → `422`；余额不足/库存不足 → `409`；同键不同载荷 → `409`；商品不存在/下架 → `404`。

`count` 列由 `migrations/business/20261110_01_point_redeem_order_count_*` 增加；全新库由 bootstrap 直接建列，存量库必须执行迁移后再部署本次代码。

**权益类商品的消费方（2026-10-29 对齐）**：`extra_apply`→申请次数（`discovery.create_application`）、`browse_unlock`→资料查看次数（`discovery._consume_browse`）、`superlike`→爆灯次数（`discovery.create_superlike`）、`paper_plane_unlock`→纸飞机次数（`community.create_paper_plane`）。四类都在"日额度用尽后"才扣加次余额，且加次余额记录在 `user_quota_grant`，可通过 `GET /users/me/quotas` 的 `extra_remaining` 查看。

**商品码唯一清单**（种子见 `database_setup_marriage.py` 的 `INSERT IGNORE INTO config_point_product`；运行时以 `GET /api/v1/points/products` 为准）：

| `code` | 名称 | 类型 | 兑换积分 | 兑换后写入的加次 `quota_code` |
|---|---|---|---|---|
| `extra_apply` | 额外申请次数 | `right` | 20 | `apply` |
| `browse_unlock` | 额外资料查看次数 | `right` | 10 | `browse` |
| `paper_plane_unlock` | 纸飞机 | `right` | 30 | `paper_plane` |
| `profile_detail_unlock` | 完整资料卡解锁 | `right` | 50 | —（不走 `user_quota_grant`） |

> **以下商品码不存在，传入将返回商品不可用**：`plane_catch`、`plane_throw`、`profile_view`、`apply`。其中「捡纸飞机」和「扔纸飞机」是**同一个** `paper_plane_unlock`，不可拆成两个商品——权益映射表 `services/points.py` 的 `right_quota` 只有 `extra_apply` / `browse_unlock` / `paper_plane_unlock` 三个 key，`profile_detail_unlock` 不在其中。
>
> 价格以上表为种子默认值，实际受 `POINT_COST_<功能编码>` 环境变量覆盖，且后台可上下架（`is_active`）。

## 人民币积分充值（2026-11-11，方案 33 / Q57-b）

充值与「积分兑换」方向相反：兑换是花积分买权益，充值是花人民币买积分。充值复用统一支付链路（`payment_order`，`type=7`），预支付、支付回调、对账与会员/置顶等订单完全一致，**没有独立的充值支付接口**。完整支付契约见 `docs/api/支付.md`。

### 1. 查询充值商品 `GET /api/v1/points/recharge-packages`

需要登录；无参数；成功状态码 `200`。返回数组（无在架商品时为空数组），每项：

| 字段 | 类型 | 必返 | 业务含义 | 示例值 |
|---|---|---|---|---|
| `id` | integer | 是 | 商品 ID（下单用） | `5` |
| `name` | string | 是 | 商品名称 | `100 积分` |
| `points` | integer | 是 | 到账积分数 | `100` |
| `price` | decimal | 是 | 售价（元），服务端定价，客户端不可传 | `6.00` |

返回示例：

```json
[{"id": 5, "name": "100 积分", "points": 100, "price": 6.00}]
```

商品来自 `admin_recharge_item`（`resource_type='points'` 且 `enabled=1`），按 `sort, id` 排序。**定价是运营数据不是代码**：该目录没有后台写入接口，上架/改价由运营直接维护数据库；调价应**新增商品行**，不要修改已被订单引用的旧行的 `quantity`/`price`（履约按订单记录的商品行取积分数）。

### 2. 创建充值订单 `POST /api/v1/points/recharge/orders`

需要登录；`Idempotency-Key` 必填（8-128 位 ASCII）；成功状态码 `201`。

请求参数：

| 参数名 | 位置 | 类型 | 必填 | 校验规则 | 业务含义 |
|---|---|---|---|---|---|
| `package_id` | body | integer | 是 | `>=1` | 充值商品 ID；数量固定 1，金额由服务端按目录计算 |

请求示例：

```json
{"package_id": 5}
```

返回 `PaidOrderResponse`（与 boost 订单同构）：

```json
{"order_no":"TEST720261111120000A1B2C3D4E5","product_code":"points_recharge","product_name":"100 积分","amount":6.00,"status":0,"expire_at":"2026-11-11T12:30:00Z","payment_required":true}
```

规则：

- 金额与积分数全部由服务端按 `admin_recharge_item` 计算；请求体多传 `price`/`amount` 等字段会被忽略（schema 只接收 `package_id`）。
- 幂等：同一用户同一 `Idempotency-Key` 重复请求回放第一笔订单（与 boost 语义一致）；换商品必须换新 key。
- 订单初始 `status=0` 待支付，30 分钟未支付过期（统一订单行为）。

错误：

| HTTP | 场景 | 前端处理 |
|---|---|---|
| 404 | 商品不存在或已下架 | 刷新商品列表 |
| 409 | 商品配置异常（`price<=0` 或 `quantity<=0`） | 提示联系客服，勿重试 |
| 422 | 缺/短 `Idempotency-Key`、`package_id<1` | 修正参数 |

### 3. 支付与到账

1. 前端拿 `order_no` 调既有 `POST /api/v1/payments/orders/{order_no}/prepay` 获取 JSAPI 参数，`wx.requestPayment` 拉起支付；
2. 微信回调 `POST /api/v1/payments/wechat/notify` 验签后把订单置 `status=1` 并投递 `FULFILL` 任务；
3. Worker 执行 `type=7` 履约：锁用户行 → 以 `biz_key=POINTS:{order_no}` 幂等写入 `user_points`（`type=5` 支付购买、`source_type=points_recharge`、`amount=商品积分数`、`balance=变动后余额`、`desc=积分充值:{order_no}`）；
4. 前端轮询 `GET /api/v1/users/me/points` 确认余额到账，**不要只凭 `requestPayment` 的 success 提示成功**；也可轮询 `GET /api/v1/points/recharge/orders/{order_no}` 看订单 `status`（仅本人订单可见，他人订单号返回 404）。

边界与对账：

- 履约幂等由 `user_points.biz_key` 唯一键保证，重复投递不重复加分。
- 商品在支付后被下架：已支付订单仍按原商品行履约（履约读目录不带 `enabled` 过滤）；商品行缺失或配置异常 → 履约失败进入重试/告警，不会静默丢单。
- 对账 Worker 按账单 `order_no` 对账，与订单类型无关，`type=7` 自动纳入。

### 4. 退款（D4：不支持系统退款）

积分充值订单在**两个后台退款入口都被拒绝**（`type=7` → `409`，提示走人工工单）：已消耗积分无法自动追回，统一人工处理。履约侧保留 `REVOKE` 冲正能力（`biz_key=REFUND:{order_no}`，负数流水，扣减不超过当前余额、不产生负余额），仅供人工/协议路径使用；**不存在用户自助退款接口**。

### 5. 后台积分明细归类

`source_type=points_recharge` 归入后台「财务管理 → 积分明细」的 `category=recharge`（与 `admin_grant` 同类）。

### 6. 测试环境联调注意

旧离线测试支付 `POST /api/v1/payments/test/pay` 只支持 `type=1/2/3/4`，`type=7` 返回 `422`。测试服联调充值必须走回调/Worker 路径，不能用 test/pay 免费履约。
