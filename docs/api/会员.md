# 会员与测试支付接口

## 业务规则

- 各在售套餐共享 VIP 标识等基础权益；套餐有效天数和每日基础额度分别由服务端返回。无免费试用，必须购买后生效。
- 每日申请认识：运营统一值 `apply_daily > 0` 时覆盖普通用户和所有 VIP 套餐；否则普通用户使用实时 `free_apply_daily_limit`（缺项取服务配置默认），VIP 在该基础上叠加当前套餐的 `apply_bonus`（缺项为 0）。历史 `vip_apply_daily_limit` 不参与计算。
- 每日常规资料浏览：会员使用套餐 `browse_daily_limit`（缺项使用扣次默认）；非会员使用实时 `free_browse_daily_limit`（缺项取服务配置默认）。同一天重复查看同一用户不重复扣次。爆灯使用实时 VIP/普通上限配置（缺项取各自服务配置默认）。
- 购买接口只创建待支付订单；会员必须在服务端完成支付履约后开通。
- development/testing 使用本地测试支付接口，不调用微信；生产环境禁止使用测试支付。
- `GET /api/v1/users/me/quotas` 可查询当前用户各项功能的每日额度和额外兑换额度。

会员只有 VIP 一种等级，套餐由 `config_membership_package` 的上架数据决定。支付方式固定微信支付，服务端决定价格、有效天数和权益。

## 接口

| Method | URL | 权限 | 说明 |
|---|---|---|---|
| GET | `/api/v1/membership/packages` | 无 | 查询在售套餐 |
| GET | `/api/v1/users/me/membership` | 登录 | 当前有效期和权益 |
| GET | `/api/v1/users/me/membership/history?page=1&page_size=20` | 登录 | 会员历史分页 |
| POST | `/api/v1/membership/orders` | 登录 | 创建待支付测试订单 |
| GET | `/api/v1/membership/orders/{order_no}` | 订单本人 | 查询订单 |
| POST | `/api/v1/payments/test/pay` | 登录（仅 development/testing 且 `WECHAT_PAY_MODE != real`） | 模拟支付成功/失败并触发订单履约 |
| POST | `/api/v1/payments/wechat/callback` | 微信服务端 | 支付回调边界 |

会员购买接口会创建待支付订单。测试环境调用 `POST /api/v1/payments/test/pay`，请求 `{"order_no":"...","success":true}` 即可完成测试支付并开通会员；重复调用幂等。该接口不能在 staging/production 使用；`WECHAT_PAY_MODE=real` 时同样返回 403，避免真实支付环境下被用于免费履约。

会员不能绕过手机号、资料完整、实名认证、隐私、拉黑和封禁规则。

套餐价格支持环境变量覆盖数据库套餐配置：`MEMBERSHIP_MONTHLY_PRICE`、`MEMBERSHIP_QUARTERLY_PRICE`、`MEMBERSHIP_YEARLY_PRICE`，以及对应的 `_ORIGINAL_PRICE` 和 `_DAILY_PRICE`。未配置时使用 `config_membership_package` 中的值。

微信回调在商户 API v3 密钥和验签适配器配置前返回 `503`，不会把前端请求或未验签回调标记为支付成功，也不会发放会员。

### 查询在售套餐与当前会员状态（任务 17）

| 用途 | Method / URL | 登录与权限 | 成功响应 |
|---|---|---|---|
| 查询在售套餐及生效后的额度预览 | `GET /api/v1/membership/packages` | 无需登录，无角色限制 | `200 application/json`，套餐数组；无在售套餐时 `[]` |
| 查询本人有效会员周期及当前额度 | `GET /api/v1/users/me/membership` | 登录；仅本人，无额外角色、实名或绑手机号要求 | `200 application/json`，会员状态对象 |

两者均无路径参数、查询参数或请求体，`Content-Type` 不必发送。

| 参数 | 位置 | 类型 | 必填 / 默认值 | 规则与含义 | 合法 / 非法示例 |
|---|---|---|---|---|---|
| `Authorization` | header | string | 仅会员状态必填；无默认值 | Bearer 格式，须为有效且未撤销的访问令牌 | `Bearer <access-token>` / `Bearer invalid-token` |

```http
GET /api/v1/membership/packages HTTP/1.1
Host: 127.0.0.1:8000
Accept: application/json

GET /api/v1/users/me/membership HTTP/1.1
Host: 127.0.0.1:8000
Accept: application/json
Authorization: Bearer <access-token>
```

非法示例：会员状态请求使用 `Authorization: Bearer invalid-token`，返回 `401`。套餐接口没有业务参数，不存在参数值校验错误；用 `POST /api/v1/membership/packages` 调用将返回 `405`。

| 返回字段 | 接口 | 类型 | 必返 | 含义、空值或枚举 | 示例 |
|---|---|---|---|---|---|
| `code` | 套餐 | string | 是 | 配置中的套餐编码，用于建单 | `monthly` |
| `name` | 套餐 | string | 是 | 套餐名称 | `新人专享` |
| `duration_days` | 套餐 | integer | 是 | 所选套餐生效后的有效天数 | `90` |
| `price` | 套餐 | number | 是 | 当前售价（元），含服务端价格覆盖 | `299.0` |
| `original_price` | 套餐 | number/null | 是 | 原价（元）；`null` 表示无配置 | `null` |
| `daily_price` | 套餐 | number/null | 是 | 配置的折算日价（元）；`null` 表示无配置 | `3.32` |
| `badge` | 套餐 | string/null | 是 | 传统运营角标；`null` 表示无角标，不作为额度来源 | `null` |
| `is_vip` | 状态 | boolean | 是 | `true` 有当前有效周期；`false` 无当前有效周期 | `true` |
| `package_type` | 状态 | string/null | 是 | 当前生效周期的套餐编码；非会员为 `null` | `monthly` |
| `start_at` | 状态 | string/null | 是 | 当前生效周期开始（含）；无周期或未设开始时间为 `null`。ISO 8601，无时区后缀时为 UTC | `2026-11-20T04:00:00` |
| `end_at` | 状态 | string/null | 是 | 当前生效周期结束（不含），不包含未来才开始的续费周期；无周期或未设结束时间为 `null`。ISO 8601，无时区后缀时为 UTC | `2027-02-18T04:00:00` |
| `rights` | 两者 | object | 是 | 兼容旧版的权益键值；配置可带扩展键（整数、布尔、字符串或 `null`），不用于展示实际额度 | 见下方 JSON |
| `rights.apply_daily_limit` | 两者 | integer | 旧键 | 旧展示值，不代表实际申请上限 | `3` |
| `rights.apply_bonus` | 两者 | integer | 旧键 | 套餐申请加次；有正数运营覆盖时不叠加 | `3` |
| `rights.browse_daily_limit` | 两者 | integer | 旧键 | 旧展示值或套餐配置；不代表当前实际浏览上限 | `20` |
| `rights.superlike_daily_limit` | 两者 | integer | 旧键 | 旧展示值，不代表实际爆灯上限 | `3` |
| `rights.visitor_detail` | 两者 | boolean | 旧键 | 旧的详细访客权益标记 | `true` |
| `rights.browse_history_scope` | 两者 | string | 旧键 | 旧的历史范围标记：`today` 当日，`all` 全部 | `all` |
| **`daily_limits`（新增）** | 两者 | object | 是 | 套餐为生效后的预览；状态为当前账号实际基础上限（含非会员） | 见下方 JSON |
| `daily_limits.apply` | 两者 | integer | 是 | 每日申请认识上限，含适用的套餐加次 | `6` |
| `daily_limits.browse` | 两者 | integer | 是 | 每日基础额度可查看的不同用户数，不含高匹配额外池 | `20` |
| `daily_limits.superlike` | 两者 | integer | 是 | 每日爆灯上限 | `3` |

套餐响应示例（价格、天数、额度仅为示例）：

```json
[
  {
    "code": "monthly", "name": "新人专享", "duration_days": 90,
    "price": 299.0, "original_price": null, "daily_price": 3.32, "badge": null,
    "rights": {"apply_daily_limit": 3, "apply_bonus": 3, "browse_daily_limit": 20,
               "superlike_daily_limit": 1, "visitor_detail": false, "browse_history_scope": "today"},
    "daily_limits": {"apply": 6, "browse": 20, "superlike": 3}
  }
]
```

当前有效会员状态示例：

```json
{
  "is_vip": true, "package_type": "monthly",
  "start_at": "2026-11-20T04:00:00", "end_at": "2027-02-18T04:00:00",
  "rights": {"apply_daily_limit": 6, "apply_bonus": 3, "browse_daily_limit": 20,
             "superlike_daily_limit": 3, "visitor_detail": true, "browse_history_scope": "all"},
  "daily_limits": {"apply": 6, "browse": 20, "superlike": 3}
}
```

无当前有效会员周期时仍返回 `200`：`is_vip=false`，`package_type`、`start_at`、`end_at` 均为 `null`，`daily_limits` 返回普通用户的当前上限。

**使用方法与业务规则**：先读套餐并选择，再使用原建单、支付及履约流程；支付后读取本人状态确认当前生效周期。两项 GET 可重复、并发调用，不建单、不扣减、不退还额度，不需要幂等键，无接口专用次数限制。运营或会员状态变化后应重新读取；套餐预览不是支付承诺，也不代表续费立即生效。`daily_limits` 是**上限，不是剩余量**，不包含积分兑换或按目标触发的额外池；剩余量见 `GET /api/v1/users/me/quotas`。有效期开始前、到期后或会员已撤销时不授权该周期。权限及扣次流程不变。

| HTTP | 业务码 | 触发条件 | 前端处理 |
|---|---|---|---|
| `401` | 无 | 状态请求未登录、令牌无效或会话过期 | 重新登录后再查 |
| `403` | 无 | 状态请求的账号不可用 | 展示服务端提示，不重试支付 |
| `405` | 无 | 使用不支持的 HTTP 方法 | 改为 GET |
| `500` | 无 | 服务异常 | 不展示未取得的额度，稍后重试 |

```json
{"detail":"无效或已过期的访问令牌","message":"无效或已过期的访问令牌"}
```

**兼容性**：两项响应仅新增 `daily_limits`，旧字段和会员历史响应不变；旧客户端可忽略新字段，不废弃旧键。新客户端收到旧服务端的响应时，缺少对象或某个额度子字段就隐藏对应数值，不从 `rights`、角标或套餐名称推算；数值 `0` 表示额度为零，不是缺失。

## 微信支付回调验签（D-21，2026-10-12 批次 B）

`POST /api/v1/payments/wechat/callback` 在业务履约前强制验签：

| 步骤 | 口径 | 失败结果 |
|---|---|---|
| 密钥 | `real` 模式取 `WECHAT_PAYMENT_SIGN_KEY`；`mock` 模式取 `WECHAT_PAYMENT_MOCK_SECRET` | `real` 缺 key → **503**（不进业务逻辑） |
| 验签 | `HMAC-SHA256(secret, f"{order_no}|{transaction_id}|{amount:.2f}")`，`secrets.compare_digest` 比对 | 不符 → **401**，**不触碰数据库** |
| 金额一致性 | `real` 模式回调 `amount` 必须与订单金额一致 | 缺失/不一致 → **409** |
| 订单状态 | 已履约 → 幂等直接返回既有结果；不可履约状态 → **409** | — |

- 幂等不依赖 `Idempotency-Key`（第三方回调不带该头），靠「订单号 + 已履约状态」判定；回调路径不做后台数据范围收口（属系统间调用）。
- 所有 404 / 409 异常落 `business_audit_log`，`action = 'payment.callback.rejected'`（点号分隔），便于对账排障。
- 回归测试：`tests/test_payment_callback_verification.py`（12 条）。

### 变更记录

- 任务 17：此前套餐及状态接口只返回旧 `rights`；现在两者新增与扣次同源的 `daily_limits`。仅影响需要读取额度的新客户端；原字段、权限、价格和支付履约保持不变。
- 2026-08-19：修复会员订单创建时 `product_type` 与 `product_name` 字段错位问题。新订单将套餐编码（如 `yearly`）写入 `product_type`；测试支付履约兼容修复前已创建的旧订单，并可按套餐名称反查并修复编码。
- 2026-08-19：会员订单使用同一 `Idempotency-Key` 重复请求时，只有套餐编码相同才返回原订单；套餐编码不同时返回 `409`，前端必须生成新的幂等键，避免换套餐却继续复用旧订单。
