# 红娘牵线 · 超时自动失败 + 牵线记录列表扩展接口

> 2026-10-28 新增。落地对标站「红娘牵线」页四件事中的后端可交付项：
> ① 配置域 `tools_match_timeout`（齿轮抽屉的超时开关与时长）；
> ② 每日 0 点定时扫描，把超时未完成的待处理牵线自动置「牵线失败」；
> ③ 牵线记录列表补派生展示字段（性别/年龄/实名/单身承诺/归属红娘昵称）；
> ④ 新增删除单条牵线记录端点（操作列「删除」按钮）。
>
> **本期不伪造无数据源的字段**：`payment_status`、统计 `unpaid`、`operator_name`
> 后端均无对应数据（`match_apply` 无支付/操作人列，统计口径里也没有 unpaid），
> 按产品确认「本期放弃、前端不显示」，不写死假值。

## 1. 配置域 `tools_match_timeout`（走通用配置接口）

无独立端点，复用既有 `GET/PATCH /admin/configs/{namespace}`（乐观锁 `version`）。
本域已在 `app/services/admin_config.py:DEFAULT_CONFIGS` 预注册，`ensure_defaults` 幂等落库，
首次即可 GET 读回、PATCH 保存（不再是「配置域不存在」404）。

**字段（default_config）**

| 字段 | 类型 | 默认 | 含义 |
| --- | --- | --- | --- |
| `enabled` | bool | `false` | 超时自动失败总开关；关闭时定时任务空跑，不动任何行 |
| `hours` | int | `48` | 自发起时间起多少小时后判牵线失败；须 > 0，非正值本轮跳过 |

**读写示例**

```http
GET   /api/v1/admin/configs/tools_match_timeout
PATCH /api/v1/admin/configs/tools_match_timeout
content-type: application/json

{ "version": <读回的当前 version>,
  "config": { "enabled": true, "hours": 1 } }
```

PATCH 遵循通用配置域的乐观锁语义：`version` 不匹配返回 409；成功后 `version` 自增。
无敏感键（`sensitive_keys` 为空）。

## 2. 定时任务：超时自动置「牵线失败」

后端**无内置调度框架**（全项目无 celery/apscheduler/cron，进程内无常驻循环），
定时任务落地为「扫描服务 + 可运行入口脚本 + 外部 crontab」三段：

- 扫描服务：`app/services/match_timeout.py::sweep_match_timeouts(db)`
- 运行入口：`scripts/run_match_timeout_sweep.py`
- 建议 crontab（每日 0 点，与后端同环境、同库）：

```cron
0 0 * * * cd /path/to/xuanshiai-backend && python scripts/run_match_timeout_sweep.py
```

**执行逻辑（对齐真实数据模型）**

1. 读 `tools_match_timeout.enabled`；为假直接返回 `affected=0`，不查库。
2. 读 `hours`（非法/缺失回落 `48`；`<=0` 视为无效配置跳过，避免瞬间清空所有待处理行）。
3. 命中集合：`match_apply` 中 `status = 0`（待处理；「待牵线 / 牵线中」都是 0，仅按是否已归属红娘区分展示）
   且 `created_at < DATE_SUB(UTC_TIMESTAMP(), INTERVAL :hours HOUR)`。
   `created_at` 由 MySQL 以 UTC 写入，截止线用 SQL 侧 `UTC_TIMESTAMP()` 保持同一时钟。
4. 逐条置失败：`UPDATE match_apply SET status = 2, responded_at = COALESCE(responded_at, UTC_TIMESTAMP()), updated_at = UTC_TIMESTAMP() WHERE id IN (...) AND status = 0`
   （`status = 2` 即「拒绝/牵线失败」，与 admin PATCH、C 端拒绝同值；带 `status = 0` 前置，重复运行幂等）。
5. 每条命中写一行 `business_audit_log`：`action='match_record.timeout_fail'`、
   `resource_type='match_apply'`、`actor_user_id=NULL`（系统自动任务）、
   `reason='超出时间未完成牵线，次数已退回'`（产品口径文案）。

**关于「次数退回」的如实说明**

产品文案要求「退回 1 次牵线服务次数」。核验结论：后端**不存在可退的持久牵线次数余额**——
发起牵线走每日 Redis 额度（`free_apply_daily_limit`），C 端拒绝（`status=2`）与后台手动标记失败
都**不做任何余额入账**。为避免凭空制造免费额度，定时任务**只置失败 + 写审计，不做余额入账**；
审计 `reason` 沿用产品文案，但实际不含积分/次数回补。若后续引入持久次数钱包，再在此处接入退回逻辑。

**返回结构**（脚本 stdout / 服务返回值）

```json
{ "enabled": true, "hours": 1, "affected": 2 }
```

## 3. 牵线记录列表新增派生字段（既有接口扩展）

**`GET /admin/matchmaker/match-records`**（`response_model=MatchRecordPage`，每项 `MatchRecordItem`）
在原有 `id / from_user_id / to_user_id / status / created_at / responded_at / from_nickname / to_nickname / matchmaker_id`
基础上新增（均为真值派生，不新建表；旧库缺关联时 `LEFT JOIN` 自然降级为 `null`，不拖垮整页）：

| 字段 | 类型 | 来源 |
| --- | --- | --- |
| `from_gender` / `to_gender` | int\|null | `users.gender`（1 男 2 女，null 未知） |
| `from_age` / `to_age` | int\|null | `TIMESTAMPDIFF(YEAR, users.birthday, UTC_DATE())`，birthday 空则 null |
| `from_is_verified` / `to_is_verified` | bool | `user_auth.realname_status = 2`（通过实名） |
| `from_has_promise` / `to_has_promise` | bool | `users.is_single_pledge = 1`（单身承诺书） |
| `matchmaker_name` | str\|null | 归属服务红娘 `users.nickname`（`ra.matchmaker_id → users.id`） |

实现口径：列表查询用 `_MATCH_RECORD_LIST_FROM`（在共用 base 上补 3 个 1:1 `LEFT JOIN`：
双方 `user_auth`、归属红娘 `users`）；`COUNT` 与统计 `GET /match-records/statistics` 仍走
不带这些 JOIN 的 `_MATCH_RECORD_BASE`，保持口径与性能。统计卡**未新增 unpaid**（无支付数据源）。

## 4. 删除单条牵线记录（新增端点）

**`DELETE /admin/matchmaker/match-records/{record_id}?confirm=true`**（带 `Idempotency-Key` 头，`response_model=MemberDeleteResult`）

- 语义：物理删除该 `match_apply` 行（表无 `deleted_at`，非软删）。仅删牵线行，
  **不动 `user_match` 关注关系**，与 PATCH 标记失败/关闭互不干涉。
- 鉴权：`CurrentMatchmakerAdmin` + `current.require("matchmaker.member.manage")`；受数据范围收口
  （相关键 `scope_assignment.user_id = a.from_user_id`，与列表/更新同口径）。
- 敏感写范式（与会员删除一致）：需 `Idempotency-Key` 头 + `confirm=true` 查询参（`require_sensitive_operation`，
  缺 confirm 返回 428），走 `begin/finish/abort` 幂等编排；重放命中直接返回上次结果，不重复删除。
- 记录不存在或越权：404「牵线记录不存在或无权限」。
- 审计：`business_audit_log`，`action='match_record.delete'`、`resource_type='match_apply'`、`reason` 取 `reason` 查询参（默认「后台删除」）。

**查询参数**

| 参数 | 位置 | 类型 | 必填 | 默认 | 含义 |
| --- | --- | --- | --- | --- | --- |
| `record_id` | path | int(≥1) | 是 | — | 牵线记录 id |
| `reason` | query | str(1–255) | 否 | `后台删除` | 删除理由（记入审计） |
| `confirm` | query | bool | 是 | `false` | 敏感操作二次确认，须显式 `true`，否则 428 |
| `Idempotency-Key` | header | str(8–128) | 是 | — | 幂等键（同键同载荷只执行一次） |

**响应**

```json
{ "deleted": [123], "failed": [] }
```

## 验收清单

- [ ] `PATCH /admin/configs/tools_match_timeout {config:{enabled:true,hours:1}, version:V}` → 200，`GET` 读回 `enabled/hours` 一致、`version` 自增。
- [ ] 造一条 `status=0`、`created_at` 早于 `NOW()-1h` 的 `match_apply`，运行 `python scripts/run_match_timeout_sweep.py` → 该行 `status=2`、`responded_at` 回填、新增一行 `match_record.timeout_fail` 审计；脚本输出 `affected>=1`。重复运行不再二次改动（幂等）。
