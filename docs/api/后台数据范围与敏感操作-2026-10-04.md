## 一、四档数据范围（D-4）

### 1.1 语义

管理员账号 `matchmaker_admin_account.data_scope` 共四档：

| 档位 | 语义 | 典型账号 |
| --- | --- | --- |
| `ALL` | 全平台 | 平台运营、财务 |
| `ORGANIZATION` | **本组织 + 其下属门店** | 区域组织负责人 |
| `STORE` | 仅本门店 | 门店店长 |
| `SELF` | 仅本人名下资源 | 一线红娘 |

账号同时持有 `*` 权限时按 `ALL` 处理（`scope_clause` 首行判定）。

**fail-closed 规则（强制）**：任何档位在**缺少必要绑定**时一律返回 0 条，绝不退化为 `1 = 1`：

- `SELF` 且 `matchmaker_user_id` 为空 → `1 = 0`
- `STORE` / `ORGANIZATION` 且 `organization_id` 为空 → `1 = 0`
- `STORE` 档但所属组织 `org_type <> 'store'`（配置错误）→ 0 条
- 对「组织自有资源」（门店、组织、门店账户）使用 `SELF` 档 → `1 = 0`

越权读取统一返回 **404「不存在」**（而非 403），避免用状态码差异枚举他组织资源 ID。写操作在越权时**不落任何变更**：先在作用域内校验、后写，或写入后校验失败即回滚。

### 1.2 唯一实现位置

四档判定**只在 `app/api/dependencies.py` 的 `CurrentMatchmakerAdmin` 上实现**，业务层与路由层不得自行分支 `data_scope`（由 `tests/test_admin_data_scope_d4.py::test_d4_scope_logic_lives_only_in_dependencies` 静态兜底）。

| 方法 | 适用场景 | 产出 |
| --- | --- | --- |
| `scope_clause(params, *, user_column, organization_column, store_organization_column=None, user_param=...)` | 被保护表**自带**归属列（`matchmaker_id` / `organization_id` 等） | `1 = 1` / 等值 / `IN (子查询)` |
| `scope_exists_clause(params, *, correlation, assignment_alias=..., user_column=..., organization_column=...)` | 被保护表**不带**归属列，归属只在 `resource_assignment` | `1 = 1` / `EXISTS (...)` |
| `scope_organization_clause(params, *, column)` | **组织自有资源**（无个人所有者） | `1 = 1` / `1 = 0` / `column IN (组织子树)` |

三者的绑定参数全部通过 `params` 传入，不接受调用方拼接字面量。绑定变量名固定为
`scope_matchmaker_user_id` / `scope_store_id` / `scope_organization_id`。

### 1.3 各模块归属锚点（6 组）

| 组 | 模块 / 端点 | 归属锚点 | 方法 |
| --- | --- | --- | --- |
| 1 | `GET /admin/matchmaker/members`（CRM 会员列表）、`/members/statistics`、`/members/{id}`、`/members/auth`、`/match-records` | 会员的生效归属（`resource_assignment.user_id = u.id`）；牵线记录按**发起方**会员归属 | `scope_exists_clause` |
| 2 | `PATCH /members/{id}/status`、`/members/{id}/assignment`、`POST /members/batch-status` | 同上（写操作先校验可见性，越权 404 且不落库） | `scope_exists_clause` |
| 3 | `POST /admin/matchmaker/members`（建档）、`PATCH /members/{id}`、`/members/{id}/certifications*`、`/members/{id}/audit-logs` | 同上；**建档同时写入 `resource_assignment` 落归属**（组织 + 红娘取自当前账号），否则门店/组织账号建出的会员谁都看不到 | `scope_exists_clause` |
| 4 | `/admin/matchmaker/meetings`（约见申请列表/审核、约会记录列表/详情/编辑/删除/反馈/统计/安排约会/添加约会） | 约见申请 `r.matchmaker_id` + `r.organization_id`；约会记录 `mr.organizer_id` + `mr.organization_id` | `scope_clause` |
| 5 | `/admin/finance/*`（汇总、日报、订单、提现、资金流水、分成明细、分店分成、导出、结算/退款/释放、提现审核） | ①订单/日报/分成/导出 → **消费会员的生效归属**（`resource_assignment.user_id = po.user_id`，与既有分店分成口径一致）<br>②提现/账本/分成 → **按账户类型分别锚定**：`account_type='user'` 走会员归属，`account_type='store'` 走组织维度 | `scope_exists_clause` + `scope_organization_clause` |
| 6 | `/admin/matchmaker/stores*`、`/store-members/*`、`/assignments/{id}/end` | 门店与门店成员 → 组织维度（`o.id` / `om.organization_id`）；资源分配 → `ra.matchmaker_id` + `ra.organization_id` | `scope_organization_clause` / `scope_clause` |
| — | `/admin/matchmaker/messages`（D-6） | 消息涉及收发双方 → `EXISTS (... scope_assignment.user_id IN (from_user_id, to_user_id))` | `scope_exists_clause` |

### 1.4 附带修复

- **会员列表重复行**：`LEFT JOIN resource_assignment` 原为非聚合子查询，一人多单会在分页中产生重复行并虚增 `total`。统一改为按 `user_id` 聚合的派生表，作用域判定改走 `EXISTS`（「任一生效归属在范围内即可见」语义）。
- **会员统计 VIP 口径**：VIP 子查询原统计**全平台** VIP，会向门店/组织账号泄露全局规模，已同口径收口。
- **约见申请结束后误报 404**：`end_assignment` 原实现「取分页首条再比对 id」，结束后基本必抛 404；改为按 id 回读。

### 1.5 未覆盖项与已知限制

以下项**本轮未纳入**，已登记为后续批次（不影响已改造路由的 fail-closed 行为）：

| 项 | 说明 |
| --- | --- |
| 约见下拉字典 `GET /admin/matchmaker/meetings/options` | 返回约见状态枚举等纯字典，不含业务数据，未叠加作用域 |
| 财务下拉字典 | `admin_list_commission_options` / `admin_store_commission_options` **已**按作用域收口（含门店列表） |
| 积分发放 `POST /admin/finance/credit-grants` | 发放目标（`all` / `verified` / `matchmaker_team`）当前为全局口径，未按作用域裁剪目标集合，归入批次 3（MM-A-02 延伸） |
| C 端资金入口 | `POST /finance/orders`、`GET /finance/balance` 等走 `CurrentUser`，不叠加后台数据范围（本就按登录用户自身收口） |
| 建档指定上级组织 | `StoreAdminCreate` 不含 `parent_id`，新建门店只能落在平台根层；因此**仅 `ALL` / `*` 账号可创建门店**，其余账号回滚并 403。如需组织建店，须先补齐「上级组织」字段（批次 3） |
| 门店报表 `_STORE_USER_SCOPE` | `organization_admin.py` 内既有的按显式 `store_id` 收口辅助函数，是「指定门店报表」的领域过滤，不是账号作用域，保留 |

## 二、敏感操作幂等与二次确认（MM-A-03）

### 2.1 请求契约

已接入的端点必须同时满足：

| 要求 | 位置 | 不满足时 |
| --- | --- | --- |
| `Idempotency-Key` 请求头，长度 8–128 | Header | **422** |
| `confirm=true` 查询参数 | Query | **428 Precondition Required**，`detail` 为「敏感操作需要二次确认：请携带 confirm=true」 |

实现见 `app/api/dependencies.py::require_sensitive_operation`。

### 2.2 已接入端点

| 端点 | operation 标识 |
| --- | --- |
| `POST /admin/matchmaker/accounts/{id}/reset-password`（重置后台账号密码） | `matchmaker.admin_account.reset_password` |
| `POST /admin/finance/orders/{order_id}/refund` | `finance.order.refund` |
| `PATCH /admin/finance/withdrawals/{withdrawal_id}` | `finance.withdrawal.review` |
| `POST /admin/matchmaker/assignments/{assignment_id}/end` | `organization.assignment.end` |
| `DELETE /admin/matchmaker/store-members/{member_id}` | `organization.store_member.remove` |

### 2.3 执行语义

单事务内 `reserve_or_replay → 执行 → complete/abort`，落表 `api_idempotency_record`：

1. 首次请求：写入 `(operation, idempotency_key)` 预留记录 → 执行业务 → 写入响应快照并置为 `succeeded`。
2. **重复请求（同 operation + key）**：直接回放已保存的响应体，业务逻辑**不执行**（金额类操作不重复扣款/发放）。
3. 业务异常：`abort`，预留记录置为可重试状态，异常原样抛出。
4. 同一 key 承载不同 `payload` 时按冲突处理。

## 三、敏感字段分级（MS-A-05）

`app/services/message_admin.py` 的 `redact_sensitive(value, level)` 分两级：

| 级别 | 触发条件 | 覆盖 |
| --- | --- | --- |
| `standard` | 默认 | 手机号、身份证、银行卡、微信号、地址类标签 |
| `elevated` | 账号持有 `message.manage` / `message.moderate` / `*` 等提权码 | 在 `standard` 基础上放宽（保留可定位信息），仍不返回完整证件号 |

- 列表与处置响应的 `content` 均按当前账号级别脱敏。
- `business_audit_log.before_json` / `after_json` 快照**同样**按级别脱敏，避免审计留痕反成泄露面。
- `_redact_content` 保留为向后兼容入口，等价于 `standard`。
