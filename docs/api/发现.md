# 首页推荐、搜索与名片互动接口

接口前缀：`/api/v1`。

除 `GET /discovery/filter-options` 外，本文件接口需要登录。推荐、广场、搜索、保存筛选还要求手机号已绑定且资料完整度为 100%。推荐、广场和搜索统一在接口依赖层执行该首页准入校验；账号冻结或注销返回 `403`，不会伪装成未登录。

## 2. 名片对象

推荐、搜索、广场和主页摘要中的 `DiscoveryCard` 字段如下：

| 字段 | 类型 | 空值/枚举 | 含义 |
| --- | --- | --- | --- |
| `user_id` | integer | 必返 | 目标用户 ID |
| `nickname` | string/null | 可空 | 昵称 |
| `avatar` | string/null | 可空 | 头像地址 |
| `age` | integer/null | 可空 | 根据出生日期计算的年龄 |
| `height` | integer/null | 锁定时为空 | 身高厘米 |
| `education_level` | integer/null | 锁定时为空 | 学历等级 |
| `occupation` | string/null | 锁定时为空 | 职业 |
| `is_married` | integer/null | 1 未婚、2 离异、3 丧偶 | 婚姻状态 |
| `online_status` | integer | 0 离线、1 在线、2 隐身 | 在线状态 |
| `mbti` | string/null | 锁定时为空 | MBTI 类型 |
| `weight` | integer/null | 锁定时为空 | 体重（kg），与 `ProfileResponse.weight` 同名字段同口径（不是 `weight_kg`） |
| `hometown_display` | string/null | 锁定时为空 | 家乡展示名（省+市+区去重拼接），由服务端按区划码合成，不下发裸码 |
| `residence_display` | string/null | 锁定时为空 | 居住地展示名，口径同上 |
| `zodiac` | string/null | 锁定时为空 | 属相（`user_profile.zodiac`），前端可继续用生日兜底 |
| `interest_tags` | array[string] | 锁定时为空数组 | 最多展示 5 个兴趣标签 |
| `certification_tags` | array[string] | 可为空数组 | 实名、单身承诺等认证标签 |
| `match_score` | number | 0~100 | 合拍度分值 |
| `match_reason` | string | 必返 | 合拍原因 |
| `is_favorite` | boolean | 必返 | 当前用户是否**收藏**（`user_favorite.type=2`，旧能力，保留兼容） |
| `is_liked` | boolean | 必返 | 当前用户是否**喜欢**该用户（`user_favorite.type=1`），与 `GET /relations/likes` 同源；**不受** `detail_locked`/隐私影响 |
| `is_vip` | boolean | 必返 | 目标用户是否有有效 VIP 会员 |
| `is_pure_free` | boolean | 必返 | 无 VIP 且无有效置顶/爆灯权益 |
| `is_boosted` | boolean | 必返 | 是否有有效置顶记录 |
| `detail_locked` | boolean | 必返 | 详细资料是否因额度/隐私锁定 |

推荐、广场和搜索的候选分页响应结构：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `items` | array[DiscoveryCard] | 当前页名片 |
| `page` | integer | 当前页，从 1 开始 |
| `page_size` | integer | 当前页大小，1~20 |
| `total` | integer | 当前查询候选数，按当前可见性和筛选条件精确计数 |
| `has_more` | boolean | 是否还有下一页 |
| `next_cursor` | string/null | 下一稳定页的服务端签名游标；没有下一页时为 `null` |
| `sort_version` | string/null | 当前稳定排序版本；推荐、广场和搜索当前为 `feed-rank-baseline-v1` |
| `total_is_estimate` | boolean | `false` 表示 `total` 是精确计数；当前候选接口固定返回 `false` |

候选排序固定为 `is_boosted DESC, last_active_at DESC, user_id DESC`。`match_score` 和 `match_reason` 继续使用 `legacy-rule-v1` 生成，只用于名片展示和既有详情额度逻辑，不参与该稳定排序。

可使用 `page` 偏移分页，或在第一页响应后携带 `next_cursor` 请求下一页。cursor 是与查看者、可见性策略、场景、筛选条件和排序版本绑定的服务端签名值；请求携带 cursor 时 `page` 必须为 `1`。伪造、过长、未知排序版本或与当前查询不匹配的 cursor 返回 `400`，错误标识为 `INVALID_CANDIDATE_CURSOR`。

**稳定分页使用方法与兼容性：**

- 这三个读取接口没有请求体。先使用筛选条件和 `page=1` 请求；响应的 `next_cursor` 非空时，使用相同的筛选条件、相同 `page_size` 和 `cursor=<next_cursor>` 请求下一页。不要把 cursor 拼接、解码或自行生成。
- cursor 绑定查看者、可见性策略、接口场景、筛选条件、`page_size` 和排序版本。变更任一筛选条件，或查看者性别、择偶偏好、实名/会员状态发生变化后，应丢弃旧 cursor 并从第一页重新请求。
- 旧客户端继续只读取 `items/page/page_size/total/has_more` 即可；`next_cursor`、`sort_version` 和 `total_is_estimate` 均为向后兼容的新增响应字段。旧 offset 请求仍按同一稳定排序执行，`total` 从“最多 500 条采样”变为精确值，不需要客户端迁移请求参数。

推荐接口首次请求示例（无请求体）：

```http
GET /api/v1/discovery/recommendations?city_code=310100&page=1&page_size=20
Authorization: Bearer <access_token>
Content-Type: application/json
```

下一页请求示例（无请求体）：

```http
GET /api/v1/discovery/recommendations?city_code=310100&page=1&page_size=20&cursor=<next_cursor>
Authorization: Bearer <access_token>
Content-Type: application/json
```

响应示例：

```json
{
  "items": [],
  "page": 1,
  "page_size": 20,
  "total": 1001,
  "has_more": true,
  "next_cursor": "<server-signed-cursor>",
  "sort_version": "feed-rank-baseline-v1",
  "total_is_estimate": false
}
```

错误与前端处理：

| HTTP | 错误标识/响应 | 触发条件 | 前端处理 |
| --- | --- | --- | --- |
| 400 | `{"detail":"INVALID_CANDIDATE_CURSOR"}` | cursor 伪造、过长、排序版本未知或与当前查询不匹配 | 丢弃 cursor，从第一页重新请求；不要重试同一个 cursor |
| 401 | 现有认证错误响应 | 缺少或失效的 Bearer Token | 重新登录后从第一页请求 |
| 403 | 现有首页准入错误响应 | 账号不可用、未绑定手机号或资料完整度不足 | 展示现有准入提示，不保留 cursor |
| 422 | FastAPI 参数校验错误 | `cursor` 与 `page>1` 同时传入，或参数长度/范围非法 | 修正请求参数后从第一页请求 |

## 3. 推荐和广场

### `GET /api/v1/discovery/recommendations`

- 权限：已绑定手机号、资料完整度 100% 且实名认证通过的登录用户
- 成功：`200 OK`
- 排序：有效置顶优先，其次按最后活跃时间和用户 ID 稳定排序；名片仍展示 `legacy-rule-v1` 的合拍度
- 排除：自己、未完善用户、不可见用户、互相拉黑和明确划过的用户。提交认识申请后，申请中、已通过或已匹配的对象仍可继续在首页看到；已浏览但未明确划过的用户也可再次推荐。

查询参数：

| 参数 | 类型 | 必填 | 规则 | 含义 |
| --- | --- | --- | --- | --- |
| `gender` | integer | 否 | `1` 或 `2` | 目标性别 |
| `age_min`/`age_max` | integer | 否 | 18~100，下限不能大于上限 | 临时年龄筛选 |
| `province_code` | string | 否 | 最长 32 字符 | 目标居住省编码 |
| `city_code` | string | 否 | 最长 32 字符 | 目标居住市编码 |
| `district_code` | string | 否 | 最长 32 字符 | 目标居住区编码 |
| `marriage_status` | integer | 否 | `1`、`2`、`3` | 婚姻状态 |
| `education_min` | integer | 否 | 1~8 | 学历下限 |
| `height_min`/`height_max` | integer | 否 | 100~250，下限不能大于上限 | 身高区间 |
| `income_min`/`income_max` | number | 否 | 0~1,000,000，下限不能大于上限 | 收入区间 |
| `pure_free` | boolean | 否 | 默认 `false` | 仅展示无 VIP 且无有效置顶/爆灯权益用户 |
| `cursor` | string | 否 | 1~512 字符；只能使用上一页响应中的 `next_cursor`，并且不能与 `page>1` 同时使用 | 稳定续页游标 |
| `page` | integer | 否 | 1~1000，默认 1 | 页码 |
| `page_size` | integer | 否 | 1~20，默认 20 | 每页数量 |

请求示例：

```text
GET /api/v1/discovery/recommendations?age_min=25&age_max=35&city_code=310100&page=1&page_size=20
```

成功返回分页结构。没有候选时：

```json
{"items":[],"page":1,"page_size":20,"total":0,"has_more":false}
```

### `GET /api/v1/discovery/plaza`

权限、参数和返回结构与推荐接口相同。广场不排除已浏览和已划过用户，但仍过滤未完善、不可见、停用和互相拉黑用户。

## 4. 按昵称或标签搜索

### `GET /api/v1/discovery/search`

- 权限：已绑定手机号、资料完整度 100% 的登录用户
- 成功：`200 OK`

| 参数 | 类型 | 必填 | 规则 | 含义 |
| --- | --- | --- | --- | --- |
| `nickname` | string | 否 | 最长 64 字符；空白会被去除 | 昵称字面模糊匹配，`%` 和 `_` 不作为通配符 |
| `tag` | string | 否 | 最长 64 字符 | 在兴趣、性格和固定分类标签中搜索 |
| `cursor` | string | 否 | 1~512 字符；只能使用上一页响应中的 `next_cursor`，并且不能与 `page>1` 同时使用 | 稳定续页游标 |
| `page` | integer | 否 | 1~1000，默认 1 | 页码 |
| `page_size` | integer | 否 | 1~20，默认 20 | 每页数量 |

`nickname` 与 `tag` 至少提供一个；同时提供时按 AND 条件匹配。搜索结果使用与推荐一致的 `feed-rank-baseline-v1` 稳定排序；名片内的合拍度仍为 `legacy-rule-v1` 展示值。

示例：

```text
GET /api/v1/discovery/search?nickname=小明
GET /api/v1/discovery/search?tag=旅行&page=1&page_size=20
GET /api/v1/discovery/search?nickname=小明&tag=摄影
```

## 5. 保存筛选条件

### `GET /api/v1/discovery/filters/saved`

- 权限：已绑定手机号且资料完整度 100% 的登录用户
- 参数：无

已保存时返回：

```json
{"filters":{"gender":2,"age_min":25,"age_max":35,"page":1,"page_size":20}}
```

未保存时返回：

```json
{"filters":null}
```

### `PUT /api/v1/discovery/filters/saved`

请求体字段与推荐筛选参数相同，保存当前用户唯一一组筛选条件，重复保存覆盖旧条件：

```json
{"gender":2,"age_min":25,"age_max":35,"city_code":"310100","page":1,"page_size":20}
```

## 6. 浏览记录、访客和收藏

### `GET /api/v1/discovery/browse-history`

查询参数：`page` 1~1000，默认 1；`page_size` 1~50，默认 20。返回分页对象，`items[].target` 为名片，`items[].viewed_at` 为浏览时间。

普通用户只能查看当天记录，VIP 可以查看历史记录。访问他人主页时记录浏览；开启 VIP 无痕浏览后不写入对方访客记录。

### `GET /api/v1/discovery/visitors`

查询参数：`page` 1~1000，默认 1；`page_size` 1~50，默认 20。普通用户返回：

```json
{"can_view_details":false,"count":3,"items":[],"page":1,"page_size":20,"has_more":false}
```

VIP 返回 `can_view_details=true`、分页字段和访客名片数组。

### `GET /api/v1/discovery/favorites`（已弃用）

> **DEPRECATED（2026-10-29）**：替代接口 `GET /relations/likes`（`type=1`）。本接口只读 `user_favorite.type=2` 的旧收藏，C 端已无调用方，保留至少一个版本周期后移除。**禁止**用本接口的 `is_favorite` 回填红心。

查询参数：`page` 1~1000，默认 1；`page_size` 1~50，默认 20。返回 `items`、`page`、`page_size`、`total`、`has_more`；没有收藏时 `items` 返回 `[]`。

### `PUT /api/v1/discovery/favorites/{target_id}`（已弃用）

> **DEPRECATED（2026-10-29）**：替代接口 `PUT /users/{target_id}/like`（`type=1`）。本接口写的是 `type=2` 旧收藏，与红心/收藏计数（`type=1`）不同源。

Path `target_id` 为正整数。收藏成功返回：

```json
{"target_user_id":23,"is_favorite":true}
```

### `DELETE /api/v1/discovery/favorites/{target_id}`（已弃用）

> **DEPRECATED（2026-10-29）**：替代接口 `DELETE /users/{target_id}/like`。

取消当前用户自己的收藏，成功返回 `{"target_user_id":23,"is_favorite":false}`。收藏不通知对方，也不产生匹配。

### `GET /api/v1/discovery/favorites/received`（已弃用）

> **DEPRECATED（2026-10-29）**：仅读 `type=2`，C 端无消费方；「喜欢我的人」改用 `GET /relations/liked-by`。

查询“谁收藏我”。需要登录；按 `page`（1~1000，默认 1）和 `page_size`（1~50，默认 20）分页。返回 `items/page/page_size/total/has_more`，每条 `items[]` 包含 `id`、`user`（`user_id/nickname/avatar/age/city_code`）、`relation=received` 和 `created_at`。已注销、隐藏资料、暂停交友及互相拉黑的用户会被过滤；该接口表达收藏关系，不等同于喜欢或认识申请。

## 7. 认识申请

### `POST /api/v1/discovery/applications/{target_id}`

- 权限：已绑定手机号、资料完整度 100% 的登录用户
- Path：`target_id` 正整数
- 成功：`201 Created`

请求体：

| 字段 | 类型 | 必填 | 规则 | 含义 |
| --- | --- | --- | --- | --- |
| `message` | string/null | 否 | 最长 255 字符 | 给对方的留言 |

示例：

```json
{"message":"你好，很高兴认识你"}
```

返回字段：`id` 申请 ID、`from_user_id` 发起方、`to_user_id` 接收方、`message` 留言、`status` 状态、`expire_at` 过期时间、`created_at` 创建时间。

申请状态：`0` 待处理、`1` 同意、`2` 拒绝、`3` 过期。普通用户每天 3 次，VIP 每天 10 次，申请 48 小时后过期；拒绝会退还发起方当日 1 次额度。

### `GET /api/v1/discovery/applications/incoming`

查询参数：`page` 1~1000，默认 1；`page_size` 1~50，默认 20。返回分页对象；无数据时 `items` 返回 `[]`。

对方在申请创建后关闭资料、撤回可见性、进入审核/停用状态或形成任一方向拉黑时，该申请不会再返回对方资料摘要；接口不暴露具体拒绝原因。

### `GET /api/v1/discovery/applications/outgoing`

查询参数：`page` 1~1000，默认 1；`page_size` 1~50，默认 20。返回分页对象；无数据时 `items` 返回 `[]`。

与收件箱相同，当前不可见的对方不会出现在列表中。

### `POST /api/v1/discovery/applications/{application_id}/accept`

仅申请接收方可调用。Path `application_id` 为正整数。成功后更新为 `status=1`，创建双方匹配记录与聊天会话，写入一条 `type=6` 系统问候并通知发起方。

会话规则：

- 会话按 `user1_id=min`、`user2_id=max` 唯一；已存在则复用，并把双方 `is_user1_hidden` / `is_user2_hidden` 复位为 `0`（用户此前「隐藏会话」不会让本次同意失效）。
- 问候文案取平台权限快照 `auto_greeting_template`，未配置时使用默认值「你好呀，我们可以开始聊天啦！」。
- 问候去重键为 `chat_message.client_message_id = accept-greeting:{application_id}`；同一申请重复处理不会插入第二条。
- 问候的 `from_user_id` 仍记为**受理方**（`chat_message.from_user_id` 非空且有外键，不伪造系统账号），`type=6` 由前端渲染为系统气泡；未读数计入申请发起方。

处理前会重新校验发起方当前是否可见；若对方已撤回资料、被限制、审核未通过或形成任一方向拉黑，返回 `404`，不更新申请状态、不创建匹配或聊天会话，也不暴露具体原因。

### `POST /api/v1/discovery/applications/{application_id}/reject`

仅接收方可调用。请求体可省略，也可以传：

```json
{"reason":"暂时不合适"}
```

成功后更新为 `status=2`，拒绝不可撤回，并退还发起方当日额度。

拒绝前同样重新校验发起方当前可见性；不可见时返回 `404` 且不改变申请状态。

## 8. 爆灯

### `POST /api/v1/discovery/superlikes/{target_id}`

- Path：`target_id` 正整数
- 权限：已绑定手机号、资料完整度 100% 且实名认证通过的登录用户
- 成功：`201 Created`

普通用户每日 1 次，VIP 每日 3 次。返回：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `target_user_id` | integer | 目标用户 |
| `remaining_today` | integer/null | 当日剩余次数 |
| `created_at` | datetime | 爆灯时间 |

爆灯会写入有效记录并通知对方；Redis 不可用返回 `503`。

### `GET /api/v1/discovery/superlikes/sent` / `GET /api/v1/discovery/superlikes/received`

查询本人发出或收到的爆灯记录。需要登录，支持 `page`（1~1000，默认 1）和 `page_size`（1~50，默认 20）。返回 `items/page/page_size/total/has_more`；每条记录包含 `id`、`user`（`user_id/nickname/avatar/age/city_code`）、`direction`、`status`、`created_at`、`matched` 和仅本人可见的 `order_no`。用户注销或互相拉黑后的记录不对外展示。

`user_boost` 同时承载「置顶助推」（`order_type=4`，写入 `user_id = target_user_id = 自己`），两个方向都**排除 `user_id = target_user_id` 的自指记录**：自己买的置顶不会出现在「我给谁爆灯」，也不会被算成「收到一次爆灯」。同一口径同步应用于「我的」页 `superlike_sent_count` / `superlike_received_count`、后台爆灯流水与 CRM「爆过灯 / 被爆过灯」筛选。

## 9. 他人主页和海报

### `GET /api/v1/users/{user_id}/profile`

Path `user_id` 为正整数。返回：

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `user_id` | integer | 目标用户 ID |
| `card` | DiscoveryCard | 名片摘要 |
| `profile` | object/null | 额度允许时的公开完整资料 |
| `is_vip_viewer` | boolean | 当前访问者是否 VIP |
| `browse_quota_remaining` | integer/null | 当天剩余可看的**不同用户**数；隐私锁定（仅 VIP 可见详情且访问者非 VIP）时为 `null` |
| `can_apply` | boolean | 当前用户是否满足申请门槛 |

**额度规则（2026-10-22 起按不同用户计次）**：

- 计费单元是当天查看过的不同 `user_id` 个数，普通用户上限读平台权限快照 `free_browse_daily_limit`（当前 8），VIP 上限读套餐 `rights.browse_daily_limit`（当前 20）。
- 同一用户当天第 2 次及以后打开：`200`，不扣次数、不写额度台账、不消耗高匹配奖励池或积分池，`browse_quota_remaining` 保持不变。
- 高合拍度名片（匹配分 > 80）在常规额度用尽后可再使用 `high_match_browse_bonus`（当前 5）个名额；两个额度池都满时才会扣积分兑换的查看次数。
- 全部池子用尽后，只有**新用户**返回 `429 今日完整浏览额度已用完`；当天已看过的用户仍可打开，此时 `browse_quota_remaining=0` 但 `profile` 正常返回。
- 额度按 UTC 自然日重置（`discovery:browse:{user_id}:{UTC 日期}`），跨天后同一用户重新计费。
- Redis 不可用时：`development`/`testing` 退化到进程内额度；其他环境返回 `503`。

`profile` 为完整资料时，精确位置编码和原始收入仍返回 `null`；新增以下脱敏展示字段：`residence_display`（例如 `北京市 朝阳区`）、`hometown_display`（例如 `浙江省 杭州市`）和 `income_display`（例如 `40w`）。字段无可展示值时返回 `null`。

名片、浏览记录、访客和收藏列表会同时应用目标用户的 `show_profile`、交友状态、拉黑关系和 VIP 详情设置；被隐藏的记录不会计入 `total`/`count`。媒体审核状态只影响媒体本身：审核中、拒绝或隐藏的媒体不会出现在公开资料响应中，不会让用户整体不可见。

### `GET /api/v1/users/{user_id}/card-preview`

首页卡片预览：只给「背景墙 + 相册首图 + 公开卡字段」，**不扣资料查看额度、不写浏览记录、不返回 `profile`**。
用途是首页切换推荐卡时补背景/相册，避免首页一次预取就消耗一次资料查看额度、并把用户写进对方「谁看过我」。

**基本信息**

- 权限：登录用户（不要求资料完整度 100%，与 `GET /users/{user_id}/profile` 的准入不同）
- 路径：`/api/v1/users/{user_id}/card-preview`
- Method：`GET`
- 请求体：无
- 成功：`200 OK`
- 响应 Content-Type：`application/json`

**请求参数**

| 参数 | 位置 | 类型 | 必填 | 默认 | 校验 | 含义 |
| --- | --- | --- | --- | --- | --- | --- |
| `user_id` | path | integer | 是 | — | ≥ 1 | 目标用户 ID；等于当前登录用户时返回 `422` |

请求示例：

```http
GET /api/v1/users/23/card-preview
Authorization: Bearer <access_token>
```

非法示例（缺参数）：

```http
GET /api/v1/users//card-preview
→ 404 Not Found
```

**返回参数**

| 字段 | 类型 | 必返 | 空值含义 | 说明 |
| --- | --- | --- | --- | --- |
| `user_id` | integer | 是 | — | 目标用户 ID |
| `card` | DiscoveryCard | 是 | — | 名片摘要，字段见第 2 节（含 `is_liked`、`weight` 等新增字段） |
| `background_wall` | string/null | 是 | 对方未上传或未过审 | 背景墙文件地址（`user_media.media_type='background'` 第一条，仅 `review_status=1`） |
| `photos` | array[string] | 是 | 无可用相册时为 `[]` | 相册**首图**，最多 1 张；刻意不返回整册，避免变成资料浏览入口 |
| `income_display` | string/null | 是 | 收入为空或详情锁定 | 收入展示（如 `1.5w`），与 `GET /users/{user_id}/profile` 的 `income_display` 同口径 |

响应示例：

```json
{
  "user_id": 23,
  "card": {
    "user_id": 23,
    "nickname": "小林",
    "avatar": "/media/avatar/23.webp",
    "age": 27,
    "height": 168,
    "weight": 52,
    "hometown_display": "江西省 吉安市",
    "residence_display": "江西省 南昌市",
    "zodiac": "属兔",
    "mbti": "ENFP",
    "is_liked": true,
    "is_favorite": false,
    "detail_locked": false,
    "match_score": 72.0,
    "match_reason": "同城 · 年龄相近"
  },
  "background_wall": "/media/background/23.webp",
  "photos": ["/media/photo/23-1.webp"],
  "income_display": "1.5w"
}
```

**使用方法与业务规则**

1. 前置条件：已登录；目标用户对当前用户可见（与推荐/详情同一套可见性谓词）。平台维护期返回 `403`。
2. 调用顺序：先取推荐/广场列表拿到 `user_id`，再对本接口逐个预览；**不要**为了背景去调 `GET /users/{user_id}/profile`（那会扣额度并留痕）。
3. 额度：**不消耗** `discovery:browse:*` 计数，不写 `user_quota_usage`，不写 `user_browse_history`。因此本接口**永远不会返回 `429`**。
4. 隐私：不返回 `profile`、手机号、真实姓名、微信等非公开字段；`card.detail_locked=true` 时 `weight/hometown_display/residence_display/zodiac/income_display` 均为 `null`，但 `background_wall`/`photos` 仍返回（首页要能显示背景，这是本接口存在的理由）。
5. 关系字段：`card.is_liked`（`type=1`）不受锁定影响，可据此渲染红心。

**错误**

| HTTP | 响应 | 触发条件 | 前端处理 |
| --- | --- | --- | --- |
| 401 | 现有认证错误响应 | 未登录或 token 失效 | 走登录引导，不要清空本地推荐缓存以外的状态 |
| 403 | 现有维护态错误响应 | 平台维护中 | 展示维护提示 |
| 404 | `{"detail":"用户不存在或当前不可见"}` | 注销、隐藏资料、暂停交友、拉黑、可见性不通过 | 回退到列表里的卡片数据，背景留空 |
| 422 | `{"detail":"不能浏览自己的名片"}` | `user_id` 等于当前登录用户 | 不发起本请求（自己主页不走预览） |

**兼容性**：新增接口，无旧调用方；`GET /users/{user_id}/profile` 语义与额度规则**未变**。

### `GET /api/v1/users/{user_id}/visitor-count`

- 权限：登录用户
- Path：`user_id`，正整数，表示要查询的公开用户
- 请求体：无
- 成功：`200 OK`

请求示例：

```http
GET /api/v1/users/23/visitor-count
Authorization: Bearer <access_token>
```

成功响应：

```json
{"user_id":23,"visitor_count":12}
```

| 字段 | 类型 | 含义 |
| --- | --- | --- |
| `user_id` | integer | 被查询的用户 ID |
| `visitor_count` | integer | `user_browse_history` 中对该用户的去重访问者总数；不返回任何访问者资料或 ID |

接口复用他人主页的账号状态、隐私、仅 VIP 可见和拉黑校验；目标不存在、不可见、被拉黑或查询自己时返回 `404`、`403` 或 `422`。匿名浏览不会写入浏览历史，因此不会计入数量。

### `GET /api/v1/users/{user_id}/poster?template=1`

- Path：`user_id` 正整数
- Query：`template` 1~25，默认 1
- 成功：`200 OK`
- Content-Type：`image/png`
- 请求体：无

服务端调用微信小程序码接口生成个人主页二维码并合成 PNG。未配置 `WECHAT_APP_ID`/`WECHAT_APP_SECRET` 或微信调用失败返回 `503`。

## 10. 错误码

| HTTP | 触发条件 | 前端处理 |
| --- | --- | --- |
| `401` | 未登录或会话失效 | 清理 Token 并回登录页 |
| `403` | 未绑定手机号、资料未完成、无资源权限或被拉黑 | 展示绑定/完善资料/权限提示 |
| `404` | 用户、申请、名片或会话目标不存在/不可见 | 移除列表项或提示不可用 |
| `409` | 重复收藏、申请冲突或状态已处理 | 刷新当前状态 |
| `422` | 参数类型、范围、枚举或区间错误 | 修正请求参数 |
| `429` | 浏览、申请或爆灯次数用完 | 展示额度/会员提示 |
| `503` | Redis 或微信服务不可用 | 稍后重试 |
