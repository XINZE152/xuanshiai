# 客源「本人资料」字段扩展

> 2026-10-28 新增。背景：对标站「新建客源 / 客源详情」表单带一大堆本人资料输入框，
> 但旧版 `CustomerLeadCreate/Update/Response` 只有 6 个业务字段（称呼、手机、微信、来源、意向、备注）
> 加 `gender`，其余输入既不发也不存——填了完整资料打开全空是旧模型的必然结果，非前端 bug。
>
> 本次给 `customer_lead` 补齐资料列，并让建单 / 更新 / 详情三处 schema 同步收发这些字段；
> 客源入库（`convert_lead`）时把资料搬运到账号侧（`users` / `user_profile` / `user_auth`）。
>
> 取值口径对齐账号本人资料：**枚举类一律 varchar 存原值**（档位字典见 `platform_base_data`，
> 不是整数码——整数码 `*_requirement` 只用于「择偶要求」表），身高/体重 int，相册 JSON。

## 通用约定

前缀 `/api/v1`，需 `Authorization: Bearer <access-token>`，与既有客源接口同域同权限
（`customer_lead.manage`），受 D-16 数据范围约束。请求/响应均为 `application/json`。

涉及端点（均既有，仅字段扩展，无新增路由）：

- **`POST /admin/customer-leads`** 录入客源
- **`PUT /admin/customer-leads/{lead_id}`** 更新客源（部分更新）
- **`GET /admin/customer-leads`** / **`GET /admin/customer-leads/{lead_id}`** 列表 / 详情
- **`POST /admin/customer-leads/{lead_id}/convert`** 一键入库（搬运资料到账号）

### 年龄 age（只读派生）

`age` **不在请求里提交**（提交也被忽略），仅出现在响应：

- 有 `birth_date` 时：读取用 `TIMESTAMPDIFF(YEAR, birth_date, UTC_DATE())`；写入时服务层同步刷新 `age` 列（供列表筛选与旧口径消费方）。
- 无 `birth_date` 但历史遗留 `age` 列有值：回退读 raw `age`。
- 两者皆无：`age` 返回 `null`。

响应模型新增只读字段：

| 字段 | 类型 | 含义 |
|---|---|---|
| `age` | int \| null | 由出生日期派生的年龄，只读 |

## 2. 更新（部分更新）语义

`PUT /admin/customer-leads/{lead_id}` 只写请求体中**显式出现**的字段；未出现的保持原值。

- 校验：若所有字段（含新增资料字段）归一化后均为 `null`（例如仅提交空白联系方式），视为「没有任何修改项」→ `422`。
- 掩码回显保护：详情读回的 `wechat` 是脱敏值（`***`），原样提交会被识别为掩码值并**丢弃**，不会污染真实微信号。
- `photos` 传 `[]` 表示清空相册（`[]` 是显式值，不等于未提供）。
- 资料列尚未迁移到库时，服务层从写入字段中静默剔除该列（「先发版后迁移」，不会 `500`）。

## 3. 入库搬运（`convert_lead`）

一键入库生成会员账号时，客源本人资料按下表搬运到新账号；缺列静默跳过。

| 客源字段 | 账号目标 | 备注 |
|---|---|---|
| `gender` | `users.gender` | 既有 |
| `birth_date` | `users.birthday` | 日期直传 |
| `marriage` | `users.is_married` | varchar 档位→编码映射：未婚→1 / 离异→2 / 丧偶→3；无法识别则不写 |
| `height` / `weight` | `user_profile.height` / `.weight` | int |
| `hometown` / `residence` / `ethnicity` | `user_profile` 同名列 | varchar |
| `house` / `car` / `smoking` / `drinking` | `user_profile` 同名列 | varchar |
| `occupation` | `user_profile.occupation`（并写 `user_auth.job`） | |
| `photos` | `user_profile.photos`（JSON） | |
| `real_name` | `user_auth.real_name` | 仅资料姓名 |
| `education` | `user_auth.education` | |
| `school` / `company` | `user_auth.school` / `.company` | |

> **不搬运**：`income`（客源为 varchar 档位，账号 `user_profile.income` 是 decimal 元，口径不兼容，
> 强行写入会破坏数值字段）。入库后会员可在 C 端资料页按档位重填。

## 4. 部署与迁移

- 存量库执行 `migrations/customer_lead_profile/20261028_01_lead_profile_up.sql` 补 12 列
  （幂等：`INFORMATION_SCHEMA` 检查 + 动态 `ALTER`，可重复执行）；回滚 `_down.sql`（会丢数据，先备份）。
- 新装库由 `app/db/business_schema.py` 建表时直接带上（`filters` 的 7 列仍由 filters 迁移补入）。
- 生产 `AUTO_INIT_DB=false`，**必须**跑迁移 SQL，否则新字段读写全部静默降级、不落库。
- 前后端顺序：后端先合并发版（缺列降级、不报错），再跑迁移，最后前端接线收发即可生效。
