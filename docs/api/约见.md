# 一期约见接口

接口前缀为 `/api/v1`，需要登录并绑定手机号。约见反馈只返回写入成功，不提供公开反馈查询接口。

| 方法 | 路径 | 权限 | 用途 |
| --- | --- | --- | --- |
| `POST` | `/matchmaker/meetings/requests` | 已登录用户 | 已废弃，普通用户不能直接发起约见 |
| `POST` | `/matchmaker/meetings/requests/from-service` | 已认证服务红娘 | 基于红娘服务单发起约见 |
| `GET` | `/matchmaker/meetings/requests/mine` | 已登录用户 | 查询自己发出或收到的申请 |
| `PATCH` | `/matchmaker/meetings/requests/{request_id}` | 申请参与方 | 接受、拒绝、联系或关闭申请 |
| `POST` | `/admin/matchmaker/meetings/requests/{request_id}/schedule` | 超级管理员 | 安排具体约会 |
| `POST` | `/matchmaker/meetings/{meeting_id}/feedback` | 约会参与方 | 提交私有反馈 |
| `POST` | `/matchmaker/workbench/meeting-requests/{request_id}/schedule` | 服务红娘工作台 | 工作台为双方接受的申请安排约见 |
| `PATCH` | `/matchmaker/workbench/meetings/{meeting_id}/status` | 服务红娘工作台 | 工作台流转约见安排状态 |

## 工作台约见排期（2026-09 新增）

### `POST /matchmaker/workbench/meeting-requests/{request_id}/schedule`

服务红娘在工作台为**双方接受的约见申请**（`status = ACCEPTED`）创建约见安排；约见申请必须位于当前红娘服务范围内（SELF 为自己跟进，ORGANIZATION 为同组织）。

- **Headers**：`Authorization: Bearer <用户 JWT>`
- **请求体**：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `scheduled_at` | string(datetime) | 是 | 约见时间，必须晚于当前时刻，否则 422 |
| `location` | string(1-128) | 是 | 约见地点，提交前去除首尾空白 |

- **返回**：201 + `WorkspaceMeetingRecordSummary`：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | int | 约见安排记录 ID |
| `status` | string | 固定为 `SCHEDULED` |
| `scheduled_at` | string(datetime) | 约见时间 |
| `location` | string | 约见地点 |
| `cancel_reason` | string\|null | 取消原因，新建为 null |

- **错误码**：404 申请不存在或不在服务范围；409 申请状态不是 `ACCEPTED`、或该申请已有进行中的安排（`SCHEDULED/REMINDED/CHECKED_IN`）；422 约见时间不是未来时间。

请求示例：

```json
{"scheduled_at": "2026-09-12T15:00:00", "location": "宣誓爱门店会客室"}
```

业务规则：同一申请同时只允许一份进行中的约见安排；安排创建后申请状态保持 `ACCEPTED`；操作写入 `business_audit_log`（action `matchmaker_workspace.meeting.schedule`）。

### `PATCH /matchmaker/workbench/meetings/{meeting_id}/status`

流转服务范围内约见安排的状态。

- **Headers**：`Authorization: Bearer <用户 JWT>`
- **请求体**：

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `status` | string | 是 | `REMINDED` / `CHECKED_IN` / `COMPLETED` / `CANCELLED` / `NO_SHOW` |
| `cancel_reason` | string(≤200) | 条件 | `CANCELLED` 或 `NO_SHOW` 必填；其他状态不允许携带 |

- **返回**：204 无返回体。
- **错误码**：404 约见安排不存在或不在服务范围；409 已取消（`CANCELLED`）的约见不能恢复；422 取消/爽约未填原因。

业务规则：取消是不可逆终态；流转写入 `business_audit_log`（action `matchmaker_workspace.meeting.record_status`）。

提交申请：

```json
{"target_user_id":23,"note":"希望在门店进行首次沟通"}
```

申请状态：`SUBMITTED`、`CONTACTED`、`ACCEPTED`、`DECLINED`、`CLOSED`。拒绝或关闭必须填写 `reason`。只有 `ACCEPTED` 才能由管理员安排约会。

红娘基于服务单发起约见时，服务状态必须为 `1=服务中` 或 `2=服务完成`；`3=已取消/退款`、服务过期、红娘停用或账号封禁时禁止发起。约见记录必须保留 `service_id` 和 `matchmaker_id`，以便退款、责任和分成追溯。

约会状态：`SCHEDULED`、`REMINDED`、`CHECKED_IN`、`COMPLETED`、`CANCELLED`、`NO_SHOW`。反馈只有约会进入 `CHECKED_IN` 或 `COMPLETED` 后允许提交。

## 会员详情页接口（2026-09 新增）

以下接口供后台会员详情的“约会记录”Tab 使用，均需要后台登录并具备 `meeting.read`（项目权限依赖会话角色）权限，响应为 JSON 分页对象：`items`、`page`、`page_size`、`total`、`has_more`。无数据时 `items` 返回空数组。

### `GET /admin/members/{member_id}/dating-records`

查询会员作为约见双方任一方的约会记录。请求体为空，支持 `page`（默认 1）、`page_size`（默认 20，最大 100）、`status_group`（`all`/`waiting`/`not_met`/`met`）和 `status`（精确状态）查询参数；同时传 `status` 与 `status_group` 时以 `status` 为准。

状态分组：`waiting = SCHEDULED, REMINDED`（待见面）；`not_met = CANCELLED, NO_SHOW`（未见面）；`met = CHECKED_IN, COMPLETED`（已见面/成功见面）。

`items` 字段：`id` 约会记录 ID，`request_id` 申请 ID，`scheduled_at` 约见时间（未排期可为 null），`location` 地点（可为 null），`status` 状态，`cancel_reason` 取消/爽约原因，`created_at`/`updated_at` 时间，`from_user_id`/`from_nickname` 发起方，`to_user_id`/`to_nickname` 被约见方。

示例：`GET /api/v1/admin/members/12/dating-records?page=1&page_size=20&status_group=waiting`

### `GET /admin/members/{member_id}/meeting-requests`

查询会员作为发起方或目标方的约见申请，对应详情页“约见申请”子 Tab。请求体为空，支持 `page`、`page_size` 和 `status`（`SUBMITTED`/`CONTACTED`/`ACCEPTED`/`DECLINED`/`CLOSED`）。

`items` 字段：`id` 申请 ID，`user_id`/`user_nickname` 发起方，`target_user_id`/`target_nickname` 目标方，`service_id` 服务单，`matchmaker_id` 红娘，`organization_id` 组织，`status` 申请状态，`note` 备注，`created_at`/`updated_at` 时间。

示例：`GET /api/v1/admin/members/12/meeting-requests?status=SUBMITTED`

### 详情页“添加约见”流程

1. 前端调用 `GET /admin/matchmaker/meetings/options` 获取红娘和会员候选项。
2. 直接添加约见调用 `POST /admin/matchmaker/meetings`，传 `from_user_id`、`to_user_id`、`organizer_id`，可选传 `scheduled_at`、`location`、`member_visible`、`sms_remind`、`met`。
3. 申请驱动的约见先由用户/红娘创建申请，后台将申请更新为 `ACCEPTED` 后调用 `POST /admin/matchmaker/meetings/requests/{request_id}/schedule` 排期。
4. 状态流转后重新查询上述两个会员详情接口刷新 Tab；取消和爽约记录原因，已取消约会不可恢复。重复排期、无权限、会员不存在分别返回 409、403、404。

**兼容性**：原 `dating-records` URL 保持不变，仅将响应明确为同一分页 JSON 结构并增加可选筛选参数；不传筛选参数时行为与旧版一致。

## 完整接口清单与调用流程

### 1. 普通用户提交约见申请

#### `POST /api/v1/matchmaker/meetings/requests`

- 权限：登录并完成实名认证/手机号校验的普通用户；不需要 `admin` 前缀。
- Body：`target_user_id: integer`（目标会员 ID，必填）、`note: string`（申请说明，1-2000 字符，必填）。
- 成功：`201 MeetingRequestResponse`，初始 `status=SUBMITTED`。
- 规则：不能申请自己；重复或额度不足时拒绝；申请进入后台审核队列。

#### `GET /api/v1/matchmaker/meetings/requests/mine`

查询当前用户发起或收到的申请，返回 `MeetingRequestResponse[]`。

### 2. Admin 查看和审核约见申请

#### `GET /api/v1/admin/matchmaker/meetings/requests`

- 权限：后台登录，`meeting.read`。
- 分页：`page` 默认 1，`page_size` 默认 20，最大 100。
- 筛选：`status`（`SUBMITTED/CONTACTED/ACCEPTED/DECLINED/CLOSED`）、`status_group`（`pending`=待处理、`done`=已处理）、`search_value`（昵称或会员 ID）、`matchmaker_id`、`from_date`、`to_date`。
- 返回：`MeetingRequestAdminPage`，字段为 `items/page/page_size/total/has_more`；每条申请包含双方 ID/昵称/会员编号、服务单、红娘、组织、状态、备注和时间。

#### `PATCH /api/v1/admin/matchmaker/meetings/requests/{request_id}`

- 权限：后台登录，`meeting.write`。
- Body：`status`（`CONTACTED/ACCEPTED/DECLINED/CLOSED`）和可选 `reason`（最多 255 字符）。
- 成功：返回更新后的 `MeetingRequestResponse`。
- 流程：普通用户提交后为 `SUBMITTED`；管理员可标记联系、通过、拒绝或关闭。`DECLINED/CLOSED` 会退还已扣次数；只有 `ACCEPTED` 可以排期。
- 错误：申请不存在 404；非法状态流转或重复处理 409；拒绝/关闭未填原因 422；无权限 403。

### 3. Admin 查询全部或指定会员约会记录

#### `GET /api/v1/admin/matchmaker/meetings`

- 权限：后台登录，`meeting.read`。
- 不传 `member_id`：查询全部约会记录。
- 传 `member_id={id}`：只查询该会员作为发起方或目标方的约会记录。
- 参数：`page`、`page_size`、`member_id`、`status`（`SCHEDULED/REMINDED/CHECKED_IN/COMPLETED/CANCELLED/NO_SHOW`）、`met`（`wait`/`met`）、`search`、`organizer_id`、`from_date`、`to_date`。
- 返回：`MeetingRecordAdminPage`，每条记录包含约会双方、红娘、时间、地点、状态、取消原因和反馈数量。
- 示例：
  - 全部：`GET /api/v1/admin/matchmaker/meetings?page=1&page_size=20`
  - 指定会员：`GET /api/v1/admin/matchmaker/meetings?member_id=12&page=1&page_size=20`

#### `GET /api/v1/admin/members/{member_id}/dating-records`

会员详情页专用查询，支持 `status_group=all|waiting|not_met|met` 和精确 `status`；返回结构与上面的分页约会记录一致，但额外固定返回该会员双方关系字段。

### 4. 约见申请到约会的流程

1. 普通用户调用 `POST /matchmaker/meetings/requests` 提交申请。
2. Admin 调用 `GET /admin/matchmaker/meetings/requests` 查询待审核申请。
3. Admin 调用 `PATCH /admin/matchmaker/meetings/requests/{request_id}` 审核；通过后状态为 `ACCEPTED`。
4. Admin 调用 `POST /admin/matchmaker/meetings/requests/{request_id}/schedule` 排期，生成约会记录。
5. Admin 使用 `GET /admin/matchmaker/meetings` 查询全部或指定会员记录，并用 `PATCH /admin/matchmaker/meetings/{meeting_id}` 更新见面状态。
6. 约会达到 `CHECKED_IN` 或 `COMPLETED` 后，参与用户可提交反馈。
