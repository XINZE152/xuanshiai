# 牵线管理流程 V2（2026-11-02）

## 变更记录与业务规则

本次用户决策：会员回应和红娘跟进阶段分开。认识申请同意立即成功；拒绝回待牵线并标注「对方拒绝」；未回应（包括申请过期）保持待牵线并标注「未回应」。若红娘已经介入，申请过期不重置其跟进阶段。

| 事件 | 原阶段 | 新阶段 | 说明 |
| --- | --- | --- | --- |
| 创建认识申请/手工牵线 | 无 | PENDING | 待牵线；默认未回应 |
| 对方同意认识申请 | PENDING / IN_PROGRESS / FAILED | SUCCEEDED | 只影响该申请ID对应的牵线，不要求红娘再次处理 |
| 对方拒绝认识申请 | PENDING / IN_PROGRESS | PENDING | 标注对方拒绝；此前电话查看不计入本轮 |
| 申请过期 | 任意 | 不变 | 未回应不等于失败，保留红娘跟进 |
| 当前红娘查看一方有效电话 | PENDING | PENDING | 微信或空电话不算 |
| 同一红娘查看本条双方有效电话 | PENDING | PENDING | 等待确认已获得双方联系方式 |
| 红娘明确确认已获得双方联系方式 | PENDING | IN_PROGRESS | 请求 contacts_obtained=true，服务端校验双方电话已查看 |
| 红娘确认已联系双方，了解被牵线方态度 | IN_PROGRESS | SUCCEEDED / FAILED | 必须确认已联系，失败需原因 |
| 查看已成功/失败记录的电话 | SUCCEEDED / FAILED | 不变 | 不重新开启牵线 |

会员拒绝不能替代红娘的最终失败判断；红娘成功/失败也不会自动创建用户聊天或交换双方联系方式。聊天仍以会员双方同意为准。原 `match_apply`、认识申请额度及聊天会话逻辑保留。

适用范围为小程序工作台。后台独立的历史牵线录入（`admin-entry`）仍保留后台人工历史结果，不把历史人工失败当成会员拒绝自动回退。

## 共同鉴权和错误

以下完整路径均以 `/api/v1` 开头；需登录并通过 `require_workspace`（有效红娘工作台身份）。`Authorization: Bearer <access_token>` 必填，无默认；非法/过期 Token 返回401。请求/响应为 `application/json`，PATCH成功为204无响应体。

普通红娘按本人工作范围、超级红娘按门店/总店范围鉴权。新查看接口按**本条牵线的工作范围**授权，仅可读取记录中 `from` 或 `to` 对应会员，不接受任意用户ID。冻结、注销及不存在会员不返回电话。

| HTTP | 条件 | 处理 |
| --- | --- | --- |
| 401 | 未登录/Token无效 | 重新登录 |
| 403 | 无红娘工作台资格 | 提示无权限 |
| 404 | 记录不在服务范围、不存在或指定会员不可联系 | 不展示号码；刷新列表 |
| 409 | 非法阶段、未确认联系、当前红娘未看双方电话 | 按提示补齐步骤；刷新权威状态 |
| 422 | ID非正整数、枚举非法、失败无原因等 | 修正参数 |

业务错误示例：`{"detail":"请先确认已联系双方，并根据被牵线方态度判断结果"}`。参数错误示例：`{"detail":[{"loc":["body","side"],"msg":"Input should be 'from' or 'to'","type":"literal_error"}]}`（实际校验响应还可能带 `input/ctx`）。

## 查询牵线记录（修改）

`GET /api/v1/matchmaker/workbench/introductions`，200。无请求体。

| 参数 | 位置/JSON类型 | 必填/默认 | 校验、含义、合法/非法示例 |
| --- | --- | --- | --- |
| Authorization | header/string | 是/无 | Bearer登录凭据；非法：空 |
| page | query/integer | 否/1 | 1..1000，页码；合法1，非法0 |
| page_size | query/integer | 否/20 | 1..100，每页记录；合法20，非法101 |
| status | query/string | 否/null | PENDING/IN_PROGRESS/SUCCEEDED/FAILED；非法DONE |
| search | query/string | 否/null | 最长64字，姓名/记录编号；非法超64字 |

示例：`GET /api/v1/matchmaker/workbench/introductions?page=1&page_size=20&status=PENDING`，Headers `Authorization: Bearer <access_token>`。非法：`?page=0`。

| 返回字段 | JSON类型/必返 | 空值、枚举、含义/示例 |
| --- | --- | --- |
| workflow_version | integer/是 | **新增**，固定2；客户端以此判断新流程已部署 |
| items | array/是 | 记录列表，空时[] |
| items[].id | integer/是 | 牵线ID，例如12 |
| items[].status | string/是 | 四态，与表中阶段一致 |
| items[].failure_reason | string/null/是 | 历史兼容字段；FAILED时为最终失败原因，PENDING可能暂存会员拒绝附言；不要据此决定阶段 |
| items[].note | string/null/是 | 来源/幂等标记，例如discovery-apply:501；null为无备注 |
| items[].created_at | string/是 | 创建时间，ISO datetime |
| items[].updated_at | string/是 | 最近变更时间，ISO datetime |
| items[].application_response | string/是 | **新增** UNANSWERED未回应（含过期）/ACCEPTED同意/REJECTED拒绝；手工新建默认UNANSWERED |
| items[].response_reason | string/null/是 | **新增** 待牵线且会员拒绝时的附言；否则null |
| items[].from_phone_viewed | boolean/是 | **新增** 当前红娘在本条、本轮已查看申请人有效电话 |
| items[].to_phone_viewed | boolean/是 | **新增** 当前红娘在本条、本轮已查看被牵线方有效电话 |
| items[].from_user / to_user | object/是 | 申请人/被牵线方摘要；不含电话 |
| 上述双方对象.user_id | integer/是 | 会员ID，例如1/2 |
| 上述双方对象.nickname | string/是 | 姓名展示，缺失时未命名会员 |
| 上述双方对象.avatar | string/null/是 | 头像地址，null=未设置 |
| 上述双方对象.gender | integer/null/是 | 1男/2女，null=未填 |
| 上述双方对象.is_vip | boolean/是 | 有效会员标识 |
| page / page_size | integer/是 | 当前页/每页条数 |
| total | integer/是 | 同筛选条件的总条数 |
| has_more | boolean/是 | 是否还有下一页 |

成功空列表示例：`{"workflow_version":2,"items":[],"page":1,"page_size":20,"total":0,"has_more":false}`。

客户端展示：PENDING下以 `application_response` 区分「对方拒绝」「未回应」，不要显示为失败；电话需逐侧重新调用查看接口才能展示，查看标记不是号码缓存。列表无业务次数扣减。

## 查看牵线一方电话（新增）

`POST /api/v1/matchmaker/workbench/introductions/{introduction_id}/contact-views`，200。

| 参数 | 位置/JSON类型 | 必填/默认 | 校验与意义/示例 |
| --- | --- | --- | --- |
| Authorization | header/string | 是/无 | Bearer登录凭据；非法：空 |
| introduction_id | path/integer | 是/无 | >=1，牵线ID；合法12，非法0 |
| side | body/string | 是/无 | from申请人/to被牵线方；合法from，非法other |
| contacts_obtained | body/boolean | 否/false | 红娘确认已获得双方联系方式时传true；双方电话未查看齐返回409 |

示例：`POST /api/v1/matchmaker/workbench/introductions/12/contact-views`，Headers `Authorization: Bearer <access_token>`、`Content-Type: application/json`，Body `{"side":"from"}`。非法Body：`{"side":"other"}`。

| 返回字段 | JSON类型/必返 | 含义/空值 |
| --- | --- | --- |
| introduction_id | integer/是 | 本条牵线ID |
| status | string/是 | 查看操作后的四态权威状态 |
| from_phone_viewed / to_phone_viewed | boolean/是 | 当前红娘本条、本轮双方电话查看状态 |
| contact | object/是 | 本次指定一方的联系方式 |
| contact.user_id | integer/是 | 指定方用户ID |
| contact.nickname / real_name | string/null/是 | 昵称/实名，未填为null |
| contact.phone | string/null/是 | 仅本次指定方电话；null=未留电话，不推进该方查看标记 |
| contact.wechat | null/是 | 本接口固定null，只处理电话，不额外暴露微信 |
| contact.scope | string/是 | ALL=超级红娘工作范围；SERVED=普通红娘本条服务范围 |

示例：
```json
{"introduction_id":12,"status":"PENDING","from_phone_viewed":true,"to_phone_viewed":false,"contact":{"user_id":1,"nickname":"测试会员","real_name":null,"phone":"13800000001","wechat":null,"scope":"SERVED"}}
```

必须先查询工作台列表再逐侧调用；不要用通用会员联系方式接口冒充本条电话查看。服务端持有牵线行锁，查看双方电话仍保留PENDING。红娘明确确认后再提交 `{"side":"to","contacts_obtained":true}`，只有本轮双方电话均已查看才在同一事务内推进IN_PROGRESS并记录确认审计。取消确认不发请求、不改变状态；前端保留确认入口。审计按记录ID及红娘ID隔离，不含电话号码，不能用另一条牵线/另一位红娘的查看凑齐。拒绝事件审计ID划分新轮次。重复确认不重复推进状态，无收费、无额度扣减，不要求Idempotency-Key；沿用统一请求限流。失败事务回滚。

2026-11-02 调整：新增可选 `contacts_obtained`，默认false；旧版“查看双方电话后自动推进”改为显式确认。前后端需同步更新，未传该字段的客户端不会推进阶段，已有牵线中及终态记录保持不变。

## 确认牵线结果（修改）

`PATCH /api/v1/matchmaker/workbench/introductions/{introduction_id}/status`，成功204，**无返回体**。

| 参数 | 位置/JSON类型 | 必填/默认 | 校验与意义/示例 |
| --- | --- | --- | --- |
| Authorization | header/string | 是/无 | Bearer登录凭据；非法：空 |
| introduction_id | path/integer | 是/无 | >=1；合法12，非法0 |
| status | body/string | 是/无 | 旧四态枚举保留，但仅IN_PROGRESS→SUCCEEDED/FAILED可变更；相同状态为幂等无操作 |
| contact_confirmed | body/boolean | 否/false | **新增** 红娘确认已联系双方并了解被牵线方态度，变更最终结果时必须true |
| failure_reason | body/string/null | 否/null | <=500字；FAILED必填非空，其他状态不得携带原因 |

示例：`PATCH /api/v1/matchmaker/workbench/introductions/12/status`，Headers同上，Body `{"status":"FAILED","contact_confirmed":true,"failure_reason":"被牵线方明确表示不合适"}`。非法：`{"status":"FAILED","failure_reason":""}`。

先查看双方电话取得IN_PROGRESS，再确认已联系；服务端再次检查当前红娘的本条双方电话审计。成功时写联系确认和状态审计，清理过时失败原因；终态不可回退/换结果，重复相同结果不会重复写审计。冲突返回409，客户端刷新列表；不因为最终成功自动扣认识申请次数，不改变原认识申请扣次/退次逻辑。

## 新建牵线记录（修改）

`POST /api/v1/matchmaker/workbench/introductions`，201。

| 参数 | 位置/JSON类型 | 必填/默认 | 校验与意义/示例 |
| --- | --- | --- | --- |
| Authorization | header/string | 是/无 | Bearer登录凭据；非法：空 |
| from_user_id | body/integer | 是/无 | >=1，申请人且在工作范围；合法1，非法0 |
| to_user_id | body/integer | 是/无 | >=1，被牵线方且在工作范围，不能等于申请人；合法2，非法1（与申请人相同） |
| applied_at | body/string/null | 否/null | ISO日期YYYY-MM-DD，默认当天；非法not-a-date |
| result | body/string | 否/PENDING | **修改** 只能PENDING，不得录入终态绕过跟进；非法SUCCEEDED |
| finished_at | body/string/null | 否/null | 兼容保留但必须null，新记录不能填写完成时间 |
| failure_reason | body/string/null | 否/null | 兼容保留，必须null/空，新记录没有最终失败原因 |

示例：`POST /api/v1/matchmaker/workbench/introductions`，Headers同上，Body `{"from_user_id":1,"to_user_id":2,"applied_at":"2026-11-02","result":"PENDING"}`。成功 `{"id":12,"status":"PENDING"}`；返回id为新记录ID，status固定PENDING。相同红娘、双方及申请日期的重复录入返回409，不要求Idempotency-Key；不扣次数，无新增次数额度。新建不向会员自动发送认识申请，不开放聊天。

## 兼容、历史数据与部署顺序

新增列表字段向后兼容。**行为收紧**：旧客户端手动从待牵线改状态或直接录入成功/失败会收到409/422；必须同步更新小程序。新版小程序仅在列表返回 `workflow_version=2` 后开放操作，否则只读并提示后端升级；不存在用旧接口猜测状态的兜底。

1. 先部署后端（无需新增表/列，使用现有审计表），再部署小程序。
2. 使用 `migrations/introduction_workflow/20261102_01_review.sql` 只读核对历史自动失败记录，导出原始行备份后再执行 `migrations/introduction_workflow/20261102_01_correction.sql`。仅纠正旧逻辑下因会员拒绝/过期自动失败的 `discovery-apply` 记录；排除红娘人工确认失败及后台历史记录。不在启动时自动迁移，脚本尚未针对远端执行。
   > 该脚本是纯数据修正、无 DDL，且 `failure_reason` 在 `match_apply.status = 3` 时被置 NULL、原值不保留，**不存在可自动执行的 down**，故按数据修正而非 schema 迁移命名（原文件名 `20261102_01_up.sql`，与同目录 `20261102_01_review.sql` 一致地不带 `_up`/`_down` 后缀，因此不进入 `scripts/check_migrations.py` 的 up/down 配对检查）。回滚口径见下一条：从事先导出的原始行按 ID 恢复。
3. 历史修复回滚从事先导出的原始行按ID恢复，不可把所有待牵线批量改成失败。新流程审计保留，旧客户端不再支持写操作。
4. 微信端回归：未回应→单侧查看仍待牵线→双方查看进入牵线中→确认联系后成功/失败；另测拒绝回待牵线、同意直接成功、空电话及越权拒绝。
