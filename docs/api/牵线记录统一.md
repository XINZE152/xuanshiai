# 牵线记录统一（INTRO-SHARED-20261112）

后台和红娘工作台的牵线列表、统计、创建、状态和删除共同使用 `matchmaker_introduction`。会员申请回应仍保存在 `match_apply`；它不是后台牵线列表的数据源。申请与牵线通过 `discovery-apply:<申请ID>` 或历史 `admin-entry:<申请ID>` 关联。会员同意时牵线成功，拒绝时牵线失败并保留原因，会员回应、通知和申请次数仍按申请原流程处理。

## 状态和权限

牵线阶段为 `PENDING` 待牵线、`IN_PROGRESS` 牵线中、`SUCCEEDED` 成功、`FAILED` 失败、`CLOSED` 已关闭。后台保留旧数字字段 `status`：待牵线和牵线中均为 0，成功为 1，失败为 2，关闭为 3；列表新增 `introduction_status` 区分前两种。顶部 `pending/matching/success/fail/closed` 按同一阶段统计。后台按原管理员数据范围限制；工作台按原红娘范围限制。无权限或记录不存在返回 404。

后台读取 `GET /api/v1/admin/matchmaker/match-records` 与 `GET /api/v1/admin/matchmaker/match-records/statistics`，均需管理员 Bearer 令牌；列表支持 `page`（1–1000）、`page_size`（1–100）、`search`、日期区间、`matchmaker_id` 和 `status_group`。列表返回 `items/page/page_size/total/has_more`，每项沿用原 ID、双方会员、时间及数字状态，并增加 `introduction_status`。统计返回 `total/pending/matching/success/fail/closed`。

后台 `POST /api/v1/admin/matchmaker/match-records` 接受 `from_love_user_id`、`to_love_user_id`、`create_time`、`complete_time`、`line_status`（1 成功、2 失败），返回 201 及新牵线 ID。双方相同或时间非法返回 422，会员不存在返回 404，重复记录返回 409。`PATCH /api/v1/admin/matchmaker/match-records/{id}` 接受 `{"status":2,"reason":"不合适"}`；状态值为 0–3，完成后不能改为其他结果，可关闭；成功返回新记录，冲突返回 409。成功记录仍创建双方匹配关系；失败不伪造次数退款。删除使用原敏感操作确认和幂等规则，删除牵线记录不删除会员申请或匹配关系。

工作台 `GET /api/v1/matchmaker/workbench/introductions` 和 `POST /api/v1/matchmaker/workbench/introductions` 使用用户 Bearer 令牌；筛选支持上述五种阶段。`PATCH .../{id}/status` 仍要求先查看双方电话及确认联系，失败必须给出原因。后台与工作台的记录 ID 一致，任一端的结果修改会立即被另一端读取。

超时任务扫描共享牵线表中的待牵线和牵线中记录并标记失败；已关联、仍待处理的会员申请同步结束，避免超时后仍可回应。此操作保留申请表和审计，不伪造余额退款。

## 历史数据和回滚

执行 `scripts/backfill_unified_introductions.py` 前必须停止牵线写入及超时任务，备份 `match_apply`、`matchmaker_introduction` 和 `business_audit_log`。显式设置 `INTRODUCTION_MIGRATION_DATABASE_URL` 指向目标 MySQL，先不带参数 dry run；校验记录和关联后，用 `--apply --expect-applications <申请条数> --expect-introductions <原牵线条数>` 执行。新增记录使用 `admin-entry:<原ID>` 标识；已有工作台记录及审计不改 ID，已有后台审计仍可通过原 ID 和标识追溯。检测到重复链接、状态或双方冲突会回滚并停止；重跑不会重复新增。原申请表保留，禁止直接删除。

回滚需再次停止写入并恢复上述备份，同时切回旧版；迁移后产生的新记录和审计必须先导出并人工合并，不能直接覆盖。切换后须检查记录数、状态分组、原审计和两端同一 ID 的创建/状态操作。
