### D-1 直播 WS 保活校验绑定错误 ID【严重度：致命，功能实际不可用】

**现状与根因（已逐行复核）**

- 票根签发：`app/api/routes/live.py:124` → `create_live_ws_ticket(current.id, session_id, ticket_id, expires_in)`，其中 `session_id` 是 **URL 路径参数 = 直播场次 ID**。
- 票根结构：`app/core/security.py:43-54`，`payload["sid"] = str(session_id)` = 直播场次 ID。
- 消费端二次确认：`app/api/routes/live_ws.py:28,33` 明确用 `ticket_session_id` 与 URL 的直播场次 `session_id` 比对，**进一步证明 `sid` 语义就是直播场次 ID**。
- 缺陷点：`app/api/routes/live_ws.py:101-109` 却把该值当作**登录会话 ID** 使用：
  ```sql
  SELECT 1 FROM user_session WHERE id=:sid AND user_id=:uid AND status=1
    AND revoked_at IS NULL AND access_expire_at>UTC_TIMESTAMP()
  ```
  参数 `{"uid": user_id, "sid": ticket_session_id}`。

**真实后果（比评估报告更严重）**

`live_ws.py:94-113` 是主循环：发消息/心跳 → 校验 → `sleep(0.05)`。上述查询用「直播场次 ID」去匹配 `user_session.id` 主键，除极端巧合（场次 ID 恰好等于该用户的某个登录会话 ID）外**必然查不到行** → `session_is_valid=False` → 立即 `close(1008, "session revoked")`。

**结论：直播 WebSocket 在真实环境下连上后会被立刻关闭，直播实时能力实际不可用。** 评估报告表述为「可能误判关闭或校验形同虚设」，实际是**必然关闭**。

**修改方案（二选一，推荐 A）**

- **方案 A（推荐，语义正确、改动可控）**：票根增加登录会话字段。
  1. `app/core/security.py:43-53`：`create_live_ws_ticket` 增加参数 `user_session_id: int`，payload 新增 `"uss": str(user_session_id)`；`decode_live_ws_ticket:62-68` 的必需字段校验同步加上 `uss`。
  2. `app/api/routes/live.py:115-125`：从当前登录态取会话 ID 传入（`get_current_user` 依赖已解析出 token 的 `sid`，直接复用，避免多查库）。
  3. `app/api/routes/live_ws.py:28,107`：新增 `login_session_id = int(payload["uss"])`，SQL 参数改用 `login_session_id`。
  4. 回归用例：场次 ID 与登录会话 ID 故意取不同值，断言 WS 不会因 1008 被动断开。
- **方案 B（快速止血）**：先删除 `live_ws.py:101-112` 的整段保活校验，仅保留 Redis Pub/Sub 与心跳，另开 P1 任务补回正确实现。
  - 收益：1 小时内恢复可用；代价：丧失「登录会话被撤销后即时踢下线」能力，需在任务票中显式记录该安全降级。

**验收标准**

1. 用真实账号连接 `WS /live/sessions/{id}/events`，连接后持续存活 ≥ 60 秒不被 1008 关闭；
2. 主动撤销该用户登录会话后，连接在一个校验周期内被关闭（仅方案 A 需满足）；
3. 新增回归测试覆盖「场次 ID ≠ 登录会话 ID」场景。

| 项 | 值 |
| --- | --- |
| 优先级 | **P0** |
| 工时 | 方案 A：1 人日；方案 B：≤0.5 人日 |
| 依赖 | 无 |
| 证据 | `live_ws.py:28,33,101-112`；`security.py:43-54`；`live.py:124` |

### D-5 后台权限映射 fail-open，56 条路由完全无权限校验【严重度：高，定性已修正】

**现状（本次新增的精确核查结果）**

`app/api/dependencies.py:279-281` 在 `get_current_matchmaker_admin` 中按 **URL 字符串子串匹配** 推导所需权限：

```python
permission = _matchmaker_admin_permission(request)   # dependencies.py:184-251
if permission:                                        # ← 未匹配到时静默放行
    current.require(permission)
```

`_matchmaker_admin_permission` 对未列入关键词的路径 `return None` → **不执行任何权限校验（fail-open）**。

对全部走红娘后台鉴权的路由做 AST 静态核对结果：**共 380 条路由，其中 56 条落入盲区、完全不做权限校验**。

**盲区清单（按风险排序）**

| 风险 | 文件 | 条数 | 代表性路径 | 危害 |
| --- | --- | --- | --- | --- |
| 极高 | `app/api/routes/admin_config.py` | 3 | `PATCH /api/v1/admin/configs/{namespace}` | **任意后台账号可修改系统配置**（`admin_config.py:21`）；且可读配置审计 `:27` |
| 极高 | `app/api/routes/admin_content.py` | 4 | `POST/PATCH/DELETE /api/v1/admin/content/{domain}` | **任意后台账号可增删改运营内容**（`:29,:40,:52`） |
| 高 | `app/api/routes/customer_leads_admin.py` | 16 | `POST /admin/customer-leads/batch-import`、`PATCH /{lead_id}/assignment`、`/{lead_id}/abandon`、`/{lead_id}/restore` | 客户线索全生命周期（含联系方式类敏感数据）无鉴权 |
| 高 | `app/api/routes/identity.py` | 3 | `GET/PATCH /admin/matchmaker/applications/{application_id}` | 红娘申请审核可被任意后台账号操作（`:80,:96,:106`） |

**修改方案**

1. **改为 fail-closed（核心）**：`dependencies.py:279-281` 调整策略——
   - 未匹配到权限映射的路径，**非显式声明豁免的一律 403**，并在异常信息中带上路径，便于快速发现遗漏；
   - 维护一个**显式豁免白名单**（仅 `/auth/me`、`/auth/logout` 等），白名单写在代码常量中而非散落在 if 分支里。
2. **逐条补显式 `require()`**：为上述 56 条路由在函数体内首行添加对应权限码，与既有写法保持一致（参考 `activity_admin.py:258,608` 的 `current.require("community.activity.read")`）。
   推荐权限码映射：
   - `admin_config.py` → `matchmaker.system.manage` / `.read`
   - `admin_content.py` → 按 domain 区分 `community.moderate` / `video.manage` / `merchant.manage`
   - `customer_leads_admin.py` → `matchmaker.lead.manage` / `.read`（若权限码不存在需先在权限字典中登记）
   - `identity.py` 后台三条 → `matchmaker.manage` / `.read`
   - `matchmaker_admin_account.py` 三条 → `matchmaker.account.manage` / `.read`
   - `matchmaker_staff_admin.py:249` → `matchmaker.manage`；`:147` → `matchmaker.read`
   - `organization_admin.py:87` → `matchmaker.organization.manage`
   - `admin_home.py` → `matchmaker.read`
3. **加静态回归测试**（关键）：新增测试用 AST 扫描所有 `Depends(get_current_matchmaker_admin)` 的路由，断言「每条路径要么命中映射、要么函数体内含 `current.require(...)`」。此测试可长期防止新路由再次落入盲区。
4. 权限码登记：确认新增权限码已进入 `matchmaker_admin_permission` 的可分配集合与前端权限树（`matchmaker_staff_admin.py:147` 的菜单树）。

**验收标准**

1. 静态回归测试通过，盲区路由数 = 0；
2. 用「仅有最低权限」的后台账号访问 `PATCH /admin/configs/{namespace}`、`POST /admin/content/{domain}`、`GET /admin/matchmaker/audit-logs`，均返回 403；
3. 未匹配路径默认 403，显式白名单仅含认证类端点。

### D-6 消息后台无 STORE 独立分支【严重度：中】

**现状**：`app/services/message_admin.py:27-39` 的 `_message_scope` 只有三支——`ALL/*` → `1=1`、`SELF` → 基于 `resource_assignment.matchmaker_id`、其余全部落入「组织（含 parent_id）」分支。**STORE（门店）范围没有独立实现**，门店级管理员会看到整个组织的消息。

**修改方案**

## 五、验收标准（按类别）

### 5.1 功能类

- 每条新增/修复路由均能在 OpenAPI 文档中看到，且文档描述与实际行为一致。
- 所有「涉及金额」的动作（支付、开通、退款、提现、奖励）满足：幂等键可控、重复请求不重复扣款/发放、失败有明确状态与审计。

### 5.2 安全类

- 权限：**不存在任何走后台鉴权却不做权限校验的路由**（由 D-5 的静态测试持续保证）。
- 数据范围：`ALL / SELF / STORE / ORGANIZATION` 四档均有实现，且**无绑定组织时返回 0 条**（fail-closed）。
- 越权：附真实多组织账号的验证记录（A 组织账号访问 B 组织数据 → 0 条或 403）。

### 5.3 可靠性类

- 实时通道（直播 WS、聊天 WS）：Redis 不可用时 fail-closed 且给出明确关闭码；断线重连可补发。
- 异步投递（通知、直播事件、Outbox）：有重试、有死信、有崩溃恢复。

### 5.4 文档类

- `docs/api/*.md` 中出现的路径与 OpenAPI 逐条对齐（D-7 的检查方式可复用为常规核对手段）。
