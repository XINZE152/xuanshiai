## 2. 与报告不一致之处（事实校正）

1. **学历方向不是缺陷，是已修复项。** `e65f597`（2026-09-13，在当前 HEAD 祖先内）已把 `_score_education` 从 `target <= minimum` 改为 `target >= minimum` 并新增方向锁定测试。报告中“编码方向与评分器相反”一节在复核时点已过期，**唯一残留缺口是 `max` 上界未处理**（见 C-03）。
2. **“每个用户固定少 20 分”不成立。** 权重会按可用维度重分配并做双向合成。准确表述：合计权重 20 的两个维度（婚姻 10、关系期待 10）在合法集合输入下无法贡献应得分数，**最终影响取决于其他维度可用情况与资料覆盖度**。
3. **`app/services/voice/realtime/` 存在。** 不能把“v2 无 generation audit”认定为本分支已核实缺陷，也不能把“目录不存在”当作“问题已修复”。列为 V-01。
4. **“未登记任务一律按 AI 生成处理”不可采纳。** `cleanup` 是治理任务（`profile.py:254`、撤回授权时专门创建，见 `derivation_outbox.py:872-892`），AI 关闭后仍应有明确策略继续运行；正确做法是三类显式登记（C-07 修复方案）。
5. **“每个 AI 路由都必须有同一个 feature gate”不成立。** 生成、读取、撤回、删除必须分别定义策略，否则修“少了门禁”会制造“无法清理”（C-08 的成因）。
6. **收入问题的根因位置需要更具体。** 报告写“理想型 Schema 注释和 mock 使用金额区间”，实际是**三处口径分裂**：`ai_profile.py:187-189` 注释 + `_RANGE_LIMITS`（`ai_profile.py:189`）+ `providers.py:159`（金额），`prompts/profile_extract.py:41`（档位），`compatibility.py:408`（直接数值比较）。只改 prompt 无法闭环。
7. **测试夹具的问题不止“一种类型”。** 除金额/集合外，`relationship_goal: "婚姻"`（中文字面量）也不在枚举 `{marriage, dating, friendship}` 内（`ai_profile.py:173`），且个人 `income_band: 20000` 会被 `_INTEGER_LIMITS` 直接拒绝（`ai_profile.py:194-196`）。
8. **后续审查报告需写明 commit SHA、检查范围、实际测试命令与结果**，否则本地/主分支/测试服容易被混为一谈（本报告 §0 已按此格式给出基线）。

1. **新增统一规范化层**（在 `app/services/ai/compatibility.py` 评分区，`_as_str` 之前）：

   ```python
   def normalize_dimension_value(field_key: str, raw: Any) -> tuple[str, Any]:
       """契约形态归一：(status, value)，status ∈ {"ok", "unknown"}。

       - 集合类字段（marriage_status / relationship_goal / city_code / *_tags）：
         tuple / list / set / frozenset / 单标量 → tuple[str, ...]；

   ```

2. **把记忆清理接入 `purge_ai_resources`**：新增 `scope="memory"`（或按 subject 粒度），删除顺序遵循“子表在前”，并沿用既有 **generation 围栏**（`derivation_outbox.py:561-570`：同步阶段打 marker，DELETE 只删带 marker 的行）——确保清理任务迟到执行时**不会误伤撤回后新建的数据**。
   - **已实施（围栏口径：序号围栏，fail-closed）**：记忆内核**没有**「同步阶段打 marker」这个半部——它的设计是 event 账本 append-only + 视图行 `status`，逐表打 marker 需改 6 张表的写入路径，超出本批范围且风险更高。改用 **owner 序号水位作围栏**（`ai_memory_owner_sequence.next_seq`），因此**不需要新增 generation 列**。三点实现要点（均为施工中发现并修正）：
     1. **围栏值必须在撤回事务里读取并冻结**（显式 forget 写进任务 payload，授权撤回/画像删除写进事件 payload）。若等到清理任务执行时再读水位，撤回后重新授权写入的新记忆会被一并删除且不可恢复。
     2. **清理按围栏过滤**：账本 `server_seq <= fence_seq`、视图 `last_event_seq <= fence_seq`；投影表无序号列，有围栏时只删 `status <> 'active'` 的旧代投影（重建的新代投影是 active，必须保留）。
     3. **有围栏时保留 `owner_sequence` 行**（仅无围栏的全量清理才删除）：若归零重编，幸存的新代行与后续写入的相对顺序会被破坏（新事件拿到更小 seq，`ORDER BY server_seq` 与 `after_seq` 分页错乱）。
     4. **围栏取「已分配最大序号」= `next_seq - 1`，不是 `next_seq`**：`next_seq` 是「下一个待分配」值（`MemoryLedger.append` 先用它当事件的 `server_seq` 再递增）。若直接用 `next_seq` 当围栏，`server_seq <= fence_seq` 会把撤回后写入的**第一条**新事件（恰好拿到那个值）一并删除——不可恢复的数据损失。已由 `test_fence_is_last_allocated_seq_not_next_seq` 钉住。
   - **fail-closed**：`memory` / `profile` / `consent_profile` 三个 scope 缺少围栏时退化为**不清**（返回 0）而非全删；仅 `user`（账号注销，owner 已不存在、不会有新行）允许无围栏全量清理。
