# 红娘后台接口文档

版本：v1；基础地址：`/api/v1`；Content-Type：`application/json`。

## 1. 认证约定

红娘后台使用独立账号表 `matchmaker_admin_account` 和独立会话表，不复用 C 端用户登录，也不复用普通管理员登录。项目不提供公开注册接口，账号由后端预置或后续发放给红娘用户。除登录外，所有接口必须携带 `Authorization: Bearer <access_token>`。

账号密码仅用于 `admin/matchmaker/auth/login`，密码服务端只保存 bcrypt 哈希。连续 5 次密码错误会锁定 15 分钟；账号停用后已有 token 立即失效。access token 默认 60 分钟，refresh token 默认 30 天，refresh 时旧会话轮换失效。

**第一个账号怎么来**：没有任何自动播种——`AUTO_INIT_DB`、`database_setup_marriage.py` 和 `migrations/` 都不会建后台账号，新库上这张表是空的（`SELECT COUNT(*) FROM matchmaker_admin_account` = 0），此时管理员端无论输什么都返回 `401 账号或密码错误`；密码也不在任何配置文件里（只存哈希，无法反查）。开发/联调环境用 `python scripts/seed_matchmaker_admin_account.py --username <自定登录名>` 交互输入密码建号（默认 `data_scope=ALL` + 权限 `*`，登录名重复时默认拒绝、需显式 `--reset-password`）；生产环境改用已登录总店账号的 `POST /admin/matchmaker/accounts`（带审计）或 `POST /admin/matchmaker/accounts/{id}/reset-password`，不要用脚本发号。

统一错误格式：

```json
{"detail":"账号或密码错误"}
```

常见状态码：`400` 参数格式错误，`401` 未登录/令牌失效/登录失败，`403` 账号停用或无权，`404` 资源不存在，`409` 状态冲突，`422` 参数校验失败。

## 2. 认证接口

### 2.1 红娘后台账号密码登录

**基本信息**：`POST /api/v1/admin/matchmaker/auth/login`；无需登录；成功 `200`。

**请求参数**：

| 参数 | 位置 | 类型 | 必填 | 校验与含义 |
| --- | --- | --- | --- | --- |
| `username` | body | string | 是 | 3-64 位，仅允许字母、数字、`_`、`.`、`-`；后台账号名 |
| `password` | body | string | 是 | 8-128 位；登录密码，不能在日志或响应中返回 |

**请求示例**：

```http
POST /api/v1/admin/matchmaker/auth/login
Content-Type: application/json
```
```json
{"username":"mm_zhangsan","password":"CorrectHorseBattery1"}
```

**成功返回**：

```json
{
  "access_token":"<access-token>","refresh_token":"<refresh-token>","token_type":"bearer","expires_in":3600,
  "account":{"id":12,"username":"mm_zhangsan","display_name":"张三","matchmaker_user_id":1001,"status":1,"last_login_at":"2026-08-06T10:00:00"}
}
```

| 返回字段 | 类型 | 必返 | 含义 |
| --- | --- | --- | --- |
| `access_token` | string | 是 | 调用后台接口的短期令牌 |
| `refresh_token` | string | 是 | 刷新 access token 的长期令牌，仅客户端安全存储 |
| `token_type` | string | 是 | 固定为 `bearer` |
| `expires_in` | integer | 是 | access token 有效秒数 |
| `account` | object | 是 | 当前独立后台账号，字段见 2.2 |
| `account.id` | integer | 是 | 后台账号 ID |
| `account.username` | string | 是 | 后台登录名 |
| `account.display_name` | string | 是 | 展示名称 |
| `account.matchmaker_user_id` | integer/null | 是 | 绑定的用户系统红娘 ID；未绑定时为 null |
| `account.status` | integer | 是 | `1` 正常，`2` 停用 |
| `account.last_login_at` | datetime/null | 是 | 最近成功登录时间 |

错误：账号不存在、密码错误、账号停用或锁定均返回 `401` 的统一提示，避免泄露账号是否存在。

### 2.2 查询当前后台账号

**基本信息**：`GET /api/v1/admin/matchmaker/auth/me`；需要登录；成功 `200`。

**请求参数**：无 body。Header：`Authorization: Bearer <access_token>`。

**返回示例**：

```json
{"account":{"id":12,"username":"mm_zhangsan","display_name":"张三","matchmaker_user_id":1001,"status":1,"last_login_at":"2026-08-06T10:00:00"},"permissions":["matchmaker:read","matchmaker:service:write"]}
```

`permissions` 为当前版本固定能力声明；权限不足或 token 非红娘后台 token 返回 `401`，不会接受用户端 token 或普通管理员 token。

### 2.3 刷新令牌

**基本信息**：`POST /api/v1/admin/matchmaker/auth/refresh`；无需 access token，但必须提供有效 refresh token；成功 `200`。

**请求参数**：`refresh_token`，body string，必填，20-512 位；旧 refresh token 使用后立即失效。

**请求示例**：

```json
{"refresh_token":"<refresh-token>"}
```

**返回**：格式与 2.1 完全相同。refresh token 过期、已注销或已轮换返回 `401`。

### 2.4 退出登录

**基本信息**：`POST /api/v1/admin/matchmaker/auth/logout`；需要登录；成功 `204`，无返回体。

Header：`Authorization: Bearer <access_token>`。重复退出返回 `204`；该会话的 access/refresh token 均失效，不影响其他设备会话。

## 3. 红娘与服务接口

以下接口全部使用独立红娘后台 token，并统一校验账号状态和会话有效期。

### 3.1 红娘列表

`GET /api/v1/admin/matchmaker/matchmakers`，需要登录，成功 `200`。

参数：`page` query integer，默认 1，范围 1-1000；`page_size` query integer，默认 20，范围 1-100。列表只返回有效服务红娘，空数据返回 `items: []`。

请求示例：

```http
GET /api/v1/admin/matchmaker/matchmakers?page=1&page_size=20
Authorization: Bearer <access-token>
```

返回示例：

```json
{"items":[{"user_id":1001,"nickname":"张三","avatar":"/storage/uploads/a.jpg","application_type":"service_matchmaker","intro":"专注本地婚恋服务","certification_tags":["平台认证"],"success_count":18,"rating_score":4.8,"rating_count":12,"is_available":true}],"page":1,"page_size":20,"total":1,"has_more":false}
```

返回字段：`items` 红娘数组；`user_id` 红娘用户 ID；`nickname` 昵称；`avatar` 头像；`application_type` 固定 `service_matchmaker`；`intro` 简介；`certification_tags` 认证标签；`success_count` 完成服务数；`rating_score` 平均评分；`rating_count` 评分数；`is_available` 当前是否可接单；`page/page_size/total/has_more` 分页信息。

### 3.2 红娘详情

`GET /api/v1/admin/matchmaker/matchmakers/{matchmaker_id}`，需要登录，成功 `200`。`matchmaker_id` path integer，必须大于等于 1。返回结构与 3.1 的 `items` 单项相同；红娘不存在或已不可用返回 `404`。

### 3.3 服务商品列表与详情

列表：`GET /api/v1/admin/matchmaker/service-products`；详情：`GET /api/v1/admin/matchmaker/service-products/{product_id}`。均需登录，成功 `200`；`product_id` 必须为正整数。列表空数据返回 `[]`，详情不存在/已下架返回 `404`。

商品返回字段：`id` 商品 ID；`code` 唯一编码；`name` 名称；`service_type` `1` 付费牵线、`3` 私人定制；`price` 金额；`description` 描述；`active` 是否上架；`created_at/updated_at` 时间。

### 3.4 新增服务商品

**基本信息**：`POST /api/v1/admin/matchmaker/service-products`；需要登录；成功 `201`。

参数：`code` string 2-32 位小写字母开头且仅含小写字母/数字/下划线；`name` string 1-128；`service_type` integer 枚举 `1/3`；`price` number 大于 0 且不超过 1000000，最多 2 位小数；`description` string 1-2000；`active` boolean 可选默认 true。请求示例：

```json
{"code":"one_to_one_match","name":"一对一牵线","service_type":1,"price":199.00,"description":"红娘一对一牵线服务","active":true}
```

返回新增商品对象，格式见 3.3。编码重复返回 `409`。

### 3.5 修改或下架服务商品

**基本信息**：`PATCH /api/v1/admin/matchmaker/service-products/{product_id}`；需要登录；成功 `200`。

请求 body 可部分更新：`name`、`service_type`、`price`、`description`、`active`，校验规则与 3.4 相同；至少提供一个字段。示例：`{"active":false,"description":"暂时停止售卖"}`。返回更新后的商品对象；不存在返回 `404`。下架为软删除，历史订单不被删除。

### 3.6 服务申请列表

**基本信息**：`GET /api/v1/admin/matchmaker/service-requests`；需要登录；成功 `200`。

参数：`status` query 可选 `0` 待处理、`1` 服务中、`2` 已完成、`3` 已取消；`page` 1-1000 默认 1；`page_size` 1-50 默认 20。返回分页对象：`items`、`page`、`page_size`、`total`、`has_more`。

`items` 字段：`id` 服务申请 ID；`user_id` 购买用户 ID；`matchmaker_id` 当前红娘 ID/null；`service_type` 服务类型；`status` 状态；`order_id` 订单 ID；`product_id` 商品 ID；`requirement` 用户需求；`feedback` 处理说明/null；`created_at`、`updated_at`、`start_at`、`end_at` 时间/null。

### 3.7 分配或处理服务申请

**基本信息**：`PATCH /api/v1/admin/matchmaker/service-requests/{service_id}`；需要登录；成功 `200`。

body 可包含：`matchmaker_id` integer/null，必须为有效服务红娘；`status` integer/null，枚举 `0/1/2/3`；`feedback` string/null，最多 2000 字。至少提供一个字段；设置状态为 `2` 或 `3` 时必须提供非空 `feedback`。

示例：

```json
{"matchmaker_id":1001,"status":1,"feedback":"已分配给张三并开始服务"}
```

允许状态迁移：`0 -> 1/3`，`1 -> 2/3`；其他迁移返回 `409`。返回更新后的服务申请对象；申请不存在返回 `404`，目标红娘无有效红娘角色返回 `422`。更新会记录更新时间并向相关用户发送通知。

## 4. 兼容与边界

### 4.1 红娘统计

`GET /api/v1/admin/matchmaker/statistics`，需要登录，成功 `200`，无请求体。返回 `total` 红娘申请总数、`available` 当前可接单数、`pending_services` 待处理服务单数、`active_services` 服务中数量、`completed_services` 已完成数量、`cancelled_services` 已取消数量。无数据时各数字为 `0`。账号无效返回 `401`；数据库不可用返回 `500`。

### 4.2 停用或恢复红娘接单

`PATCH /api/v1/admin/matchmaker/matchmakers/{matchmaker_id}/status`，需要登录，成功 `200`。path `matchmaker_id` 为正整数；body `status` 必填，`1` 恢复接单、`2` 停止接单；`reason` 可选，最多 255 字，停用时建议填写。示例：`{"status":2,"reason":"服务质量复核中"}`。返回 `{"matchmaker_id":1001,"status":2,"reason":"服务质量复核中"}`。接口同步更新红娘角色状态，停用不会删除历史服务单；无效红娘返回 `404`，并发更新以后一次提交结果为准。

### 4.3 门店接口

`GET /api/v1/admin/matchmaker/branches` 查询门店；`POST /api/v1/admin/matchmaker/branches` 创建门店；`GET /api/v1/admin/matchmaker/branches/{branch_id}` 查询详情；`POST /api/v1/admin/matchmaker/branches/{branch_id}/members` 添加门店成员。全部需要登录。

> **数据范围（2026-10-11，D-10）**：列表/详情/加成员均按账号四档数据范围收口（`ALL/STORE/ORGANIZATION/SELF`）。越权读取统一返回 `404`（不区分状态码，避免枚举）；加成员前先校验门店可见性，越权时**不落任何成员行**。未绑定组织的账号返回空列表 / `1 = 0`。详见 [`docs/api/后台数据范围与敏感操作-2026-10-04.md`](api/后台数据范围与敏感操作-2026-10-04.md) 第 1.3 节第 7 组。

创建 body：`code` 2-64 位字母/数字/下划线/短横线且唯一；`name` 1-128 字；`display_name` 可选最多 128 字；`region_code` 可选最多 64 字；`auto_redirect` 可选 boolean 默认 false。成员 body：`user_id` 正整数，`role_code` 为 `store_manager` 或 `store_matchmaker`。创建成功 `201`，详情/列表成功 `200`，重复编码、重复成员返回 `409`，用户无对应身份返回 `403`。门店返回字段为 `id/code/name/display_name/region_code/status/auto_redirect/created_at`；成员返回 `id/organization_id/user_id/role_code/status/started_at/ended_at`。

### 4.4 资源分配

`POST /api/v1/admin/matchmaker/assignments` 分配会员资源；`GET /api/v1/admin/matchmaker/assignments` 查询分配记录。需要登录。创建 body：`user_id` 必填正整数；`organization_id` 和 `matchmaker_id` 至少填写一个且为正整数；`source` 枚举 `manual/promotion/default/self_created`，默认 `manual`。同一用户的新分配会结束旧的有效分配，返回 `201`；目标门店不存在、目标红娘无效或缺少目标返回 `404/422`。

> **数据范围（2026-10-11，D-10）**：`GET` 按四档收口（此前为无条件 `1=1`，任何门店账号可见全平台分配）；`POST` 要求目标门店/红娘落在当前账号作用域内，否则 `403`。
> **敏感操作（2026-10-11，D-9）**：`POST` 必须携带 `Idempotency-Key`（8–128）与 `confirm=true`，缺键 `422`、缺二次确认 `428`；同键重放返回上次结果，不重复创建分配。越权校验先于幂等预占执行。

查询参数：`page` 默认 1、范围 1-1000；`page_size` 默认 20、范围 1-100；`user_id`、`matchmaker_id` 可选正整数。返回 `items/page/page_size/total/has_more`，`items` 字段为 `id/user_id/organization_id/matchmaker_id/source/status/effective_at/ended_at`；无记录返回 `items: []`。并发分配在事务内先结束旧记录再创建新记录。

### 4.5 安排约见

`POST /api/v1/admin/matchmaker/meetings/requests/{request_id}/schedule`，需要登录，成功 `201`。path `request_id` 为正整数；body 沿用约见安排契约，必须提供 `scheduled_at`、`location`，可提供参与者和组织信息，具体长度/时间校验由 `MeetingScheduleCreate` 执行。已安排、已取消或不存在的申请返回 `409/404`；重复提交不会生成可并存的无效安排。返回 `id/request_id/organizer_id/organization_id/scheduled_at/location/status/cancel_reason/created_at/updated_at`。

## 5. 会员 CRM 接口

以下接口均使用独立红娘后台账号，必须携带 `Authorization: Bearer <access_token>`。

### 5.1 会员列表

`GET /api/v1/admin/matchmaker/members`，成功 `200`。query：`page` 1-1000 默认 1；`page_size` 1-100 默认 20；`gender` 可选 `1/2`；`status` 可选 `1/2/3`；`vip` 可选 boolean；`search` 可选最多 64 字，匹配昵称或手机号。返回 `items/page/page_size/total/has_more`。item 字段：`id`、`nickname`、`phone`、`gender`、`status`、`is_vip`、`vip_end_at`、`matchmaker_id`、`created_at`。无数据返回 `items: []`。非法分页、枚举或超长搜索词返回 `422`。

请求示例：`GET /api/v1/admin/matchmaker/members?page=1&page_size=20&vip=true&search=138`。成功响应示例：`{"items":[{"id":1001,"nickname":"张三","phone":"138****8000","gender":1,"status":1,"is_vip":true,"vip_end_at":"2026-12-01T00:00:00","matchmaker_id":12,"created_at":"2026-08-01T10:00:00"}],"page":1,"page_size":20,"total":1,"has_more":false}`。手机号仅用于后台查询展示，客户端应继续脱敏。

### 5.2 会员统计

`GET /api/v1/admin/matchmaker/members/statistics`，成功 `200`，无请求体。返回 `total` 总会员数、`male` 男性数、`female` 女性数、`vip` 当前有效 VIP 数、`active` 状态正常数；无数据各字段为 `0`。

### 5.3 会员详情

`GET /api/v1/admin/matchmaker/members/{member_id}`，成功 `200`。`member_id` 必须为正整数；返回列表字段及 `avatar`、`birthday`、`is_married`、`height`、`weight`、`zodiac`、`household`、`ethnicity`、`house`、`car`、`smoking`、`hometown_*_code`、`residence_*_code`、`household_*_code`、`residence_city_code`。不存在返回 `404`，未登录返回 `401`。详情仅供已登录红娘后台使用，前端不得缓存手机号等敏感字段。

会员详情编辑接口支持通过下拉选项维护属相、户籍、民族、购房、购车和吸烟情况；体重支持 `30~150kg` 数字输入。字段为空时传 `null`，未提供的字段保持原值。

### 5.4 修改会员状态

`PATCH /api/v1/admin/matchmaker/members/{member_id}/status`，成功 `200`。body：`status` 必填枚举 `1` 正常、`2` 冻结、`3` 注销；`reason` 必填 1-255 字。示例：`{"status":2,"reason":"用户投诉待复核"}`。返回 `id/status/reason`。不存在返回 `404`，参数不合法返回 `422`；每次修改写入 `business_audit_log`，重复提交相同状态不会产生额外业务记录。冻结/注销后的会员仍保留历史服务、订单和会员记录。

### 5.5 自然注册会员的自动归属

会员本人在小程序里填资料不经过后台。当本次保存后基础信息那一栏十项（性别、生日、现居地、家乡、婚姻状况、学历、职业、收入、身高、体重）全部填齐时，服务端自动补一条 `resource_assignment`（`source='self_registered'`，只带 `organization_id`，`matchmaker_id` 为空）和一条 `matchmaker_member_review`=`PENDING`，该会员随即进入承接门店超级红娘工作台的资料待审列表，由超级红娘再指定具体服务红娘。**资料完整度分数不再参与判断**（2026-10-21 变更，此前要求完整度 ≥ 60；基础信息十项只占 48 分，会员必须补满头像/自我介绍/相册/兴趣标签才会进待审，与「填完基础信息就该有人审」的口径不符）。承接门店由 `MEMBER_AUTO_ASSIGN_ORGANIZATION_ID` 指定；未配置时不自动分派，自然注册会员继续等后台手工分派（`POST /api/v1/organization/assignments`）。已有生效归属的会员、服务红娘账号、门店已停用的情况都不触发，红娘已判过的 `PASSED/REJECTED` 也不会被打回待审。字段清单、触发入口与回滚方式见 `docs/api/个人资料.md` 的 2026-10-21 变更记录。

**待审卡片字段口径（`GET /api/v1/matchmaker/workbench/members`，2026-10-19 变更）**：待审要审的是会员自己填的资料，所以 `job` 优先取 `user_profile.occupation`（为空才回落到红娘录入/认证用的 `user_auth.job`），`hometown`/`residence` 在 `user_profile` 的旧文本列为空时按省市区编码现拼（与会员本人资料卡同一个 `region_display`，例如「浙江省 杭州市」）。字段名、类型和状态码均未变化，只影响这几个字段的取值来源；`PATCH .../public-profile-review` 的返回体同样走这套口径。

`education` 同日再变更一次：

- 变更前：只返回 `user_auth.education` 文本，自助填写的会员学历恒为 `null`。

**2026-10-21 再修正——档位字典回到存储刻度**：上面那条把字典写成会员端 AI 档位（1=初中及以下…6=博士）是错的，`user_profile.education_level` 的存储域是 **1=高中及以下、2=大专、3=本科、4=硕士、5=博士**（列注释、`app/services/discovery.py` 筛选项、`app/services/ai_avatar.py`、`app/services/admin_home.py` 统计均为此套），后果是自选「本科」（存 3）的会员在待审卡片显示成「大专」。现在卡片、`GET /api/v1/users/{id}/profile`、发现页、后台统计共用 `app/services/profile.py` 的 `EDUCATION_LEVEL_LABELS`（1-5），并新增反向 helper `education_level_from_label("本科") -> 3`（字典外返回 `None`，不做相近猜测）。AI 抽取契约仍是 1-6 域，写入存储前必须经 `app/services/ai/search.py` 的 `_AI_EDU_TO_STORAGE` 换算，两套刻度不得直接混用；小程序端原先反着解码（1=博士…8=小学）的四处（`pages/index/index.uvue`、`pagesSub/userExtra/user/detail.uvue`、`components/MatchmakerPendingReview.uvue`、`pagesSub/matchmaker/become-matchmaker.uvue`）和 onboarding 的 `educationMap` 已同步改为 1-5。

**待审列表数据源（2026-10-21 变更，仅前端取数）**：小程序「资料待审」的「全部/待审/我的/已驳回」四个页签改为只读 `GET /api/v1/matchmaker/workbench/members`（「待审/已驳回」带 `review_status`，搜索带 `search`），红娘录入会员（`POST` 同路径，返回 `201` + `member_id`）和自然注册会员提交资料后当场落在队列里，录入成功提示直接进入「待审」页签。此前这四个页签取的是首页广场 `GET /api/v1/discovery/plaza` 且只保留 VIP，而录入/未过审的会员既不是 VIP 也不在广场，所以永远看不到——接口本身没有变化，只改前端取数。「线上VIP/线下VIP」两个页签继续走广场，因为在线状态只有广场接口提供。卡片婚况文案同批按 `users.is_married` 的实际编码纠正（1 未婚、2 离异、3 丧偶、4-7 离异细分档；原先按 0 未婚、1 已婚显示，会把录入时选的「未婚」显示成「已婚」）。

**待审筛选（REVIEW-FILTER-20261107）**：`GET /api/v1/matchmaker/workbench/members` 新增可选 query `filters`，为 URL 编码的 JSON 对象，值均为字符串。需用户 Bearer 令牌及红娘工作台权限，成功返回原 `WorkspaceMemberPage`（`items`、`page`、`page_size`、`total`、`has_more`、`filter_version`）；无请求体。筛选与红娘原有数据范围同时执行，在计数和分页前应用，缺值不匹配；`mine=1` 在当前权限范围内再限制为本人当前跟进会员。

#### 捞取弃海会员（MEMBER-PICKUP-20261107）

`POST /api/v1/matchmaker/workbench/members/{member_id}/pickup`。需要 `Authorization: Bearer <用户访问令牌>` 和有效服务红娘工作台身份；无请求体，响应为 JSON、成功状态码 200。`member_id` 是路径内必填正整数，表示会员用户 ID。示例：`POST /api/v1/matchmaker/workbench/members/123/pickup`，无请求体。

成功响应示例：`{"member_id":123,"matchmaker_id":21,"review_status":"PENDING"}`。`member_id` 是被捞取会员 ID；`matchmaker_id` 是实际捞取红娘的用户 ID；`review_status` 固定为 `PENDING`，表示重新进入资料待审，并非自动审核通过。红娘有组织归属时只能捞取当前有效归属属于同组织、且审核状态为 `REJECTED` 的会员；无组织归属时沿用已有工作范围。`GET /workbench/members?review_status=REJECTED` 对有组织的红娘展示同组织弃海会员；其他状态仍沿用既有权限范围。

后端锁定会员、当前审核状态和归属，结束旧有效归属、建立当前红娘归属、清除驳回信息并写审计，在一个事务中提交。请求重复或会员已不是弃海状态时返回 `409`，例如 `{"detail":"该会员已被捞取或不在弃海状态"}`；不存在或不在范围返回 `404`；未登录 `401`；无红娘工作台权限 `403`；无效 ID 返回 `422`。客户端遇到 `409` 应刷新列表，不应重复提交。接口不直接通过公开资料审核。

| 键 | 值和含义 |
| --- | --- |
| `gender` | `male` / `female` |
| `ageRange` | 年龄整数 18–120；按生日和服务器日期计算 |
| `heightRange` | 身高整数 140–220 cm |
| `weight` | 体重整数 40–120 kg |
| `hometown`、`residence`、`household` | 空格分隔的省、市、区完整名称（如 `江苏省 南京市 鼓楼区`），按行政代码或旧文本匹配 |
| `education` | `highschool`、`college`、`bachelor`、`masters`、`doctor`；优先已认证学历，与卡片显示一致 |
| `marital` | `1` 未婚、`2` 离异（含历史细分）、`3` 丧偶 |
| `occupation` | 会员编辑页的预设职业原文，不接受“其他职业”自由文本 |
| `income` | 年收入 `under10`、`10-20`、`30-50`、`50-100`、`over100`；档位边界依次为 10、20、30、50、100 万元 |
| `mbti` | 16 种标准 MBTI 类型之一 |
| `housing`、`vehicle`、`ethnicity`、`smoking`、`drinking`、`religion` | 会员基础资料编辑页对应的选项原文 |
| `mine` | `1`，本人当前跟进会员 |

兼容旧调用方：`ageRange` 还接受 `under20`、`20-25`、`26-30`、`31-35`、`36-40`、`over40`；`heightRange` 还接受 `under160`、`160-169`、`170-179`、`over180`；`education` 还接受 `master`（硕士或博士）。条件对象的键可以省略或传空字符串表示不限，未知键即使为空也会被拒绝。

年龄、身高和体重支持自定义闭区间，格式为 `range:下限:上限`，例如 `{"heightRange":"range:160:175"}`；可只给一端，如 `range:160:` 或 `range::175`。年龄允许 18–120 岁、身高 140–220 cm、体重 30–150 kg；两端均省略、超出范围或下限大于上限返回 `422`。原有单值和固定档位仍兼容。

示例：`GET /api/v1/matchmaker/workbench/members?page=1&page_size=30&filters=%7B%22gender%22%3A%22female%22%7D`，携带 `Authorization: Bearer <token>`。成功示例：`{"items":[],"page":1,"page_size":30,"total":0,"has_more":false,"filter_version":1}`；非法示例 `filters={"gender":"unknown"}` 返回 `422` 和 `{"detail":"无效的筛选条件：gender"}`。未登录返回 `401`，无工作台权限返回 `403`。不支持的键、值或格式同样返回 `422`。收入“保密”与未填写都存为 NULL，不能区分，故不提供该条件。`filter_version=1` 表示服务器支持本筛选契约；旧服务器可能忽略未知参数，客户端选择条件时必须检查该字段。VIP 页签仍使用另一数据源，不支持这些筛选条件。

### 5.6 会员「申请认识」即红娘的申请牵线（2026-10-23 变更）

- 变更前：会员在首页点「申请认识」只写 `match_apply`，红娘工作台的牵线管理只写 `matchmaker_introduction`，两张表互不相通。会员自己发起的申请在任何红娘的牵线列表里都不存在，红娘看不到「有会员想认识谁」，也就无从介入撮合；而 `matchmaker_introduction` 里也不存在「待牵线」的产生入口（工作台手工添加的记录只会落 `SUCCEEDED`/`FAILED`）。
- 变更后：会员侧的申请认识即红娘口径的**申请牵线**，同步落 `matchmaker_introduction`，状态流为 `PENDING` 待牵线 → `IN_PROGRESS` 牵线中 → `SUCCEEDED` 牵线成功 / `FAILED` 牵线失败。
  - **落库（`POST /api/v1/discovery/applications/{target_id}`）**：申请写入的同事务内追加一条 `PENDING` 记录，跟进人按**申请人**的生效 `resource_assignment` 解析——谁发起申请就挂谁的服务红娘；申请人只归属到门店、没指定具体红娘时 `matchmaker_id` 用 `0` 占位（该列 `NOT NULL`），靠 `organization_id` 让该门店的超级红娘在工作台看到；申请人完全没有生效归属时回落到承接门店 `MEMBER_AUTO_ASSIGN_ORGANIZATION_ID`。申请人本人是 `service_matchmaker`、或既无归属又未配置承接门店时不生成记录（挂上去也没人看得见）。`note` 固定为 `discovery-apply:{申请 id}` 作幂等键，同一次申请不会因重试多出记录。
  - **推进（红娘端）**：小程序牵线卡片点「联系Ta」并成功取到联系方式后，若该记录仍是 `PENDING`，前端自动提交 `PATCH /api/v1/matchmaker/workbench/introductions/{id}/status`（`status=IN_PROGRESS`）并就地改这张卡片的徽标，不用红娘再点一次状态。看到联系方式即视为已开始撮合；读取失败或演示数据不推进。红娘仍可手动改任意状态。
  - **结果同步（`POST /api/v1/discovery/applications/{id}/accept|reject`）**：被认识方的决定就是这次撮合的结果——同意同步为 `SUCCEEDED`，拒绝同步为 `FAILED`（`failure_reason` 取会员填写的拒绝理由，为空回落「对方暂时婉拒了你的申请」，超 500 字截断）。**只改 `PENDING`/`IN_PROGRESS` 的行**：红娘手工判过的成功/失败是她对线下撮合过程的结论，不被会员事后决定改写；红娘手工录入的进行中记录同样会同步。
  - **超时同步**：`match_apply` 的 48 小时过期清扫（申请列表、申请详情等入口触发）在把申请置为 `status=3` 的同时，把这对会员仍在进行的牵线同步为 `FAILED`，理由「对方超时未回应」，牵线管理里不留永远撮合不成的进行中记录。
- 影响范围：`match_apply` 的状态码、返回结构、请求参数全部不变；变化是 `matchmaker_introduction` 多了会员侧写入方与同步路径，因此工作台的「待我牵线 / 牵线中 / 牵线成功」等计数（`GET /api/v1/matchmaker/workbench/dashboard`）会包含会员自发起的申请，`GET /api/v1/matchmaker/workbench/introductions` 会返回 `matchmaker_id=0` 的门店公海行（仅该门店 `level=SUPER` 的红娘可见，普通红娘按 `matchmaker_id` 过滤看不到）。表结构无变更（未加列、未加索引，复用 `note` 唯一约束语义）。

### 5.7 公开资料审核只对总店红娘开放（2026-10-27 变更）

`PATCH /api/v1/matchmaker/workbench/members/{member_id}/public-profile-review`，请求参数、返回体、状态码含义均不变，新增一个权限前置。

- **变更前**：只校验工作台准入（`service_matchmaker` 角色生效 + 有启用的工作台档案）和归属范围（`_member_scope_predicate`），因此 `level=NORMAL` 的普通服务红娘对挂在自己名下的会员同样能判「通过 / 不通过」。
- **变更后**：路由在范围校验之前先过 `app/services/matchmaker_workspace.py:require_review_authority`，`level != 'SUPER'` 直接返回 `403`，`detail` 为 `仅总店红娘可审核会员公开资料`。闸门只看 `matchmaker_workspace_profile.level`，不看 `organization_id`——即总店超级红娘（不挂门店，平台全部已归属会员）和门店超级红娘（本店范围）都可审核，两者仍受原有范围过滤约束，不互相越范围。
- **普通红娘不受影响的路径**：代会员编辑资料（`PATCH .../workbench/members/{id}/profile` 及其昵称/头像/相册/偏好等子接口）、录入会员（`POST /api/v1/matchmaker/workbench/members`，落 `PENDING`）、客源一键入库（`convert_workspace_lead` 的重复入库分支内部会重置为 `PENDING`，走服务层不调本路由，因此不会被这道 403 打断）。也就是说普通红娘仍能把资料改好并留在待审队列里，只是不能判定审核结论。
- **错误码**：`401` 未登录；`403` 非总店红娘（本次新增，工作台准入不满足时同样是 `403`，`detail` 不同）；`404` 会员不存在或不在当前工作范围；`422` `status` 非 `PASSED/REJECTED` 或 `REJECTED` 未带 `reason`。前端建议：`403` 直接提示 `detail`，不要重试。
- **前端同批改动**：小程序 `components/MatchmakerPendingReview.uvue` 读 `GET /api/v1/matchmaker/workbench/profile` 的 `level` 得出 `canReview`，普通红娘点卡片状态徽标只提示「仅总店红娘可审核会员资料」不再打开审核弹层，「更多」菜单里的「驳回资料」对普通红娘隐藏（菜单高度按四项计算，分隔线收在「修改红娘」上）。
- **影响范围**：仅该路由的权限语义；后台（`/api/v1/admin/...`）侧的会员资料审核入口是平台运营在用，不受本条约束。

### 5.8 会员的牵线记录（2026-10-27 变更，同时补全契约）

**基本信息**

- 用途：小程序「资料待审」卡片「更多 → 牵线(N)」子页，只读查看**某个会员名下**的全部牵线记录（红娘手工添加的 + 会员「申请认识」自动同步的）。
- URL：`GET /api/v1/matchmaker/workbench/members/{member_id}/match-history`
- Method：`GET`，无请求体。需要登录（C 端 `Authorization: Bearer <access_token>`），且账号必须是可进入工作台的服务红娘（`service_matchmaker` 角色生效 + 有启用的工作台档案）。`NORMAL` 与 `SUPER` 红娘都可读，本接口不做总店限制（总店限制只针对 §5.7 的审核动作）。
- 成功状态码 `200`，响应 `application/json`。

**请求参数**

| 参数 | 位置 | 类型 | 必填 | 默认 | 校验 | 含义 |
| --- | --- | --- | --- | --- | --- | --- |
| `member_id` | path | integer | 是 | 无 | `ge=1`，非正整数或 `0` 返回 `422` | 目标会员的 `users.id`，即资料待审卡片的 `user_id` |
| `page` | query | integer | 否 | `1` | `1-1000` | 页码，越界返回 `422` |
| `page_size` | query | integer | 否 | `20` | `1-100` | 每页条数，小程序固定传 `100` |

非法示例：`GET .../members/0/match-history` → `422`；`GET .../members/53/match-history?page_size=200` → `422`。

**请求示例**


**使用方法与业务规则**

- 前置条件：登录 + 工作台准入；会员必须在当前红娘的服务范围内（`resource_assignment` 有生效行），越范围与不存在的 ID 一样返回 `404`，不泄露资源是否存在。
- 调用顺序：先 `GET /api/v1/matchmaker/workbench/members` 拿到卡片和 `user_id`；打开卡片「更多」菜单时前端调本接口一次、只取 `total` 作为「牵线(N)」的 N（卡片已有 N 时不重复请求）；进入「牵线记录」子页再取 `items`。
- 页签与筛选：子页的「主动牵线/被动牵线」两个页签按 `direction` 在**前端本地**过滤，切换页签不再发请求；因此 N 是双向总数，页签内条数可能少于 N。
- 幂等与频率：只读、无副作用、可重复调用，不推进任何状态、不扣次数。
- 记录可见性：只要会员在服务范围内，TA 名下的牵线记录就全部可见，**包含其他红娘为 TA 牵的线**（与 §5.6 里 `GET /workbench/introductions` 按红娘/门店过滤的口径不同——那张列表看的是「我牵的线」，本接口看的是「这个会员的牵线历史」）。
- 后台补录的牵线：自 2026-10-27 起，运营在后台「牵线记录」新增或改状态时会同步一条 `matchmaker_introduction`（`note=admin-entry:{match_apply id}`），因此这类记录同样出现在本接口里；口径与影响见 `docs/api/m4-customer-lead-and-service.md` 4.5。后台列表本身仍只读 `match_apply`，所以红娘手工录入和会员申请认识产生的牵线不会反向出现在后台列表。
- 状态流转：本接口不参与流转，只展示 `matchmaker_introduction` 的当前状态；改状态仍走 `PATCH /api/v1/matchmaker/workbench/introductions/{id}/status`。
- 边界场景：对方注销或资料为空 → 昵称回落 `未命名会员`，记录仍然返回；记录超过 100 条 → `has_more=true`，小程序当前一次取 100 条、暂无翻页，需要更多时前端补分页。
- 兼容性：仅新增字段语义变化，见下方变更记录；旧客户端按整数解析 `status` 会显示成兜底文案「待牵线」，不会再出现「双方同意/已拒绝」。

**错误**

| HTTP | 触发条件 | 响应示例 | 前端处理建议 |
| --- | --- | --- | --- |
| `401` | 未登录或 Token 失效 | `{"detail":"Could not validate credentials"}` | 跳登录 |
| `403` | 登录者不是可进入工作台的服务红娘 | `{"detail":"<workspace_access 的 message>"}` | 直接提示 `detail` |
| `404` | 会员不存在，或不在当前红娘的服务范围 | `{"detail":"会员不存在或不在当前工作范围"}` | 提示后关闭子页并刷新列表 |
| `422` | `member_id` 非正整数、`page`/`page_size` 越界 | FastAPI 校验错误数组 | 检查请求参数 |

**变更记录（2026-10-27）**

- 变更前：数据源是 `match_apply`（只覆盖会员在首页点「申请认识」的记录），`status` 是 `0/1/2/3` 整数（待回应/双方同意/已拒绝/已关闭），返回字段为 `responded_at`，排序 `id DESC`。红娘在工作台手工添加的牵线一条都不在这里，待审会员的「牵线(N)」几乎恒为 `0`。
- 变更后：数据源改为 `matchmaker_introduction`（§5.6 起成为牵线记录的唯一事实表），`status` 改为 `PENDING/IN_PROGRESS/SUCCEEDED/FAILED` 字符串枚举，`responded_at` 改为 `updated_at`，排序改为 `created_at DESC, id DESC`；其余字段名与分页结构不变。
- 影响范围：本接口唯一调用方是小程序 `components/MatchmakerPendingReview.uvue`（牵线记录子页 + 菜单计数），同批已改状态文案与配色（待牵线灰、牵线中蓝、牵线成功绿、牵线失败红）、方向副文案改为「把本会员介绍给 TA / 把 TA 介绍给本会员」。`match_apply`、C 端「我的申请」和工作台牵线记录中心均未改动；表结构无变更。

## 6. 客源线索接口

所有接口使用 `Authorization: Bearer <access_token>`，未登录返回 `401`。线索状态为 `NEW`、`CONTACTED`、`INTENDED`、`CONVERTED`、`LOST`、`CLOSED`。

### 6.1 列表、统计、详情

`GET /api/v1/admin/customer-leads` 支持 `page` 1-1000、`page_size` 1-100、`status` 状态枚举、`source` 最多 64 字、`matchmaker_id` 正整数和 `search` 最多 64 字。返回 `items/page/page_size/total/has_more`，线索字段为 `id/name/real_name/phone/wechat/source/photo/gender/birthday/intention_level/status/matchmaker_id/organization_id/next_follow_at/converted_user_id/remark/created_by/created_at/updated_at`。

`GET /api/v1/admin/customer-leads/statistics` 无请求体，返回 `total/new_count/contacted_count/intended_count/converted_count/lost_count`；无数据返回全 0。`GET /api/v1/admin/customer-leads/{lead_id}` 返回单条线索，ID 必须为正整数，不存在返回 `404`。

### 6.2 新增和修改

`POST /api/v1/admin/customer-leads` body：`name` 1-128 字；`phone` **必填**，11 位大陆手机号（`^1[3-9]\d{9}$`）；`wechat` 最多 128 字（选填，仅备注，不能替代手机号）；`source` 1-64 字；`real_name` 最多 64 字、`photo` 最多 512 字、`birthday` `YYYY-MM-DD`、`gender` `0未知/1男/2女`（默认 0）、`intention_level` 枚举 `1/2/3`、`remark` 最多 2000 字，全部选填且逐项落库。线索必须能联系到人、且只有手机号能一键入库成会员，所以缺手机号返回 `422`（`必须登记 11 位手机号`）。成功 `201`，示例：`{"name":"李女士","phone":"13900001111","source":"offline_event","intention_level":2,"remark":"希望近期了解牵线服务"}`。2026-10-26 修复：该 INSERT 原先只给第一列生成占位符，除 `name` 外的字段都被 MySQL 按列默认值写入，现已逐列绑定（回归 `tests/test_customer_lead_create_columns.py`）。

`PATCH /api/v1/admin/customer-leads/{lead_id}` 支持部分更新 `name/real_name/phone/wechat/source/photo/birthday/intention_level/gender/status/remark/next_follow_at`，至少提供一个字段；状态值必须使用上述枚举。`phone` 要么不传，要么传有效的 11 位手机号：传 `null`/空串返回 `422`（`手机号不能清空，只能改成有效的 11 位手机号`）；表单预填的脱敏展示值（如 `139****0101`）按旧值豁免，服务端整键丢弃、等同未修改手机号。成功返回更新后的线索，非法状态或空 body 返回 `422`，不存在返回 `404`。更新不删除跟进历史。

### 6.3 跟进和分配

`GET/POST /api/v1/admin/customer-leads/{lead_id}/follow-ups` 查询或新增跟进记录。新增 body：`method` 枚举 `PHONE/WECHAT/VISIT/OTHER`；`content` 1-2000 字；`intention_level` 可选 `1/2/3`；`next_follow_at` 可选时间。新增成功 `201`，线索为 `NEW` 时自动变为 `CONTACTED`。查询支持 `page` 1-1000、`page_size` 1-100，返回记录数组，无数据返回 `[]`。

`PATCH /api/v1/admin/customer-leads/{lead_id}/assignment` 分配线索，body 的 `matchmaker_id` 和 `organization_id` 至少一个；红娘必须是有效服务红娘，门店必须存在且启用。返回更新后的线索；目标无效返回 `422`。所有新增、修改、分配操作写入后台审计日志。

### 6.4 一键入库

`POST /api/v1/admin/customer-leads/{lead_id}/convert` 用线索手机号生成正式会员账号（`users`，无微信 openid，验证码即可登录；同一行写入初始登录密码的 bcrypt 哈希，取自 `LEAD_CONVERT_INITIAL_PASSWORD`，默认 `abc123`，置空则不设密码），并写入公开资料待审（`matchmaker_member_review`=`PENDING`）、资源归属（`resource_assignment`，`source='lead_convert'`），把线索置为 `CONVERTED` 且回填 `converted_user_id`，归属同时写回线索。body 三个字段全部可选：`matchmaker_id`、`organization_id`（省略即沿用线索上已有的分派，两处都没有返回 `422` `请先选择归属红娘或门店`）、`gender`（省略即沿用线索性别）。返回 `{lead, user_id, review_status}`。已入库/已关闭/已弃海、以及没有手机号的线索返回 `409`；线索手机号不是有效 11 位大陆号码时返回 `422`（`手机号「{phone}」不是有效的 11 位号码，请先修正线索电话后再入库`，2026-10-19 新增，用于拦住批量导入之前留下的微信-only/占位号码，不生成登不进来的会员号）；线索手机号已经是某个会员的登录号时返回 `409`（`users.phone` 唯一），不会重复建号。下拉字典 `GET /api/v1/admin/customer-leads/options` 额外返回 `stores`（启用门店），供入库弹窗选择归属。完整字段表见 `docs/api/m4-customer-lead-and-service.md` 2.17。

### 6.5 红娘工作台客源列表 `GET /api/v1/matchmaker/workbench/leads`

红娘小程序工作台的「客源线索 / 已放弃线索」两档都读这一条接口（路由 `app/api/routes/matchmaker_workspace.py`，服务层 `list_workspace_leads`）。鉴权为 C 端用户 Token + 工作台准入，`query` 为 `page` 1-1000、`page_size` 1-100、`status`（`NEW|CONTACTED|INTENDED|CONVERTED|LOST|CLOSED`）、`search` 最多 64 字。

**返回参数**：`{items[], page, page_size, total, has_more}`，`items[]` 为 `WorkspaceLead`（字段名与后台侧 `CustomerLead` 一致，另带 `last_follow_up_at`）。

**新增字段**（2026-10-28，均可缺省）：

| 字段 | 类型 | 取值口径 |
| --- | --- | --- |
| `abandon_reason` | string \| null | 当前生效弃海记录（`customer_lead_abandonment.restored_at IS NULL`）的 `reason`；未弃海、或已恢复后为 `null` |
| `abandoned_at` | datetime \| null | 同上一条记录的弃海时点 |
| `creator_name` | string \| null | 录入人显示名，按 `customer_lead.created_by` 现拼（`matchmaker_workspace_profile.display_name` 优先，回落 `users.nickname`）；`created_by` 为空或该账号既无档案也无昵称时为 `null` |

取数在 `_LEAD_SELECT`（`app/services/matchmaker_workspace.py`）里用两层 `LEFT JOIN`：先按 `lead_id` 取 `MAX(id)` 的生效弃海流水，再回表取 `reason` 与 `abandoned_at`。同一条线索多次弃海-恢复最多只有一条生效记录，所以连接不放大行数（实测同一 `page_size=100` 条件下连接前后都是 21 行）。`_LEAD_SELECT` 同时服务列表（`list_workspace_leads`）和单条读取（`_require_scoped_lead`，即编辑/分派/跟进/入库的返回体），两处口径一致。

`creator_name` 与既有的 `matchmaker_name` 是同一套写法、两组独立连接：一组按 `l.matchmaker_id`（跟进红娘），一组按 `l.created_by`（录入人），各自 `LEFT JOIN matchmaker_workspace_profile`（带 `status = 1`）并回落 `users.nickname`，所以「档案被停用/没建过」的账号显示昵称，两者都没有时为 `null`。客源表上本来就一直在写 `created_by`（`create_workspace_lead` 把它和 `matchmaker_id` 一起填成当前红娘的 `actor.user_id`，所以「在哪个红娘账号名下录入的就归哪个红娘」原本就是写入规则），本次没有新增列，也没做数据回填。

**动作响应体的口径差异**：`POST /workbench/leads/{lead_id}/abandon` 返回的是弃海**前**读取的稳定副本（普通红娘弃海后不再拥有该客源，所以不能弃海后再读），这两字段恒为 `null`；`POST .../restore` 在事务提交后重读，此时 `restored_at` 已写、生效记录消失，同样为 `null`。小程序两端都不依赖动作响应渲染弃海信息，成功后重新拉列表。

**排序**：接口仍按 `l.id DESC` 返回，不做弃海时间排序。已放弃池的「最新弃海在最上」在小程序端本地实现（`pagesSub/matchmaker/become-matchmaker.uvue` 的 `workspaceVisibleLeads`），按 `abandoned_at` 字符串降序、相同时按 `id` 降序，空值沉底。

**捞取即换人（2026-10-28）**：`POST /api/v1/matchmaker/workbench/leads/{lead_id}/restore` 除了把 `status` 置回 `NEW`、把生效弃海流水写上 `restored_by/restored_at/restore_reason`，现在同一条 `UPDATE` 里把 `matchmaker_id`、`created_by` 和 `organization_id` 都改写成捞取人本人——谁捞回就在谁名下，卡片「录入人」显示捞取人，`GET .../workbench/leads` 的 `SELF` 范围（按 `matchmaker_id` 或本人弃海流水过滤）也据此判定。原来的登记人没有丢：弃海流水的 `abandoned_by` 和 `business_audit_log`（`matchmaker_workspace.lead.abandon` / `.restore`）都保留两条动作的历史。弃海动作仍只清 `matchmaker_id`、不动 `created_by`；后台侧 `POST /admin/customer-leads/{lead_id}/restore`（`docs/api/m4-customer-lead-and-service.md` 2.13）行为不变，不改归属。

**变更记录（2026-10-28）**

- 变更前：`WorkspaceLead` 不带弃海信息，弃海时填的原因只存在于 `customer_lead_abandonment`，只有后台 2.5/2.6 两个接口能查；小程序「已放弃线索」卡片只有「备注」行（显示的多是弃海前的跟进备注，弃海原因没有入口），且顺序按客源 id 倒序——早录入、晚弃海的客源会沉到底部。
- 变更后：所有走 `_LEAD_SELECT` 的响应多出 `abandon_reason`、`abandoned_at` 两个可选字段（默认 `null`，旧客户端忽略即可）；零 DDL，不加列、不加索引，只多两层 `LEFT JOIN`。

## 8. VIP 与行为查询

`GET /api/v1/admin/members/vip` 需要登录，支持 `page` 1-1000 默认 1、`page_size` 1-100 默认 20、`expiring_within_days` 1-3650 和 `search` 最多 64 字。只返回当前有效 VIP；返回 `items/page/page_size/total/has_more`，item 字段为 `membership_id/user_id/nickname/phone/package_type/amount/order_no/start_at/end_at/status`。无数据返回 `items: []`。本期不提供绕过支付订单直接开通、续期或取消 VIP 的接口。

`GET /api/v1/admin/members/{member_id}/behavior/login-logs` 需要登录，path ID 必须为正整数，query 分页规则同上。返回登录日志分页对象，item 字段为 `id/user_id/nickname/login_status/ip/device_id/platform/failure_reason/created_at`；`login_status` 为 `1` 成功、`2` 失败。无日志返回 `items: []`，不存在用户或无权限返回 `404/401`。IP、设备和失败原因仅供后台风险排查，不得回传到 C 端。

`PATCH /api/v1/admin/members/{member_id}/vip` 管理 VIP，body：`action` 为 `OPEN/RENEW/CANCEL`；`OPEN/RENEW` 必须提供 `package_type` 和 `order_no`；`CANCEL` 必须提供 `reason`。开通/续期时，服务端会锁定并校验该会员的已支付会员订单（订单类型为会员、状态为已支付、套餐匹配），订单已处理时幂等返回原会员记录；没有有效订单返回 `409`，不会直接创建虚假支付或账本流水。续期从当前有效 VIP 到期时间开始计算。

## 12. 个人余额支付会员

会员用户先调用 `POST /api/v1/membership/orders` 创建会员订单，再调用 `POST /api/v1/membership/orders/{order_no}/pay-with-balance` 使用个人可用余额支付。Header 必须携带 `Authorization: Bearer <user-token>` 和 `Idempotency-Key`（8-128 位）。接口仅允许支付当前用户自己的会员订单，订单必须未支付且未过期。

成功返回 `MembershipOrderResponse`：`order_no`、`package_code`、`product_name`、`amount`、`status=1`、`expire_at`、`payment_required=false`；支付方式在服务端记录为余额。余额不足返回 `409`，订单不存在返回 `404`，订单已支付/已关闭/已过期返回 `409`。接口在事务内锁定订单和用户账本，按 `CREDIT - DEBIT` 计算可用余额，写入 `membership_order` 扣款流水和会员权益；同一订单重复请求幂等返回已支付结果，不重复扣款。

示例：

```http
POST /api/v1/membership/orders/VIP20260807123456ABC/pay-with-balance
Authorization: Bearer <user-token>
Idempotency-Key: vip-balance-pay-001
```

余额支付不会伪造微信支付回调；退款应通过财务退款流程冲正订单和账本。个人余额来源仍需通过已实现的分成、退款冲正或其他合法账本入账流程产生。

用户端 `/matchmakers`、`/matchmaker/service-products` 继续保持原有行为，供 C 端使用；本文件新增的管理查询即使业务字段复用，也使用 `/admin/matchmaker/*` 路径并单独鉴权。后台账号与用户账号不是同一主体，`matchmaker_user_id` 仅用于后续绑定业务数据，不作为登录凭据。涉及账号发放、权限扩展、账号停用和审计日志时，应通过受控后台或数据库运维流程完成，暂不提供公开注册接口。

`avatar` 只读回显，保存走会员侧头像接口；`success_cases` 最多 3 条，每条最多 3 张图，图片为 `/storage/...` 相对路径，由展示侧补全。未找到本人的入驻申请行时返回 `404`，`detail` 为「未找到红娘入驻档案，暂不能编辑主页」。

### 13.2 保存主页资料

`PATCH /api/v1/matchmaker/workbench/homepage`，需要登录，成功 `200` 返回保存后的完整 `MatchmakerHomepage`，请求体为增量字段（只提交改过的键，未出现的字段不动）。

| 字段 | 类型 | 规则 | 落库位置 |
| --- | --- | --- | --- |
| `nickname` | string | 1~64 字，去首尾空白 | `users.nickname` |
| `slogan` | string\|null | ≤64 字；传空串表示清空（存 `NULL`） | `user_matchmaker_apply.slogan` |
| `specialties` | string[] | ≤5 项，去空白去重，重复报「擅长领域不能重复」；传 `[]` 清空 | `user_matchmaker_apply.application_details.specialties` |
| `introduction` | string | 10~2000 字 | `user_matchmaker_apply.intro` |
| `success_cases` | object[] | ≤3 条；`description` 1~50 字，`images` ≤3 项，空图项自动丢弃 | `user_matchmaker_apply.application_details.success_cases` |

- `application_details` 是审核资料共用的 JSON 列，保存时只覆盖 `specialties`/`success_cases` 两个键，`wechat`、`expected_price`、`avatar` 等原有键原样保留。
- `slogan` 上限取 64 字（而不是申请表的 128），是为了让红娘档案列 `matchmaker_profile.slogan`（varchar 64）与主页同时可写，不出现超长截断。
- 头像不进这个 PATCH：会员侧 `POST /api/v1/users/me/avatar` 上传成功即写 `users.avatar`，公开主页同步生效。案例图片复用 `POST /api/v1/matchmaker/workbench/leads/photo`，只返回 `{url, thumbnail_url, size}`，不挂任何业务记录。
- 保存前对申请行 `SELECT ... FOR UPDATE`，写审计动作 `matchmaker_workspace.homepage.update`（对象类型 `user_matchmaker_apply`），同一请求内一次提交。重复提交相同内容不会有额外副作用，落库值与首次一致。

## 19. 小程序「红娘喜讯」中心接后台喜讯内容域（2026-10-27 新增，同日补红娘端报喜写入）

- 变更前：小程序「红娘管理中心 → 服务导航 → 红娘喜讯」的工作区内容全部来自 `mock/matchmaker.uts` 的 `mockMatchmakerNews` / `mockMatchmakerNewsBanners`，与后台「运营工具-喜讯管理」写进 `admin_content_item(domain=good_news)` 的真实记录毫无关系——运营在后台录了喜讯，红娘在小程序里看到的仍是那几条演示数据，反之红娘也看不到任何真实喜讯。锦旗同理（`domain=good_news_pennant`）。
- 变更后：新增两个只读接口，数据源就是后台那两张内容域，**不新建表、零 DDL**，后台录一条红娘这边就能看到一条。范围口径与其它工作台中心一致（`SUPER` 看全部、`NORMAL` 只看自己名下），公开开关沿用后台的 `extra.public`（后台保存时已映射成行级 `status`，`2` 即不公开）。同日补上红娘端「报喜-反馈喜讯」写入（19.4），写入的行同样落 `status=2`，因此读接口的行级过滤按范围分档：`NORMAL` 为 `status IN (1, 2)`（配合归属条件，她只会看到自己代报的待审行）、`SUPER` 为 `status = 1 OR extra.matchmaker_id = 本人`（总店看全部公开行，再加上自己代报的待审行；这里的归属只认 `extra.matchmaker_id`，不用 `created_by`——后台写入时那一列存的是管理员 ID，与 C 端 `user_id` 同号段，用它放行会把后台标为不公开的别人的行漏出来），返回体用 `pending_review` 标出未放行行。字段解析约定：`stage` 取 `extra.status`（中文文案，与后台栏目配置的 8 个分类同名）、正文 `extra.content_html` 剥 HTML 标签并按纯文本返回、`extra.meet_duration` 为纯数字时补「个月」单位、双方昵称头像按 `extra.from_user_id/to_user_id` 回查 `users`。
- **后台表单当前的取数现状（前端必须按此兜底）**：`xuanshiai-admin` 的喜讯抽屉只写 `feedback_name` / `partner_name` 两个姓名文本，「库中会员 / 自定义」单选是装饰性的，从不提交会员 ID；也不写 `images` / `blessing_count`。因此后台录入的行上 `from_user_id`、`to_user_id` 为 `null`，`from_name`/`to_name` 回落姓名文本，`from_avatar`/`to_avatar` 为 `null`，`images` 回落行级 `image_url` 的单张图，`blessing_count` 为 `0`。这些键接口已支持，等后台把会员选择器接上或开放红娘端报喜写入后即自动生效，前端不需要改契约。
- 归属可见性：普通红娘按 `extra.matchmaker_id` 过滤，后台录喜讯时可以不选服务红娘，这类**无归属行只有总店（`SUPER`）看得见**；锦旗墙没有 ID 列，受赠人是 `extra.target` 姓名文本，所以普通红娘按本人工作台显示名精确匹配，红娘改名即失配（要彻底解决需给锦旗补 `target_matchmaker_id`，本轮未做）。

### 19.4 红娘端「报喜 - 反馈喜讯」写入（2026-10-27 同日新增）

**基本信息**

- 用途：小程序「红娘喜讯」右下角「报喜」悬浮键 → 面板里的「反馈喜讯」表单，红娘代会员登记喜讯。
- URL：`POST /api/v1/matchmaker/workbench/good-news`，`application/json`。
- 鉴权：C 端 `Authorization: Bearer <access_token>` + 工作台准入（`require_workspace`），`NORMAL`/`SUPER` 都可提交。成功状态码 `201`。
- 图片先单独上传：`POST /api/v1/matchmaker/workbench/good-news/photo`，`multipart/form-data`、字段名 `file`、限 5 MB，落 `storage/uploads/good-news/`，返回 `{url, thumbnail_url, size}`。`url` 是服务端相对路径，入库存它，展示时由前端拼域名。

**请求参数**

| 参数 | 位置 | 类型 | 必填 | 校验 | 含义 |
| --- | --- | --- | --- | --- | --- |
| `stage` | body | string | 是 | `1-20` 字符 | 当前状态，取栏目配置的喜讯分类中文文案；小程序的选择器给的是除「锦旗飘扬」之外的 7 档 |
| `partner_name` | body | string | 是 | `1-40` 字符 | 对方称呼，去空格后不能为空 |
| `meet_duration` | body | string | 否 | `<=20` 字符 | 相识时间；填纯数字时读接口会补成「N个月」 |
| `content` | body | string | 否 | `<=1000` 字符 | 情感状态描述与对服务的反馈，按纯文本存进 `extra.content_html` |
| `images` | body | array<string> | 否 | 最多 9 项 | 已上传图片的相对路径，空串会被丢掉 |

**落库口径**：插一条 `admin_content_item`——`tenant_id=1`、`domain=good_news`、`title=stage`、`subtitle=红娘显示名`、`image_url=images[0]`、`status=2`、`sort=0`、`created_by=`红娘 `user_id`，`extra_json` 为 `{status, partner_name, matchmaker_id(字符串), matchmaker_name, meet_duration, content_html, images, blessing_count: 0, source: "matchmaker_workspace"}`。

- 不写 `feedback_name` / `from_user_id`：表单按用户确认的口径只有「对方称呼」一个姓名字段，所以卡片左侧不渲染，只显示右侧的对方称呼（读接口对无名一侧给占位串，前端按空处理）。
- 不写 `public`：可见性只由行级 `status` 决定。后台「运营工具-喜讯管理」把这条的 `status` 改回 `1` 即放行。放行前只有提交人自己看得到（19.1 里 `SELF` 放宽到 `status IN (1, 2)`、`SUPER` 用 `status = 1 OR extra.matchmaker_id = 本人`），她的卡片上带 `pending_review`；别人的待审行对总店也是隐藏的。

**返回参数**：`{ "id": <admin_content_item.id>, "pending_review": true }`。

**错误契约**：`401` 未登录；`403` 无工作台准入；`422` 字段越界，或 `stage` / `partner_name` 去空格后为空（`detail` 为「当前状态与对方称呼都要填写」）。

**边界**：一次提交插一行，不做重复检测（同一对会员连报两次会有两行）；本轮没有开红娘端改/删自己代报行的入口，撤回只能后台删记录。

**回归测试**：`tests/test_matchmaker_workbench_good_news.py` 新增写入 3 例（待审行与 `extra` 字段、空姓名 `422` 且不落库、`SELF` 放宽到 `status IN (1, 2)` 而 `SUPER` 用 `status = 1 OR extra.matchmaker_id = 本人`）；总店读域一例同时断言归属条件不出现在 `AND` 上，即公开行不因归属被收窄。

## 20. 红娘工作台 · 分成明细（2026-10-28 新增）

小程序「数据看板 - 分成明细」与「我的收益 - 分成明细」原来只有本地演示行，会员名和事件名都是编的。本轮补一个只读接口，直接回带真实订单里的消费会员与分成规则，合计口径与工作台概览的「线上分成」一致。

- URL：`GET /api/v1/matchmaker/workbench/commission-entries`
- 鉴权：普通会员 token（与工作台其它接口相同），需通过 `require_workspace` 准入门槛。
- 请求参数：`page` 1-1000（默认 1）、`page_size` 1-100（默认 20）。
- 排序：`created_at DESC, id DESC`。
- 可见范围：只返回 `beneficiary_type='service_matchmaker'` 且 `beneficiary_id=当前登录用户` 的分成行，即「我本人的线上分成」，不随总店/门店级别扩大。

**响应**

```json
{
  "items": [
    {
      "id": 1024,
      "created_at": "2026-10-22T10:12:00",
      "consumer_id": 53,
      "consumer_name": "小鹿",
      "consumer_avatar": "/storage/uploads/53/avatar-example.webp",
      "event_name": "VIP会员-季度开通",
      "order_no": "PO202610220001",
      "base_amount": "1980.00",
      "amount": "297.00",
      "status": "AVAILABLE"
    }
  ],
  "page": 1,
  "page_size": 20,
  "total": 1,
  "has_more": false,
  "total_amount": "297.00"
}
```

字段说明：

- `consumer_*` 由 `payment_order.user_id -> users.nickname/avatar` 回带；订单缺失（后台手工录入）时 `consumer_id=0`、`consumer_name` 为「未知会员」、`consumer_avatar=null`。
- `event_name` 取 `commission_rule.name`，规则未关联或被删时退回订单 `product_name`，两者都空时给「服务分成」。
- `base_amount` / `amount` 为两位小数字符串；`amount` 可能为负（退款冲正行）。
- `status`：`PENDING` 待入账 / `AVAILABLE` 已入账 / `FROZEN` 冻结 / `REVERSED` 已冲正。
- `total_amount`：本人全部非冲正分成之和，与 `GET /workbench/dashboard` 的 `online_commission` 同一条件（`status <> 'REVERSED'`），两处金额一致；分页参数不影响该值。

**前端接入**：`api/matchmaker.uts#getMatchmakerWorkspaceCommissionEntries()` 把行映射成 `{time,name,avatar,item,amount,status,statusLabel,orderNo}`，头像走 `resolveMediaUrl`，金额显示为 `+￥297.00` / `-￥297.00`。进入「线上分成」时加载，加载中/失败/空各有状态块，资金结算卡用 `total_amount`。本机（`API_BASE_URL` 含 `127.0.0.1`）且服务端无记录时回退演示行并显示「本地测试数据」，部署环境不回退。

**边界**：只读，无写操作；与后台 `GET /api/v1/admin/finance/commission-entries` 相比只服务当前红娘本人，多返回 `consumer_name/consumer_avatar/event_name` 三个展示字段。财务明细（线下业绩）的数据源见 §21。

**变更记录（2026-10-28）**

- 新增上述只读接口，无 DDL、无存量数据迁移。
- 小程序「分成明细」由 `mock` 演示行切换为本接口；「分成标准」与「财务明细」不变。其中「财务明细」已于同日接入 §21。

## 21. 红娘工作台 · 线下业绩明细（2026-10-28 新增）

小程序「数据看板 - 财务明细」原来只有本地演示行。本轮补一个只读接口，返回**本人作为销售红娘的线下 VIP 已收款订单**，与后台「工作汇报 - 线下业绩」、组织报表的 `offline_performance` 使用同一口径；工作台概览里硬编码为 `"0"` 的「线下业绩」指标同步改为真实求和。

**基本信息**

- 用途：小程序「数据看板 - 财务明细 - 财务明细」逐笔列表与资金结算卡。
- URL：`GET /api/v1/matchmaker/workbench/offline-income`
- Method：`GET`，无请求体；`Content-Type` 无要求，响应 `application/json`。
- 鉴权：C 端 `Authorization: Bearer <access_token>`，并通过 `require_workspace` 工作台准入（`NORMAL` / `SUPER` 均可）。成功 `200`。

**请求参数**

| 参数 | 位置 | 类型 | 必填 | 默认 | 校验 | 含义 |
| --- | --- | --- | --- | --- | --- | --- |
| `page` | query | integer | 否 | 1 | `1 ~ 1000` | 页码，越界返回 `422` |
| `page_size` | query | integer | 否 | 20 | `1 ~ 100` | 每页条数，越界返回 `422` |

**请求示例**

```http
GET /api/v1/matchmaker/workbench/offline-income?page=1&page_size=20
Authorization: Bearer <access_token>
```

非法示例：`page=0`、`page_size=101` → `422`；未带 Token → `401`；非工作台账号 → `403`。

**返回参数**

| 字段 | 类型 | 必返 | 空值含义 | 业务含义 |
| --- | --- | --- | --- | --- |
| `items[].id` | integer | 是 | 无 | `payment_order.id` |
| `items[].paid_at` | string(date-time) | 是 | 无 | 支付时间；`pay_time` 为空时回落订单 `created_at` |
| `items[].consumer_id` | integer | 是 | `0`＝订单无会员 | 消费会员 `users.id` |
| `items[].consumer_name` | string | 是 | 回落「会员#<id>」，无 id 时「未知会员」 | 消费会员昵称 |
| `items[].consumer_avatar` | string/null | 是 | `null`＝未上传头像 | 会员头像相对路径，前端拼域名 |
| `items[].item_name` | string | 是 | 回落「线下VIP服务」 | 订单商品名 `product_name`，即套餐名 |
| `items[].order_no` | string/null | 是 | `null`＝订单无编号 | 支付订单号 |
| `items[].amount` | string | 是 | 无 | 订单实收金额，两位小数字符串 |
| `page` | integer | 是 | 无 | 当前页码（原样回显） |
| `page_size` | integer | 是 | 无 | 每页条数（原样回显） |
| `total` | integer | 是 | 无 | 符合条件的总条数 |
| `has_more` | boolean | 是 | 无 | `page * page_size < total` |
| `total_amount` | string | 是 | 无 | 本人全部线下业绩之和，两位小数字符串；不受分页影响 |

**返回示例**

```json
{
  "items": [
    {
      "id": 88,
      "paid_at": "2026-10-22T14:20:00",
      "consumer_id": 53,
      "consumer_name": "小鹿",
      "consumer_avatar": "/storage/uploads/53/avatar-example.webp",
      "item_name": "线下VIP · 季度服务",
      "order_no": "PO202610220009",
      "amount": "1200.00"
    }
  ],
  "page": 1,
  "page_size": 20,
  "total": 1,
  "has_more": false,
  "total_amount": "1200.00"
}
```

无数据时：

```json
{"items": [], "page": 1, "page_size": 20, "total": 0, "has_more": false, "total_amount": "0.00"}
```

**使用方法与业务规则**

- 取数条件：`payment_order.matchmaker_id = 本人 user_id AND status = 1 AND product_type = 'offline_vip'`，排序 `paid_at DESC, id DESC`。
- 口径与后台一致：后台 `matchmaker_staff_admin.work_report.offline_income` 与 `organization_admin` 的 `offline_performance` 用同一组条件求和，因此三处金额应相等；`GET /workbench/dashboard` 的 `offline_performance` 指标本轮同步改为真实值（此前硬编码 `"0"`）。
- 只读、幂等、可重复调用；`total_amount` 分页不变。退款不在此接口处理：订单退款后 `status` 不再为 `1`，该笔自然从明细与合计中消失。
- 会员姓名/头像按订单 `user_id` 回带；订单缺失会员或会员删号时按上表兜底，不会 `500`。
- 错误：`401` 未登录；`403` 非工作台账号；`422` 分页参数越界。

**前端接入**：`api/matchmaker.uts#getMatchmakerWorkspaceOfflineIncome()` 把行映射为 `{time,name,avatar,item,amount}`，头像走 `resolveMediaUrl`、缺图时页面显示姓名首字；金额显示 `+￥1,200.00`。进入「财务明细」时加载，加载中/失败/空各有状态块，资金结算卡用 `total_amount`。本机（`API_BASE_URL` 含 `127.0.0.1`）且服务端无记录时回退演示行并显示「本地测试数据」，部署环境不回退。

**变更记录（2026-10-28）**

- 新增 `GET /api/v1/matchmaker/workbench/offline-income`，无 DDL、无存量数据迁移。
- `GET /api/v1/matchmaker/workbench/dashboard` 响应中 `offline_performance` 的取值由固定 `"0"` 改为本人线下 VIP 已收款订单金额之和（两位小数字符串），字段名与类型不变，向后兼容。
- 小程序「财务明细」由 `mock` 演示行切换为本接口；「结算说明」页签文案同步去掉「本地演示数据」表述（改为只说明结算口径，数据来源由逐笔页签的演示提示控制）。
- 回归测试：`tests/test_matchmaker_workspace_offline_income.py`（范围条件与回带字段 1 例 + 缺失订单字段兜底 1 例）+ `tests/test_matchmaker_workspace_contracts.py` 路径注册断言。

## 22. 红娘工作台 · 身份徽标接口与角色名称口径（2026-10-28 新增）

小程序「我的账号」页头部的角色徽标此前写死为「服务红娘」，不随账号实际角色变化；「管理中心」欢迎卡的角色虽然来自服务端，但对 `SUPER` 一律显示「超级服务红娘」，与后台「总店-超级红娘」的说法不一致。本轮补一个只读身份接口，并把两处的角色文案收敛到同一个函数。

**基本信息**

- 用途：小程序「红娘管理中心 - 我的账号」页头角色徽标；后台如需只取红娘身份也可复用。
- URL：`GET /api/v1/matchmaker/workbench/identity`
- Method：`GET`，无请求体，无查询参数。成功 `200`。
- 鉴权：C 端 `Authorization: Bearer <access_token>`，并通过 `require_workspace` 工作台准入（`NORMAL` / `SUPER` 均可）。

**返回参数**

| 字段 | 类型 | 必返 | 空值含义 | 业务含义 |
| --- | --- | --- | --- | --- |
| `greeting` | string | 是 | 无 | 问候语，固定「你好」（与首页概览一致） |
| `name` | string | 是 | 无 | 红娘显示名：工作台档案 `display_name` → `users.nickname` → 「服务红娘」 |
| `role_name` | string | 是 | 无 | 角色徽标文案，见下方口径表 |
| `avatar` | string/null | 是 | `null`＝未上传头像 | 头像相对路径（`users.avatar`），前端拼域名 |

**角色名称口径**

| 工作台档案 | 门店绑定 | `role_name` | 数据范围（`_scope_predicate`） |
| --- | --- | --- | --- |
| `level='SUPER'` | 未绑定（`organization_id IS NULL`） | 总店超级红娘 | 平台全部 |
| `level='SUPER'` | 已绑定门店 | 门店超级红娘 | 该门店 |
| `level='NORMAL'` | 任意 | 服务红娘 | 自己名下 |

**返回示例**

```json
{
  "greeting": "你好",
  "name": "红娘测试账号",
  "role_name": "总店超级红娘",
  "avatar": null
}
```

**使用方法与业务规则**

- 只读、幂等、无副作用。服务层 `workspace_identity(actor)` 与首页概览的 `identity` 共用同一个构造，两处角色文案不会再分叉。
- 角色判定只看 `matchmaker_workspace_profile.level` + `organization_id`（`status=1` 的那行），与数据范围完全同源；后台「红娘管理」的角色下拉通过 §16 的建档/编辑链路写 `level`，改完即在此生效。
- 错误契约：未登录 `401`；账号不是可进工作台的服务红娘 `403`（与其它工作台中心同语义）。

**前端接入**：`api/matchmaker.uts#getMatchmakerWorkspaceIdentity()` 映射为 `{greeting,name,roleName,avatar}`；`pagesSub/matchmaker/my-account.uvue` 在 `onLoad` 时拉一次，徽标文本取 `role_name`，请求失败时退回「服务红娘」，不阻塞页面其它内容。

**变更记录（2026-10-28）**

- 新增 `GET /api/v1/matchmaker/workbench/identity`，无 DDL、无存量数据迁移。
- `GET /api/v1/matchmaker/management-center/dashboard` 与后台 2.20「预览前台」响应中的 `identity.role_name`：`SUPER` 由「超级服务红娘」改为「总店超级红娘」（挂门店的改为「门店超级红娘」），`NORMAL` 仍为「服务红娘」。字段名、类型、状态码不变，只是取值文案变化；后台预览抽屉与小程序欢迎卡展示的是服务端原样文本，无需改代码。
- 小程序「我的账号」页头徽标由写死的「服务红娘」改为读取本接口的 `role_name`。
- 回归测试：`tests/test_matchmaker_workspace_contracts.py` 新增角色口径 1 例（总店/门店/普通三态 + 身份模型字段），并在路径注册断言中加入本接口。
