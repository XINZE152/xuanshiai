## 二、逐项核查证据

### 1. 系统配置（finance 配置域）—— 只存未消费

- 全后端 `get_runtime_value(...)` 运行时读取点仍只有 `platform_permissions` 的 8 处配额键（discovery/community），**无任何对 `finance` 命名空间的读取**。
- 支付/提现等真实开关实际来源：
  - 支付渠道：`core/config.py settings.wechat_payment_mode = "mock" | "real"`（环境变量），`is_test_mode` 校验 mock 组合；
  - 提现开关/最低额、退款人工审核、自由收款、电子合同：代码中无开关判断。
- 因此本页修改仅落入 `admin_config_snapshot`（含审计日志），属“管理存档”，不会让提现立刻放开或关闭。

### 2. 收入明细 —— 真实表 ✅

- 写入方：`services/payments.py`（VIP/爆灯/置顶）、`services/membership.py`（会员套餐）、`services/matchmaker.py`（红娘服务订单）均 `INSERT payment_order`。
- 后台：`admin_list_orders` 直查 `payment_order`，本次补充 `start_time/end_time` 过滤。**页面显示即真实订单。**

### 3. 资金流水 —— 真实表 ✅

- 写入方：分成结算、分成释放、提现（DEBIT 冻结）、提现驳回（CREDIT 回补）、退款（DEBIT 冲正）均写 `account_ledger`，且带 `idempotency_key` 防重。
- 后台：`admin_list_ledger` 直查，本次补时间过滤。

### 4. 余额提现 —— 真实表 + 审核链路 ✅

- 申请：`request_withdrawal` 校验可用余额后插入 `withdrawal_request` 并冻结账本（DEBIT AVAILABLE）。
- 审核：`review_withdrawal` 状态机 `PENDING_REVIEW→APPROVED/REJECTED→PROCESSING→SUCCEEDED/FAILED`；驳回/失败自动回补余额。
- 本次前端 Tab（全部/待审核/已完成/已驳回）映射 `status` 查询参数，搜索键对齐。**审核动作真实影响账本。**

### 5. 统计报表 —— 新增真实聚合 ✅

- 新增 `admin_revenue_daily_report`：`GROUP BY DATE(pay_time)`，`status=1` 计收入（笔数/金额），`status=3` 计退款（笔数/金额），可选 `start_date/end_date`。
- 前端 finance-statistic 已接该接口。数据实时来源于订单表，非 mock。

## 三、问题与建议（按优先级）

| 级别 | 事项 | 建议 |
|---|---|---|
| P0 | 提现开关/最低额不生效 | 在 `request_withdrawal` 增加读取 `finance.withdrawal`：`enabled=false` 时拒绝申请，金额低于 `min_amount` 时拒绝；余额提现菜单才真正受系统配置控制 |
| P0 | 退款人工审核不生效 | `refund_order` 增加读取 `finance.refund.manual_review`：开启时后台审核通过才冲正，关闭时回调直接处理 |
| P1 | 支付模式两套源 | 统一：以 `settings.wechat_payment_mode` 为权威或将配置域 `payment_mode` 纳入运行时校验（mock 环境仅允许沙箱回调）；避免“后台显示正式、环境仍 mock” |
| P1 | 自由收款/电子合同开关 | 这两个能力当前无业务模块，属预埋配置；待模块落地时读取 `free_payment.enabled` / `e_contract.enabled` |
| P2 | 合同 4 页 | 待接入电子签服务商后建真实表/路由，再替换占位 |
