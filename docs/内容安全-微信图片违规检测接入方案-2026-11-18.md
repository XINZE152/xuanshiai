- 文档版本：1.1.0
- 日期：2026-11-18
- 任务标识：`CONTENT-SEC-20261118`（新增于 `docs/待完成事项.md`）
- 状态：**方案定稿，未改代码**。本轮仅产出方案与决策记录，实施需用户另行批准。
- v1.1.0 变更：新增 §1.1「提审合规性结论」（微信官方明文判定：未接入官方内容安全检测接口将无法通过代码审核）；据此把 Phase 1/2 升为**提审阻塞项**；新增「昵称检测」P0 缺口（`profile.py:863` 原本完全不过滤）；§5.5 扩展为全场景文本覆盖。
- 适用范围：微信小程序端用户上传媒体（头像 / 相册 / 背景墙 / 社区配图）与社区文本的内容安全检测。

## 一、结论摘要

1. **后端当前对用户上传图片没有任何自动违规检测。** 现有的「审核」全部是**文本敏感词**或**人工队列**，图片类违规图可直接上传并立即对外展示。
2. **微信小程序确实提供该能力**（`imgSecCheck` / `mediaCheckAsync` / `msgSecCheck`），且是平台强制合规要求——人工初审只能作为补充，不能替代官方接口。本方案改为对接微信官方接口，不自建图片模型。
3. **基础设施已现成**：后端已有带缓存的微信 `access_token` 获取能力与 `users.openid`，可直接满足微信内容安全接口的强制参数要求，无需新建 token 体系。
4. **已定决策（2026-11-18，用户确认）**：
   - 覆盖范围：**全部上传媒体 + 社区内容**
   - 服务不可用兜底：**转人工审核**（不拒绝、不放行）
   - 展示时机：**检测通过才生效**（未过审不对外展示）
   - 实施节奏：**先不改代码**，方案先行
5. **接口选型建议**：Phase 1 用 `imgSecCheck`（同步返回，改动集中、无需消息服务器）；`mediaCheckAsync` 列为 Phase 3（需新建消息推送服务器）。
6. **提审合规性（新增，见 §1.1）**：微信官方明确「未接入官方内容安全检测接口的小程序将无法通过代码审核」。因此本方案不是合规优化项，而是**提审阻塞项**，Phase 1 与 Phase 2 须合并为提审前必做。

### 1.1 提审合规性结论（2026-11-18 核查官方规范）

**结论：社区帖子无官方内容安全检测，提审驳回风险高，且不是「可能」而是官方明文判定。**

#### 官方依据

| # | 出处 | 原文要点 |
| --- | --- | --- |
| ① | 微信服务市场官方置顶《关于微信小程序部分类目报备审核说明》 | 「为辅助小程序顺利通过报备审核，**代码审核环节会针对小程序的安全保障能力进行敏感类关键词检测，未接入官方"内容安全检测接口"的小程序将无法通过代码审核**。」 |
| ② | 微信运营专员常见驳回话术 | 「【发布】功能在进行内容安全验证时，存在信息安全风险，请尽快完善内容机制：**1、确保已接入内容安全API并要求所调用API可在小程序内任意发布的场景生效**；2、小程序内检测结果安全说明仅需提示用户所发布内容含违规信息即可」 |
| ③ | 同 ① | 「提供UGC自定义发布内容功能的小程序，需要在小程序内接入官方"内容安全检测接口"校验用户输入的文本/图片……用户自定义发布的内容包括：**昵称/花名、个人资料签名/日志/聊天/评论、头像/表情/相片、直播**等各种场景……**接入微信公众平台内容安全API（imgSecCheck、msgSecCheck、mediaCheckAsync）能力，以及通过其他技术或人工审核手段做好内容审核**」 |

关键解读：

- ① 表明这是**机器审核环节**（关键词检测），不是人工抽查，结论前置、可预期。
- ② 的「**在任意发布的场景生效**」意味着审核员会抽查**多个**发布入口，只覆盖部分场景（哪怕社区发帖已覆盖）仍可能被判定不达标。
- ③ 括号内并列要求「官方接口 **以及** 人工审核」——二者是**并列**关系，人工审核不能替代官方接口（与本方案 §4 一致）。
- 社区/论坛属 UGC 类目，须补选「社交-社区/论坛」类目并完成**网信办报备**（7 个自然日周期，首次提审需移交报备）。报备前官方准备清单即要求接入上述三个接口。
- 上线后仍会巡检：「若小程序发布后出现UGC内容安全违规问题，也将按平台规则进行处置」。

#### 后端现状 vs 微信要求（逐项对照）

| 微信要求 | 后端现状 | 达标 |
| --- | --- | --- |
| 接入官方内容安全接口（文本） | 仅本地词库 `config_sensitive_word`；外部文本接口是阿里云**云市场第三方**（`aliyun_content_moderation.py`）且 `.env.example:216` `ALIYUN_CONTENT_MODERATION_ENABLED=false` **默认关闭** | ❌ 非官方接口且默认关 |

| 违规提示文案 | ✅ 422「动态内容含高风险违规词，请修改后重试」 | ✅ |

**判定：现状满足微信要求的「人工审核 + 举报 + 提示」三要件，但完全空缺「官方接口」这一机器审核门槛项。**

#### 新增发现：昵称是漏网入口（本次核查新发现，方案 v1.0 未覆盖）

`app/services/profile.py:863-885` `update_nickname` 直接 `UPDATE users SET nickname`，**不经过任何敏感词检测**（对比：自定义标签 `:729`、关于我问答 `:824` 均已走 `moderate_text`）。

## 三、微信内容安全能力选型

### 3.1 三个接口对比

| 维度 | `imgSecCheck` | `mediaCheckAsync` | `msgSecCheck` |
| --- | --- | --- | --- |
| 路径 | `POST /wxa/img_sec_check` | `POST /wxa/media_check_async` | `POST /wxa/msg_sec_check` |
| 同步性 | **同步**，直接返回 | **异步**，30 分钟内回调 | **同步**，直接返回 |
| 结果获取 | 响应体 `errcode` | 消息推送 `MsgType=event` / `Event=wxa_media_check` | 响应体 `errcode` |
| 媒体形态 | base64 图片 | URL（图片 / 音频） | 文本 |
| 图片格式 | PNG / JPEG / JPG / GIF | jpg / jpeg / png / bmp / gif | — |
| 图片大小 | ≤ 1MB | ≤ 10MB | — |
| 图片尺寸 | ≤ 750×1334px | 未设限 | — |
| 额度（单 appId） | 2000 次/分、20 万次/天 | 2000 次/分、20 万次/天 | 同量级 |
| 费用 | 免费 | 免费 | 免费 |
| 前置条件 | 企业/组织主体 + 微信认证 | 同左 | 同左 |

**违规判定**：`errcode = 87014` 表示命中违规（risky）。`mediaCheckAsync` 的回调中 `result.suggest` 取 `risky` / `review` / `pass`，`result.label` 取 `100 正常 / 20001 政敏 / 20002 色情 / 20006违法违规 / 21000 其他`。

**场景值（scene）**：`1 资料`（头像、昵称）、`2 评论`、`3 论坛`、`4 社交日志`。头像取 `1`，社区动态取 `3`，评论取 `2`。

> 参数与限制以微信官方文档为准，实施前需复核 `https://developers.weixin.qq.com/miniprogram/dev/server/API/sec-center/sec-check/`。

### 3.2 选型结论

**Phase 1 用 `imgSecCheck`**：

- 同步返回 ⇒ 一个 HTTP 请求内闭环，不需要消息推送服务器、不需要 `trace_id` 对账、不需要处理 30 分钟延迟窗口。
- 后端当前**没有**消息服务器（无 `echostr` 校验、无 AES 解密），走 `mediaCheckAsync` 要从零建这一层，Phase 1 不宜承担。
- 额度对当前规模充足。

**`mediaCheckAsync` 留作 Phase 3**，触发条件：需要 OCR 文字识别、音频检测、单文件 >1MB 或 >750×1334px。

### 3.3 视频的边界（必须明确）

微信内容安全接口 **v2 只支持 `media_type` 1=音频、2=图片，不支持视频**。因此 `profile.py:1251 upload_video` 与 `community_media.py:146` 的视频分支**无法直接送检**。

处理方案（Phase 3）：自研抽帧，取首/中/尾 3 帧各走一次 `imgSecCheck`，全部通过才算通过。Phase 1 期间视频维持现状（人工审核）。

## 四、目标架构

### 4.1 主链路

```
上传请求
  │
  ├─ 读字节（≤ IMAGE_MAX_BYTES = 5MB，profile.py:57）
  ├─ 格式归一：若非 PNG/JPEG/JPG/GIF → Pillow 转 JPEG
  ├─ 尺寸归一：缩放到 ≤ 750×1334px，压到 ≤ 1MB
  ├─ 取 users.openid（缺失 ⇒ 跳过自动检测，走人工）
  │
  ├─▶ 微信 imgSecCheck（scene=1 资料）
  │     │
  │     ├─ errcode=0 ──────────▶ 通过
  │     │                          ├─ 转 webp + 缩略图 → 落盘
  │     │                          ├─ user_media.review_status = 1
  │     │                          ├─ UPDATE users.avatar（首次生效）
  │     │                          └─ sec_check_status = 1（通过）
  │     │
  │     ├─ errcode=87014 ──────▶ 违规
  │     │                          ├─ 不落盘（或落盘后立即删）
  │     │                          ├─ sec_check_status = 2 + sec_check_label
  │     │                          ├─ 写 business_audit_log
  │     │                          └─ HTTP 422「图片含违规内容，请更换」
  │     │
  │     └─ 超时/网络异常/协议错 ──▶ 异常
  │                                ├─ 落盘，review_status = 0
  │                                ├─ sec_check_status = 3 + sec_check_error
  │                                ├─ 写 community_moderation_task（人工队列）
  │                                └─ 头像不生效（按「检测通过才生效」口径）
  └─────────────────────────────────────────────────────────
```

### 4.2 展示口径（核心设计）

**写侧收紧，读侧零改动。**

只要 `users.avatar` 只在 `review_status=1` 时写入，所有读路径（`get_profile` / `discovery` / `social` / `public_preview` / `candidate_visibility`）自动一致——不必逐个改 SQL，也不存在漏改一处的问题。这正是 `待完成事项.md:621` 提出的「统一口径」解法。

三态语义：

| 场景 | `users.avatar` | 展示 |
| --- | --- | --- |
| 自动检测通过 | 写入新值 | 展示新头像 |
| 自动检测异常（转人工） | **不写**，保留旧头像 | 展示旧头像 / 占位图 |
| 判定违规 | **不写** | 展示旧头像 / 占位图 |

> 与相册/视频/背景墙现状对齐：`profile.py` 的 `_get_media(approved_only=True)` 已在 public 场景按 `review_status` 过滤，头像改为同口径后即消除 `待完成事项.md:621` 所述的「头像与相册口径不一致」。

### 4.3 与 2026-10-26 旧口径的差异

旧决策（`待完成事项.md:750`）：`review_status=0`（待审）放行展示。
新决策：**检测通过才生效** ⇒ `review_status=0` 一律不对外展示。

该变更会影响**存量数据**（见 §7.6），实施时须同步更新该条目并给出存量处置口径。

### 5.1 新增 `app/services/wechat_sec_check.py`

仿 `app/services/aliyun_content_moderation.py` 的适配器结构。

```python
@dataclass(frozen=True)
class SecCheckDecision:
    action: str                    # allow / reject / manual_review
    risk_level: int = 0            # 0 正常 / 1 疑似 / 2 违规 / 3 服务异常
    label: int | None = None       # 微信 label：100/20001/20002/20006/21000
    provider: str = "wechat_img"
    raw_errcode: int | None = None
    error: str | None = None
```

| 函数 | 职责 |
| --- | --- |
| `check_image(data: bytes, *, scene: int, openid: str) -> SecCheckDecision` | 归一化 → 调 `img_sec_check` → 归一化响应 |
| `_normalize_for_wechat(data: bytes) -> bytes` | 转 JPEG + 缩放 ≤750×1334 + 压到 ≤1MB（复用 `_image_outputs` 之外的独立工具） |
| `_classify(payload: dict) -> SecCheckDecision` | `errcode==0` → allow；`87014` → reject(label)；其他 → manual_review |

**兜底对齐**：`ALIYUN_CONTENT_MODERATION_FAIL_MODE` 的范式 → 新增 `WECHAT_SEC_CHECK_FAIL_MODE=manual_review|reject`，默认 `manual_review`（本次已定决策）。

## 七、关键约束、坑与风险

### 7.1 webp 格式（最易踩）

微信 `imgSecCheck` **不支持 webp**。当前 `_image_outputs`（`profile.py:443`）在存储前统一转 webp。若在转码后检测，将永久失败。⇒ **检测必须插在 `_image_outputs` 之前**，且对原始非 JPEG/PNG 的输入先转 JPEG。

### 7.2 尺寸与体积

原图普遍 >1MB、>750×1334px。送检前必须归一化，否则微信直接报参数错误。归一化后送去检测的是缩略图版本——对违规内容的判定不受影响。

### 7.3 openid 强约束

微信要求「用户最近两小时内访问过小程序」。以下情形无有效 openid 或可能超窗：
- 后台红娘代传（`auto_approve=True` 路径）
- 长期未打开小程序的老用户
⇒ 这些场景**跳过自动检测直接转人工**，不得因缺 openid 而放行。

### 7.4 额度与幂等

- 额度 2000 次/分、20 万次/天。按当前用户规模足够，但需**图片 hash 缓存**（`WECHAT_SEC_CHECK_CACHE_TTL_SECONDS`）避免同一用户反复换头像重复消耗。
- 上传接口本身不幂等（每次 uuid4 新文件），检测失败重试会重复消耗额度——缓存同时承担幂等职责。

### 7.5 主体资质（硬性前置）

微信内容安全接口要求小程序为**企业/组织主体且已完成微信认证**，个人主体调用会失败。**实施前必须确认生产小程序的主体资质与认证状态**，否则整个方案不成立。这是最需要先验证的外部依赖。

### 7.6 存量数据

存量 `user_media` 的 `sec_check_status` 全为 0（未检测），且已有 `users.avatar` 指向未经检测的历史图。三种处置口径，需用户拍板：

| 口径 | 做法 | 影响 |
| --- | --- | --- |
| A. 存量豁免 | 存量不追溯，仅约束新上传 | 存量违规图长期存在，审核视角下仍是暴露面 |
| B. 批量刷检 | 写离线任务对存量头像批量送检，违规的清空 `users.avatar` | 一次性消耗额度，需限流与断点续跑 |
| C. 灰度收紧 | 新上传严格执行，存量维持展示，观察一段时间再收紧 | 折中，两套口径并存期 |

### 7.7 人工审核 SLA

异常转人工后，`review_status=0` 的头像**不生效**（§4.2），用户会看到头像消失。若人工审核滞后，用户感知为「头像丢了」。⇒ 需要明确人工审核 SLA，并考虑在检测异常时**保留旧头像**（本次决策是「不生效」，但建议评估：异常时保留旧头像比置空更优）。

### 7.8 违规图落盘时机

判定违规时**不落盘**最安全；但若已落盘需保证删除且不留可访问 URL。⇒ 建议检测通过后再落盘。
