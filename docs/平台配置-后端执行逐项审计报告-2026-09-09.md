# 平台配置 · 后端执行逐项审计报告

> 审计日期：2026-09-09
> 审计范围：「平台配置」菜单 7 个子页面所写全部配置域（`platform_*`）在后端运行时是否真的被读取并影响逻辑。
> 结论先行：**7 个页面中，绝大多数配置只是"能存、能读回、有审计"，后端业务运行时并没有消费它们**；唯一真正被消费的是 `platform_permissions` 里的配额类扁平键（每日浏览/申请/爆灯/纸飞机次数），且**页面改的是嵌套分组、后端读的是顶层扁平键，两者不对应**——即权限配置页即便改了，也不会影响后端限额。

---

## 一、后端消费配置的唯一入口

后端读取这份快照配置的运行时函数只有一个：

```python
# app/services/admin_config.py:232
async def get_runtime_value(db, namespace, key, fallback): ...
```

全后端对它的调用，**只有 2 个文件、8 处**：

| 调用位置 | namespace | 键名 | 作用 |
| --- | --- | --- | --- |
| `services/discovery.py:429` | platform_permissions | `free_browse_daily_limit` | 非VIP每日浏览配额 |
| `services/discovery.py:449` | platform_permissions | `high_match_browse_bonus` | 高分浏览加成次数 |
| `services/discovery.py:736-737` | platform_permissions | `free_apply_daily_limit` / `vip_apply_daily_limit` | 非VIP/VIP每日申请认识配额 |
| `services/discovery.py:897,901` | platform_permissions | `vip_superlike_daily_limit` / `free_superlike_daily_limit` | VIP/非VIP每日爆灯配额 |
| `services/community.py:1551-1558` | platform_permissions | `free/vip_apply_daily_limit`、`paper_plane_daily_limit` | 社区申请 + 纸飞机每日配额 |

除此之外，没有任何其他后端代码读取 `admin_config_snapshot`（grep 全仓库确认：无直接 `SELECT config_json` 的其他调用，无 `get_config()` 的运行时调用）。

后端配置表 `admin_config_snapshot` / `admin_config_audit_log` 在 `database_setup_marriage.py:917` 建表；默认值由 `ensure_defaults()` 懒初始化。

**关键结构性发现**：后端消费的是 `platform_permissions` 的**顶层扁平键**（如 `free_browse_daily_limit`），而前端「权限配置」页保存的是**嵌套分组**：

```
{ browse: { gender, pageLimit, otherPage, single }, view: { photo, video, voice, ... },
  state: { delegate, secret, pause, single }, line: { realname, agreement, times, beLinked },
  other: { idcard, hongniangShow, multiAccount, avatar, photo, martial, edu } }
```

→ 后端读取的键名在页面上根本不存在；页面编辑的键后端根本没人读。**即便权限配置页的所有值都改过，后端限额逻辑拿到的仍是旧值/默认值。**

## 二、逐页面审计

### 1. 基本配置（`/platform-config-basic`）

| Tab | namespace | 后端是否执行 |
| --- | --- | --- |
| 基本配置 | `platform_basic` | ❌ 无任何消费。平台名称/Logo/分享标题/缺省头像等后端运行与用户端接口均未读取 |
| 运营模式 | `platform_operation` | ❌ 无任何消费（后端无"线上/线下模式"分支读取） |
| 信息登记引导页配置 | `platform_register_guide` | ❌ 无任何消费（会员注册/登记流程不走该配置） |
| 基本资料登记配置 | `platform_register_fields` | ❌ 无任何消费（登记字段在后端是 `core/profile_tags.py` 常量 + 数据库字段） |
| 私密信息登记与展示配置 | `platform_private_fields` | ❌ 无任何消费 |
| 筛选功能配置 | `platform_filter_config` | ❌ 无任何消费（筛选/浏览偏好不读此配置） |

> 佐证：会员资料下拉选项（学历/职业/婚姻/年收入/城市/标签等）来自后端**写死的常量** `app/core/profile_tags.py`（约 20 组分类、190+ 选项），由 `services/discovery.py`、`services/profile.py`、`schemas/auth.py` 直接引用——与 `platform_base_data`、`platform_register_fields` 等配置域完全无关。

### 2. 导航配置（`/platform-navconfig`）→ `platform_navigation`
❌ **无任何消费**。后端不存在读取导航入口列表并生成用户端导航的接口/逻辑；小程序/App 导航属前端静态配置。

### 3. 平台布局（`/platform-page`）→ `platform_layout`
❌ **无任何消费**。首页模块开关、样式、统计栏数字、VIP 展示数量等均无后端读取点（用户端首页由小程序/H5 前端自行决定）。

### 4. 权限配置（`/power-config`）→ `platform_permissions`
⚠️ **部分存在消费但键不对应（实际不生效）**：
- 后端确有的 8 个 `get_runtime_value` 调用全部落在本 namespace 的配额类**扁平键**上。
- 前端页面保存的是 `browse/view/state/line/other` **嵌套键**，与后端读取键名无交集。
- 前端页面描述的"浏览展示权限、资料查看权限、状态更改权限、牵线权限、其他权限"（约 28 个开关/单选/输入）**后端零消费**。
- 后端真正消费的限额值（免费浏览 8 次/天等）由 `ensure_defaults` 初始默认 或 `app/core/config.py` 的 settings 兜底，**页面无法修改**。

### 5. 内容配置（`/platform-content`）

| Tab | namespace | 后端是否执行 |
| --- | --- | --- |
| 文案配置 | `platform_content` | ❌ 无任何消费（协议/弹窗/介绍文案无读取接口；小程序内文案为前端内置） |
| 自定义页面 | `platform_custom_pages` | ❌ 无任何消费 |
| 会员中心 | `platform_member_states` | ❌ 无任何消费（会员状态名称/描述无后端读取） |

### 6. 基础数据（`/platform-base`）→ `platform_base_data`
❌ **无任何消费**。29 组可维护字典仅存储于此；会员端下拉选项、审核原因、跟进模板等数据源均为**后端代码常量或各自业务表**（如 `profile_tags.py`、`config_membership_package`、业务表字典），不读此配置域。

### 7. 收费配置（`/platform-payconfig`）→ `platform_pay`
❌ **无任何消费**。VIP 套餐/价格等真实数据源是数据库表 `config_membership_package`（被 `services/membership.py`、`payments.py`、`quotas.py`、`discovery.py` 读取），**不是** `platform_pay` 配置域。审核费、实名费、置顶费、牵线套餐等在该页的修改不会影响任何后端计费逻辑。

## 四、为什么会出现这个局面

1. **配置域是"后补"的管理面**：`admin_config_snapshot` + 平台配置页面是为后台可视化新增的存储层；而既有业务代码（先写）消费的是 settings 常量、`core/profile_tags.py` 常量、`config_membership_package` 等业务表，二者从一开始就不是同一套数据源。
2. **前端接线时按"UI 结构"造键**：各页面按自己控件的形状设计 JSON（嵌套分组），未与后端已消费的键名对齐，导致"最可能生效的权限配额键"也对不上。
3. **缺少用户端公开读取接口**：后端没有把 `platform_*` 配置域暴露给小程序/App/H5 的公共接口（配置读取均在 `/admin/configs/*` 管理端、需 `platform.config.read` 权限），因此即便想让客户端读，也读不到。

## 五、要让"配置真正驱动后端"需要的动作（按优先级）

| 优先级 | 配置域 | 需要做的事 |
| --- | --- | --- |
| P0 | `platform_permissions`（配额类） | 将 discovery/community 的 `get_runtime_value` 键与前端保存键对齐（二选一：a. 后端改读嵌套 `browse/view/...` 下的对应键；b. 前端保存时把 UI 值映射成后端已读的扁平键 `free_browse_daily_limit` 等）。并让页面把 8 个配额数字暴露出来 |
| P1 | `platform_pay` | 会员/VIP/服务收费统一改为读取该配置域（或把页面改成直接维护 `config_membership_package` 等真实表），否则"收费配置"永远不落地 |
| P1 | `platform_base_data`、`platform_register_fields/private/filter` | 字典/登记字段改为运行期从配置域下发：会员端表单选项接口改为读配置域合并 `profile_tags.py`；或删除页面避免误导 |
| P2 | `platform_basic` / `platform_content` / `platform_navigation` / `platform_layout` 等 | 若需客户端展示（平台名/分享文案/协议/导航/首页模块），新增用户端公共接口把对应 namespace 下发（去敏感化），供小程序/H5 渲染；否则这些页面仅为"运营存档" |
| P3 | 运营模式 `platform_operation` | 若真要做全平台线上/线下开关，需要在注册/浏览/牵线/会员等入口增加该开关判断 |
